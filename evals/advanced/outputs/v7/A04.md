The query has two independent defects: its `WHERE` clause drops customers without a paid order, and joining two independent child collections multiplies their monetary contributions. Moving the predicate repairs the customer population; counting distinct orders repairs the count; neither change repairs the sums. [A04-QUERY]

## What the current query returns

All monetary values below are **integer cents**.

| name | paid_orders | gross | refunds | net |
| --- | ---: | ---: | ---: | ---: |
| Ada | 4 | 320 | 40 | 280 |
| Ben | 1 | 40 | `NULL` | 40 |

Cy has no output row. I executed the supplied query against the supplied data in SQLite and obtained this result.

For Ada's paid order 10, the line amounts are `2 × 50 = 100` and `1 × 60 = 60`. Its refunds are 15 and 5. Both lines match both refunds because each join uses the order ID, with no relationship pairing a particular line with a particular refund. The intermediate rows for this order are therefore:

| Order | Line amount | Refund amount |
| ---: | ---: | ---: |
| 10 | 100 | 15 |
| 10 | 100 | 5 |
| 10 | 60 | 15 |
| 10 | 60 | 5 |

This relation has one row per **line–refund combination within an order**, not one row per order, line, or refund. Consequently:

- `COUNT(o.id)` counts order 10 four times.
- Gross is `100 + 100 + 60 + 60 = 320`.
- Refunds are `15 + 5 + 15 + 5 = 40`.
- Net is `320 − 40 = 280`.

Each line is repeated once per refund, and each refund is repeated once per line. Their multiplication happens before `GROUP BY`; grouping afterward sums the already repeated values. [A04-DATA, A04-QUERY]

Ben's order 20 has one line and no refund. The left join preserves one row with line amount 40 and a `NULL` refund. `SUM(r.amount)` is therefore `NULL`, but the net expression substitutes zero for that refund total, giving 40.

Cy initially survives the left joins as a customer row with `NULL` order fields. However, `WHERE o.status = 'paid'` does not evaluate to true for that row, so it is removed before grouping. Ada's cancelled order 11 is also removed and contributes nothing. A customer whose orders were all cancelled would likewise disappear. [A04-QUERY]

## The correct business result

Using each paid order, line, and refund once gives:

| name | paid_orders | gross | refunds | net |
| --- | ---: | ---: | ---: | ---: |
| Ada | 1 | 160 | 20 | 140 |
| Ben | 1 | 40 | 0 | 40 |
| Cy | 0 | 0 | 0 | 0 |

Ada's gross is `2 × 50 + 1 × 60 = 160`, refunds are `15 + 5 = 20`, and net is 140. Ben contributes 40 gross and no refunds. Cy still receives a row because the required reporting population is every customer. These totals also reconcile to 2 paid orders, 200 cents gross, 20 cents refunded, and 180 cents net across all customers. [A04-DATA, A04-CONTRACT]

## Aggregate the independent children before joining

First reduce each child table to at most one row per order. Then those results can safely join to paid orders without multiplying one another:

```sql
WITH line_totals AS (
    SELECT order_id,
           SUM(quantity * unit_price) AS gross
    FROM line
    GROUP BY order_id
),
refund_totals AS (
    SELECT order_id,
           SUM(amount) AS refunds
    FROM refund
    GROUP BY order_id
)
SELECT c.name,
       COUNT(o.id) AS paid_orders,
       COALESCE(SUM(lt.gross), 0) AS gross,
       COALESCE(SUM(rt.refunds), 0) AS refunds,
       COALESCE(SUM(lt.gross), 0)
         - COALESCE(SUM(rt.refunds), 0) AS net
FROM customer AS c
LEFT JOIN orders AS o
       ON o.customer_id = c.id
      AND o.status = 'paid'
LEFT JOIN line_totals AS lt
       ON lt.order_id = o.id
LEFT JOIN refund_totals AS rt
       ON rt.order_id = o.id
GROUP BY c.id, c.name
ORDER BY c.id;
```

The grain—the entity represented by one row—changes as follows:

| Relation | Grain |
| --- | --- |
| `customer` | One customer |
| `orders` | One order, uniquely identified by `id` |
| `line` | One line record |
| `refund` | One refund record |
| `line_totals` | One order having at least one line |
| `refund_totals` | One order having at least one refund |
| Joined rows before final grouping | One paid order per customer, or one placeholder for a customer with none |
| Final result | One customer |

The safety comes from `GROUP BY order_id`: each child total has at most one matching row for an order's primary key. A left join to either total therefore cannot increase the number of rows representing that order.

Putting the paid condition in `ON` limits which orders match while retaining every customer. `COUNT(o.id)` then counts each paid order once and ignores the `NULL` order ID in a no-order placeholder. `COUNT(*)` would incorrectly count that placeholder as an order.

A paid order with no lines still has an order row, so it counts as one and contributes zero gross. Its refunds remain independently available through `refund_totals`. For example, an order with no lines and a 5-cent refund correctly contributes gross 0, refunds 5, and net −5 under the stated formula. An order with neither lines nor refunds contributes one order and zero to all monetary totals. I checked both edge cases with this structure in SQLite.

## Why the proposed shortcuts are insufficient

**Move the predicate and use `COUNT(DISTINCT o.id)`.** These changes preserve customers and count each paid order once, respectively. But Ada's four line–refund combinations still exist. The two sums still read 320 and 40, so net remains wrong at 280. Changing the input to one aggregate function does not change the rows seen by other aggregate functions.

**Use `SUM(DISTINCT ...)`.** `DISTINCT` removes repeated numeric values, not repeated appearances of the same business record. On this particular dataset, the distinct amounts happen to yield Ada's correct totals. That coincidence does not establish a valid query.

For example, two genuine quantity-one lines priced at 50 cents each must contribute 100 cents. `SUM(DISTINCT quantity * unit_price)` counts the value 50 once and returns 50. Identical unit prices cause this error when the extended line amounts are equal; different quantities can instead produce different amounts. Two legitimate refunds of 5 cents must similarly total 10, while `SUM(DISTINCT amount)` would return 5. Equal amounts across different orders would also be incorrectly collapsed within a customer group. Record identity cannot be replaced by amount equality.

## Missing records, zero values, and `COALESCE`

These cases have different meanings even when the contract displays the same zero:

| Case | Underlying evidence | Monetary display |
| --- | --- | ---: |
| An order has no refund | No matching refund record; the left join supplies `NULL` | 0 |
| An order has a zero refund | A real record whose amount is 0 | 0 |
| A customer has no paid orders | No contributing order; the customer has a placeholder row | 0 |

`SUM` ignores `NULL` inputs and returns `NULL` when it has no non-`NULL` values to sum. In contrast, a real zero amount contributes a numeric zero. `COALESCE(total, 0)` converts a missing total to the requested display value; it intentionally does not preserve the distinction between no refund and a zero-valued refund. If refund existence matters later, aggregate a refund-record count as a separate metric.

For Cy, the rewritten query does create a customer group, but that group contains the placeholder rather than a paid order. Its monetary sums are `NULL` until converted to zero. The original query never creates that group because its `WHERE` clause removed Cy, and `COALESCE` cannot recreate a missing row.

The original net calculation also converts only the refund sum. For a paid order with no lines, gross can remain `NULL`, and `NULL` minus any amount remains `NULL`. The rewrite converts both totals before subtraction. None of this zero handling can repair multiplied rows or an incorrect count.

Finally, the safety depends on keeping the stated grain. Adding a raw one-to-many table—such as multiple shipments per order—before the final grouping could repeat each order's already aggregated gross and refunds again. Aggregate any new independent child collection to the appropriate join key before attaching it, and recheck that every intended order still appears once before customer-level sums are computed.
