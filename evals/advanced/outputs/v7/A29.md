## Bring this route into compliance

1. **Require the correct audience in the active verifier.** Enable audience checking and configure the expected value as exact array membership of `inventory-api`. Reject a missing audience or a nonmatching value. Preserve the valid-signature and `corp` issuer checks.
2. **Remove expiration grace and enforce the strict boundary.** Set leeway to zero, but also ensure the actual acceptance predicate is `now < exp`. Merely substituting zero into the supplied gateway predicate yields `now <= exp`, which still accepts a token at the exact expiration instant. If configuration cannot express strict comparison, change the verifier or add an enforcing check on the trusted request path.
3. **Retain the backend's exact read-scope requirement.** Continue rejecting write-only tokens on this route. No scope implication should be introduced unless the policy changes.
4. **Verify the effective deployment.** Confirm the new configuration and predicate are active on the instances serving this route, then record end-to-end results and the layer responsible for each rejection. A configuration file or planned rollout alone does not establish active enforcement. [A29-POLICY7] [A29-DEPLOYMENT]

A gateway-based design assumes that every request reaching this backend route has traversed that verifier and that the authenticated handoff from gateway to backend cannot be forged. Verify that trust path. If it cannot be guaranteed, the backend should independently enforce the signature, issuer, audience, and strict expiration requirements as well as scope. The packet does not establish that a direct-backend bypass exists; this is a condition to verify, not an observed incident finding.
