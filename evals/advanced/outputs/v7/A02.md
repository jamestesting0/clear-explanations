The final handler is the error handler, which records `outer:audit-failed`. The write error is initially recovered into `"fallback"`, but the exception thrown by `finally` replaces that fulfilled outcome. The nested microtask also waits its turn; it does not interrupt the callback that schedules it. [A02-CODE]

## Observable order

The program prints:

```text
start | end | first | peer | await-resumed | nested | write:row | caught:write-failed | audit | outer:audit-failed | timer
```

I ran the supplied standalone script under Node v24.22.1 and obtained that sequence.

There are two ordering questions: when callbacks become eligible to run, and what the promise chain's outcome becomes.

### How the callbacks reach that order

The initial script runs synchronously. It records `start`, registers the promise callback that will record `first`, queues `peer`, and starts the async function. That function reaches `await 0` and suspends, scheduling its continuation. The script registers the timer and records `end`. None of the queued callbacks interrupts this initial execution.

At the end of that synchronous work, the relevant queued microtasks are ordered as follows:

| Already queued callback | What it will record |
| --- | --- |
| First promise reaction | `first` |
| Explicit `queueMicrotask` callback | `peer` |
| Async function continuation | `await-resumed` |

When the first callback runs, it records `first` and queues the callback for `nested`. **Queueing appends work for later execution; it does not call that work immediately.** `peer` and the async continuation are already waiting, so they run before `nested`. Thus the observable sequence is `first`, `peer`, `await-resumed`, `nested`.

Returning `Promise.resolve("row")` also does not call the next `.then` inline. The promise returned by the first `.then` must adopt the returned promise's outcome, and the downstream handler runs through promise scheduling. Even an already fulfilled promise does not turn `.then` into a synchronous function call. The already queued `nested` therefore runs before `write:row`. No particular count of internal promise jobs is needed to establish this observable order.

`await 0` needs no I/O. It suspends the async function even though the value is immediately available, then resumes it through the promise job queue. That continuation runs before the timer. All the microtasks generated by this finite chain finish before the timer callback records `timer` and prints the array. [A02-CODE]

### How the promise outcome changes

| Handler | Action | Outcome passed onward |
| --- | --- | --- |
| First `.then` | Returns a fulfilled promise containing `"row"` | Fulfilled with `"row"` |
| Write `.then` | Records `write:row`, then throws | Rejected with `Error("write-failed")` |
| `.catch` | Records the error, then returns `"fallback"` | Fulfilled with `"fallback"` |
| `.finally` | Records `audit`, then throws | Rejected with `Error("audit-failed")` |
| Final `.then` | Runs its rejection callback | Records `outer:audit-failed` |

A `finally` callback normally preserves the earlier fulfillment or rejection when it finishes successfully. But if it throws, or returns a promise that rejects, that failure becomes the chain's new rejection. The callback's purpose as “housekeeping” gives it no exemption from this rule. Consequently, `success:fallback` is never recorded. The final rejection callback handles the audit failure in this program. [A02-CODE]

The incident summary is therefore wrong about immediate nested execution, wrong about `await` requiring I/O, correct that this particular `catch` creates a fallback value, and wrong that `finally` cannot change the result. Those are separate mechanisms and need separate corrections.

## Preserve the save outcome while observing audit failures

One small correction is to make the audit path finish successfully after it has either completed auditing or recorded its failures. Keep the write's recovery policy separate, so a write error with no fallback remains a rejection.

The following illustrative structure **waits for audit and, if audit fails, waits for one delivery attempt to the error collector**. `write`, `audit`, and `sendToErrorCollector` stand for application functions that may throw synchronously or return promises. `fallback` is a descriptor containing an already available draft value, such as `{ available: true, value: draft }`, or `{ available: false }`.

```javascript
const failedAuditDeliveries = [];

async function auditAndCollect() {
  try {
    await audit();
  } catch (auditError) {
    try {
      await sendToErrorCollector({ kind: "audit", error: auditError });
    } catch (collectorError) {
      // Explicit terminal policy: keep both errors in local diagnostics.
      // This buffer append is assumed nonthrowing in normal operation.
      failedAuditDeliveries.push({ auditError, collectorError });
    }
  }
}

function saveWithAudit(write, fallback) {
  return Promise.resolve()
    .then(() => write())
    .catch(writeError => {
      if (fallback.available) return fallback.value;
      throw writeError;
    })
    .finally(auditAndCollect);
}
```

This preserves all three required operation outcomes:

- A successful write keeps its saved value.
- A failed write with an available fallback returns that draft.
- A failed write without a fallback rethrows the same `writeError`, so the caller receives the original failure.

In each case, `auditAndCollect` handles audit failures locally and attempts to send them to the separate collector. If collector delivery also fails, both errors remain in the explicit diagnostic buffer. This example makes no automatic retry; a caller or diagnostic interface can inspect that buffer. There is no detached collector promise whose rejection is left unhandled.

Because the audit helper fulfills after these handled paths, `.finally(auditAndCollect)` preserves the operation's prior outcome. It does not broadly recover the save itself: only the save's own `catch` may choose a fallback, and it rethrows when none exists. If the local diagnostic append is replaced with a fallible storage or logging operation, that replacement needs its own explicit failure policy too.

Waiting adds audit and collector latency to the save's completion, and a call that never settles can delay it indefinitely unless a timeout policy is added. It still does not guarantee that a browser will keep the page alive until audit delivery finishes. The local diagnostic buffer is also lost with the page; durable delivery would require a separately designed persistent queue or server-side mechanism. Those lifetime limits are distinct from the callback order forced by the self-contained program.
