**The current implementation finishes with value 7.** It rejects the delayed write from the older leader, but it does not reject an older command from the current leader. Those are two different ordering problems. [A07-STORAGE; A07-ARRIVALS]

## What each arrival does

Starting state: `max_token=40`, `value=0`.

| Arrival | Incoming command | Decision under the current rule | State afterward |
|---|---|---|---|
| 1 | A: token 41, sequence 1, value 6 | Accept: 41 is greater than 40. | `max_token=41`, `value=6` |
| 2 | B: token 42, sequence 2, value 8 | Accept: 42 is greater than 41. | `max_token=42`, `value=8` |
| 3 | A: token 41, sequence 2, value 9 | Reject: 41 is smaller than 42. | `max_token=42`, `value=8` |
| 4 | B: token 42, sequence 1, value 7 | Accept: equality is allowed, and sequence is ignored. | `max_token=42`, `value=7` |

The final overwrite is permitted by the implementation even though B issued sequence 1 before sequence 2. Storage sees arrival order, and its rule does not remember the order within B’s generation. [A07-STORAGE; A07-ARRIVALS]

## What leases and the existing check accomplish

A lease expiration ends A’s authority according to the lock service. It does not retract packets already sent, stop a paused process from resuming, or make storage consult the lock service. Arrival 3 is therefore possible even without overlapping leases. Checking the lease immediately before sending also leaves a gap: the lease can expire while the request is delayed. [A07-LEASE]

The token check is a **fence against older generations**: after storage has accepted token 42, token 41 cannot overwrite it. Its boundary matters: storage has to learn about the newer token first. It does not necessarily reject token 41 merely because A’s lease has expired somewhere else.

That fence does not order commands sharing token 42. Conversely, rejecting every token equal to `max_token` would reject legitimate later commands from B as well as retries. A leader needs an ordering field within its generation, not a blanket ban on further updates. [A07-STORAGE; A07-REVIEW]

## An atomic rule for both ordering and retries

For each resource, persist the greatest applied **revision**, defined as the pair `(token, sequence)`, together with the current payload, value, and response information. Compare pairs by token first, then by sequence when the tokens match. Thus `(42,1)` is newer than any `(41,sequence)`, while `(42,2)` is newer than `(42,1)`.

Perform the following comparison and any resulting update as one indivisible storage operation:

| Incoming revision compared with stored revision | Required behavior |
|---|---|
| Greater | Apply the replacement, record the new revision and payload, and report an applied business change. |
| Smaller | Reject as superseded; leave the value unchanged. |
| Equal, identical payload | Return an explicit duplicate/already-applied acknowledgment, with the recorded result as appropriate; make no new business change. |
| Equal, different payload | Return a conflict; leave the value unchanged. |

“Identical payload” should cover all fields that define the command’s effect. Reusing a revision for a different command is an error, not a retry. A retry must keep its original revision and payload. [A07-ARRIVALS]

For the supplied arrivals, the corrected rule accepts `(41,1)`, then `(42,2)`; it rejects both `(41,2)` and `(42,1)`. **The corrected final value is 8.** B can still make another legitimate update with `(42,3)`.

A retry of a command that has since been superseded takes the “smaller” branch. It does not change the value or count as a new business change. Remembering only the latest revision cannot tell whether that older command once applied or was always overtaken. If callers also need an exact historical result for every old retry, retain a durable command/result history keyed by revision. That is an additional acknowledgment guarantee, beyond preventing stale updates and duplicate effects.

## Where the remembered revision belongs

The revision must live at the storage authority that applies the value, and it must survive crashes and failovers together with that value. If replicas can accept writes, their coordination must preserve this same atomic rule for the resource. Otherwise, two servers could each accept a command against stale metadata, or a restart could forget the fence.

Keeping the revision only in a worker is insufficient: workers can fail independently, and another worker or a delayed packet can reach storage. Recording the revision separately from the value also creates a crash window between updating the two.

Local client clocks do not enforce this rule. They do not necessarily agree, and elapsed time at the sender does not determine which command arrives at storage first. The supplied token and sequence identify the required business order directly; enforcement must occur when storage attempts the change.

## What is and is not guaranteed

The corrected rule makes the stored revision increase whenever a new command is applied. Once a newer revision has applied, an older one cannot overwrite it; retries cannot repeat an applied change. This is an ordering guarantee for commands reaching the authoritative storage.

It does not ensure that every issued command arrives or executes: sequence 1 can be overtaken by sequence 2. It also does not guarantee delivery of acknowledgments, determine whether a lost-response command ran without consulting stored information, or ensure eventual progress during an indefinitely long network partition. Connectivity, retries, and an available storage authority are still needed for progress. No ordering check can manufacture delivery across a partition.
