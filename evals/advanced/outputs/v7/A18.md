**`structuredClone` comes closest to the report contract, but it still drops the symbol-keyed marker and rejects the demonstrated function value.** Spread retains shared mutable objects; the JSON round trip changes the date into a string and removes the property whose value is `undefined`. None is interchangeable with the others under the current contract. [A18-CODE, A18-CONTRACT]

### Spread: a new outer object containing shared objects

`{ ...source }` copies the values of the source's own enumerable properties, including the enumerable symbol-keyed property. “Own” means attached directly to `source`; “enumerable” marks a property for operations such as this copying step.

The copied values for `meta` and `created` are references to the original objects. Consequently, changing `source.meta.tag` and mutating the original date also changes what `spread` sees. Its date remains a `Date`, but it is the same mutable date object as the source's. Its `optional` property is present with value `undefined`, and its property keyed by the original `secret` symbol has value `"token"`. [A18-CODE]

This directly disproves the claim that creating a new outer object makes the copy deep: the nested objects remain shared.

### JSON round trip: independent JSON data with changed representation

Serializing and parsing reconstructs `meta` as a separate object, preserving its earlier `"old"` tag. The date serializes as its ISO timestamp string; parsing does not automatically reconstruct a `Date`. The `optional` property is omitted because its value is `undefined`, and the symbol-keyed property is omitted as well. [A18-CODE]

Those losses disprove the claim that a JSON round trip preserves every JavaScript value. Here, even the distinction between an absent property and a present property valued `undefined` matters to the API. A missing property can also yield `undefined` when read, so testing the read value alone would miss that difference. [A18-CONTRACT]

### Structured clone: independent supported values

`structuredClone` produces a separate `meta` object and a separate `Date` with the original timestamp. It also preserves the own `optional` property with value `undefined`. For this ordinary source object, it copies the enumerable string-keyed properties and omits the symbol-keyed property. [A18-CODE]

All three techniques leave out `hidden`, which is nonenumerable, and `inherited`, which belongs to the source's prototype. None preserves that custom prototype relationship here; the copied objects do not acquire `inherited: 9` through it either. These omissions are distinct from copying an own property with an undefined value.

## Running a getter is different from copying its descriptor

The source's `amount` property has a getter: code that runs when its value is read. The copies are made sequentially:

1. Spread reads `source.amount`, incrementing `reads` to 1, and stores the number 1.
2. JSON serialization reads it next, incrementing `reads` to 2, and writes the number 2 into the serialized representation.
3. Structured cloning reads it next, incrementing `reads` to 3, and stores the number 3. [A18-CODE]

Each result has an ordinary data property containing its number, rather than the source's getter descriptor. That is why inspecting the result descriptor's `.get` produces `undefined` and the logged `amountGetter` is the string `"undefined"`. Reading the copies during logging runs no source getter, so the final count stays at 3.

Thus a built-in copying operation can run user code while gathering values without retaining that code on its result. The third reviewer's claims about both descriptor preservation and absence of user-code execution are contradicted by this fixture. Materializing `amount` once fits the requirement that repeated report reads should not increment a hidden counter; whether report creation may run a getter is a separate policy decision. [A18-CLAIMS, A18-CONTRACT]

## Choosing a report representation and failure policy

For the demonstrated `meta`, `Date`, and `undefined` values, structured cloning satisfies the required independence and types. It does **not yet satisfy the marker requirement**. There are two explicit options:

- Preserve the known marker deliberately, using the same symbol key and copying its current string value into the report. This is a specific transformation for the demonstrated marker, not a promise to clone arbitrary symbol-associated values.
- Obtain and document the contract change removing the marker, then update its consumer. The owner's willingness to consider removal is not itself the completed change. [A18-CONTRACT]

A deliberate data-transfer representation could select the report fields, copy the nested report data and date, preserve the present `undefined` field, and read `amount` once under a documented rule. This also makes it possible to reject unexpected accessors if executing them during report construction is unacceptable.

The final experiment passes an object with an own function-valued property to `structuredClone`; it throws `DataCloneError`. A plugin introducing such a property can therefore turn a previously successful snapshot into a failure. The helper should declare whether unsupported values cause a clear rejection or whether particular fields undergo an explicitly defined transformation or omission. Silently falling back to JSON would introduce additional date and property-presence changes that violate this report contract.

The demonstration establishes behavior for the types actually shown; it does not establish support for arbitrary JavaScript objects, custom class semantics, or every possible plugin value. Tests should check the required types, property presence, marker policy, mutation independence, getter behavior, and failure behavior. Equal-looking JSON text cannot establish those properties—and this program's selected diagnostic fields already expose several differences. [A18-CODE, A18-CLAIMS]
