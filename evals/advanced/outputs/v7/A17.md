The callbacks capture different things: `late` shares a variable that ends up referring to the original second dictionary; `objects` saves each dictionary reference; `values` saves each number. **Replacing `rows[1]` changes the list's reference, not the references already held by the callbacks or `saved_second`.** [A17-CODE]

## Exact output

Running the supplied program produces:

rows [{'n': 10}, {'n': 20}]

## What each callback retains

Call the original dictionaries **D1**, initially `{"n": 1}`, and **D2**, initially `{"n": 2}`. `saved_second` refers to D2.

| Construction | Evaluated while building callbacks | Looked up when called with no arguments |
| --- | --- | --- |
| `late` | Each lambda is created with access to the same comprehension variable `row`. | The current value of that variable, then its dictionary entry `"n"`. |
| `objects` | Each `row=row` default saves the reference currently held by `row`: D1 or D2. | The `"n"` entry of that saved dictionary. |
| `values` | Each `row["n"]` default reads the number immediately: 1 or 2. | The saved default number; no dictionary lookup occurs. |

Within the `late` comprehension, the loop assigns D1 and then D2 to one shared `row` binding. The lambdas do not receive independent bindings on each iteration. After the comprehension finishes, both still access that binding, whose final value is D2. It is a reference to a dictionary, not a reference to the list's second slot. [A17-CODE]

Before S1, `rows[0]["n"] = 10` **mutates D1**. The first `objects` callback therefore sees 10. The historical number already captured by the first `values` callback remains 1.

Next, `rows[1] = {"n": 20}` creates a new dictionary, D3, and replaces the reference in that list slot. It does not change D2. Both `late` callbacks, the second `objects` callback, and `saved_second` still refer to D2, whose number is still 2. That accounts for every result at S1.

Then `saved_second["n"] = 99` mutates D2. Both `late` callbacks and the second `objects` callback observe 99 at S2. D2 remains alive through those references even though it is no longer present in `rows`. The list itself contains D1 and D3, so its final numbers are 10 and 20. [A17-CODE]

## Which behavior fits which contract?

| Intended contract | Existing construction that satisfies it here |
| --- | --- |
| Return each row's number as it existed at construction | `values` |
| Follow edits to the particular dictionary originally supplied | `objects` |
| Follow whichever dictionary currently occupies a particular list position | None of the three |

`late` does not implement the distinct per-row behavior of either of the first two contracts: both callbacks follow D2. An interface that intentionally follows list positions would instead retain access to the source list and each intended index, then retrieve the object at that index when invoked. Such an interface would also need defined behavior for later reordering, deletion, or an index becoming invalid. [A17-INTENT]

The reviewers' callback predictions fail for specific reasons:

- **All second-row callbacks return 20:** none of these callbacks retrieves `rows[1]` when called. Replacement therefore does not redirect them to D3.
- **A default argument deeply snapshots a dictionary:** a default saves a reference to its evaluated value. In `objects`, that value is the original mutable dictionary, so later edits remain visible.
- **Every comprehension iteration creates an independent captured loop variable:** the `late` lambdas share one binding within that comprehension. Each function object is distinct; the captured binding is shared.

Capturing 1 or 2 works for the historical contract here because integers are immutable: later dictionary assignments do not change those integer values. If `row["n"]` instead referred to a mutable nested object, saving that value as a default would retain its reference and expose later mutations. A historical representation for arbitrary nested data therefore needs an explicit decision about which objects and relationships to preserve; using defaults is not a general deep-copy operation.

## Why both buffer lists change

Two separate operations preserve sharing:

1. **List multiplication:** `[[]] * 2` creates one inner list and places two references to it in `buckets`. Appending `"x"` through `buckets[0]` changes the object also reached through `buckets[1]`.
2. **Shallow outer copying:** `buckets.copy()` creates another outer list but copies those same inner references. All four slots across the two outer lists therefore reach the same inner list. Appending `"y"` through `outer_copy[1]` changes that shared object too. [A17-CODE]

The buffer reviewer's observation that the outer identity changes is correct; the claim that this makes the inner lists independent is not. Independent row buffers require a distinct mutable buffer object for each row. Whether another outer collection should share those row buffers is a separate design choice. Changing only the outer list cannot provide the required per-row independence.
