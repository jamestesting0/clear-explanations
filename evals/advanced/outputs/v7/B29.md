**The outbox made order creation and event creation atomic locally; it did not make remote reservation creation atomic with the sender's `sent` flag.** A lost response left the sender needing to retry, and a new idempotency key made that retry look like a new operation to the receiver. The two reservations are consistent with the stated design. [B29-S1, B29-S2, B29-S3]

## Which transaction covers which state

The first local database transaction commits the order and its outbox event together. That prevents a committed order from lacking its corresponding committed event. The external API's database is outside this transaction. [B29-S1]

Later, the dispatcher makes a network request. Only after receiving success does it use a second local transaction to mark the event sent. Between remote execution and that local commit, the remote reservation can exist while the outbox row still says unsent. Two relevant failure windows are:

- The receiver creates the reservation, but the response is lost or the dispatcher crashes before receiving it.
- The dispatcher receives success, but crashes before the `sent` update commits.

Both leave work eligible for retry despite an existing remote effect. A missing response can also mean the request never executed; the local unsent flag alone cannot distinguish these outcomes. [B29-S1]

## What happened to E8

| Step | Sender state | Receiver effect |
| --- | --- | --- |
| 09:00 local commit | O8 and E8 exist; E8 unsent | No reservation established by this local commit |
| First request, key A1 | Response lost; E8 remains unsent | R101 created |
| 09:01 retry, key A2 | Success received | R102 created |
| Second local transaction | E8 marked sent | Both reservations remain |

This trace follows the incident logs. One order row and one event row count durable local records, not network attempts or remote effects. [B29-S3]

The receiver deduplicates by `Idempotency-Key` within its account and route scope. It does not independently deduplicate the `event_id` in the body. Because A1 and A2 differ, the receiver's same-key protection does not connect the attempts, even though their payloads match. The sender has supplied a delivery-attempt identity where it needs a stable operation identity. [B29-S2, B29-S3]

## Compare the proposed changes

**Marking sent before sending exchanges the retry risk for a loss risk.** On an initial attempt, the process could commit `sent`, crash before transmitting, and leave an order with no reservation while the normal unsent-row dispatcher skips the event. Moving the local update cannot make it atomic with the remote effect. [B29-S1, B29-S4]

**A stable key derived from `event_id` addresses this incident's duplicate-creation mechanism.** If both E8 attempts had used the same key, account, route, and payload, the retry one minute later would have returned R101's original result without creating R102 under the supplied contract. The dispatcher could then mark E8 sent. A crash before that update would remain recoverable through another same-key retry within retention. [B29-S2, B29-S3, B29-S4]

Payload stability matters: during retention, reusing the key with a different payload returns 409. It is not permission to change the intended operation while preserving its identity. [B29-S2]

The bounded guarantee is precise: **retries with the same key, scope, and payload within the receiver's 24-hour retention do not create another reservation and return the original result.** That protects remote effects within the stated window. It does not mean there was only one delivery attempt, and eventual completion still depends on successful communication and retry processing. [B29-S1, B29-S2]

## Older replays need a further rule

A replay 36 hours later falls outside that protection. The receiver may have forgotten the key, so even the same stable key may create a new reservation. It is not certain to duplicate, but uniqueness is no longer guaranteed by this contract. [B29-S2, B29-S4]

A stronger design could enforce permanent uniqueness for the logical reservation identity at the receiver, with the uniqueness record and reservation creation committed together in the receiver's database. Alternatively, the system could bound every automatic and manual replay to a matching retention period, and block older ambiguous events pending an authoritative reconciliation process. Merely extending local bookkeeping or blindly replaying an expired key does not resolve an unknown remote outcome.

Those are additional design requirements, not capabilities established by the packet. The existing R101 and R102 also require separate reconciliation; changing future keys does not remove an already-created duplicate. The overview's “exactly-once” phrase obscures these distinctions between event creation, delivery attempts, and remote effects. [B29-S3, B29-S4]
