The checklist fails first at the unique index: accounts 1 and 2 both normalize to `li@ex.test`. Beyond that collision, the plan changes write requirements and column meanings while binaries that depend on the old contract are still running. **A completed backfill is a statement about rows processed so far; it is not a rule governing future writes.** [A16-OLD, A16-DATABASE]

## What fails, and when

| Step | Result under the supplied conditions |
| --- | --- |
| Add nullable `email_norm` | Compatible expansion: version 1 can keep omitting it. |
| Backfill before adding uniqueness | Can populate the column, but creates two `li@ex.test` values. The backfill itself does not resolve ownership. |
| Create the unique index | Fails on those duplicate non-null values. Creating it before the backfill would instead make the conflicting backfill write fail. |
| Deploy version 2 to half the fleet | Requires compatibility safeguards: fallback lookup can find multiple accounts, and version 1 can continue creating unnormalized rows. |
| Enforce `NOT NULL` | Fails validation if nulls remain; if installed successfully, it rejects subsequent version 1 inserts because version 1 supplies no value. |
| Remove or replace the original representation | Breaks compatibility unless every active and permitted rollback version supports the resulting schema and meaning. Version 2 itself still references `email_norm`. |

These consequences follow from the supplied write behavior and constraints, rather than from the order in which the deployment checklist happens to name them. [A16-OLD, A16-NEW, A16-DATABASE, A16-PLAN]

Version 1 can also leave a **stale non-null value** if it changes an existing row's `email` without changing `email_norm`. Checking for nulls alone therefore cannot establish consistency. Version 2's transaction keeps its own successful writes together, but cannot make version 1 maintain that relationship. [A16-OLD, A16-NEW]

Keeping a column named `email` preserves a piece of SQL syntax, not the old behavior. Version 1 depends on the original address values, case-sensitive identity and uniqueness, and the ability to write without calculating a second value. Replacing that column with normalized data changes those assumptions. An old binary may still issue a syntactically valid statement while finding different accounts, failing a newly imposed constraint, or writing an address that has not been normalized. The compatibility assessment must cover those behaviors, as well as column names. [A16-OLD, A16-PLAN]

## Why the race passes the index

The later-stage race leaves:

| Account | `email` | `email_norm` |
| --- | --- | --- |
| 4 | `PAT@EX.test` | null |
| 5 | `Pat@ex.test` | `pat@ex.test` |

The raw addresses differ under case-sensitive comparison. The normalized index sees one null, which it permits, and one non-null `pat@ex.test`, which is unique among indexed non-null values. Both inserts therefore satisfy the stated constraints. [A16-RACE, A16-DATABASE]

A fallback that computes lowercase for the null row makes account 4 searchable as `pat@ex.test`; it does not reserve that identity or exclude account 5. A lookup that considers both the stored and fallback values finds two candidates. A lookup that returns a stored match before checking fallback candidates merely hides the collision. Neither is a safe ownership decision. Later backfilling account 4 to `pat@ex.test` conflicts with account 5's indexed value. [A16-NEW, A16-RACE]

Thus the nullable index enforces uniqueness **among populated normalized values**, not across all account identities. Fallback is read behavior, not a database constraint or a write-coordination mechanism.

## A staged migration

1. **Expand while retaining the rollback contract.** Add the nullable column and preserve the original column, its data, and its existing constraints. Deploy compatible code that writes both representations together. Keep the new case-insensitive login behavior disabled until it can handle the population safely; a version 2 path that assumes exactly one normalized match is unsafe on the initial data. During this stage, an unmodified version 1 rollback must still be able to read and write. [A16-OLD, A16-NEW]

2. **Inventory and reconcile identities.** Group accounts by `lowercase(email)` across all rows, including rows whose normalized column is null or stale. Identify the existing collision between accounts 1 and 2 and any additional collisions created during deployment. Backfill resumably and check that populated values equal `lowercase(email)`. Treat each pass as provisional while old writers remain active. [A16-OLD, A16-DATABASE]

3. **Establish an enforceable writer boundary.** A straightforward transition is to retire or disable every version 1 write path, briefly fence account writes if necessary, and perform final reconciliation and backfill before reopening writes under the new rules. Include background jobs, imports, and queued work. If version 1 must continue writing during enforcement, an additional mandatory compatibility mechanism must normalize and enforce uniqueness for those writes too—for example, a database rule or a write service that old writes cannot bypass. None exists in this packet. A nullable index plus application fallback is not that mechanism. [A16-DATABASE]

4. **Verify and enforce the new identity rule.** With the writer boundary holding, validate that every row has the correct normalized value and that normalized identities are unique. Create or validate the unique index and enforce `NOT NULL`; enable case-insensitive login after the ownership resolutions and constraints are in place. Ensure later writes preserve `email_norm = lowercase(email)` and handle uniqueness conflicts without attaching a request to the wrong account. If the nullable index was created earlier, its presence does not eliminate this final validation.

5. **Contract after compatibility has been demonstrated.** Retain the original representation while any active or supported rollback binary needs it. Deploy readers and writers compatible with the intended final schema, drain incompatible versions, and then remove obsolete columns. Renaming `email_norm` also requires a transition for version 2, which references that name. Decide separately whether the product still needs original address casing for display or other behavior. [A16-NEW, A16-PLAN]

The first stage can remain reversible without globally enforcing the new identity rule. Once `NOT NULL` or incompatible column changes are introduced, rollback to unrestricted, unmodified version 1 requires a compatibility mechanism or an explicit end to that rollback window.

## Ownership decisions and release evidence

The product must decide how to resolve accounts that normalize to the same address. Proving common ownership may justify an approved merge with purchase histories and references preserved. Different owners may need separately verified login identifiers or a policy for disambiguation. Choosing the smallest ID, deleting a duplicate, or selecting the first fallback match cannot establish who owns either account. The race supplies no basis for merging accounts 4 and 5. [A16-OLD, A16-NEW, A16-RACE]

Evidence for `NOT NULL` should include a final scan showing zero nulls, zero normalization mismatches, and zero unresolved normalized duplicates, **plus evidence that all subsequent writer paths maintain those properties**. Exercise inserts, email changes, and concurrent case-variant attempts through each permitted write path; a successful backfill alone is insufficient.

Evidence for contraction must additionally show that deployed applications, jobs, and supported rollback versions no longer require the original column or the names being removed. Compatibility tests must check account lookup and ownership behavior as well as successful SQL execution. Until that evidence exists, preserving both representations is part of preserving the migration's rollback promise.
