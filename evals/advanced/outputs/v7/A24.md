## Complete latency in the microbenchmark

The CPU and database stages are serial, so their times add:

| Quantity | Calculation | Result |
| --- | --- | ---: |
| Original complete latency | `8 + 12` | 20 ms |
| Optimized CPU time | `8 / 4` | 2 ms |
| Optimized complete latency | `2 + 12` | 14 ms |
| Complete-latency speedup | `20 / 14` | About 1.43× |
| Limiting latency as CPU time approaches zero | `0 + 12` | 12 ms |
| Limiting complete-latency speedup | `20 / 12` | About 1.67× |

The unchanged database stage prevents the complete path from achieving a fourfold speedup, even if CPU work became arbitrarily fast. These limits apply to this isolated path under its stated assumptions; they are not a model for every request in the separate replay. [A24-MICRO]

## Mean user wait and the 95th percentile

The requested mean gives each of the 1,000 requests equal weight, so endpoint means receive weights of 90% and 10%:

| Endpoint | Requests | Before per request | After per request | Before: sum of response times | After: sum of response times |
| --- | ---: | ---: | ---: | ---: | ---: |
| Fast | 900 | 10 ms | 8 ms | 9,000 ms | 7,200 ms |
| Slow | 100 | 100 ms | 150 ms | 10,000 ms | 15,000 ms |
| **Total** | **1,000** | | | **19,000 ms** | **22,200 ms** |

Therefore:

- **Before mean:** `19,000 / 1,000 = 19 ms`.
- **After mean:** `22,200 / 1,000 = 22.2 ms`.
- **Change:** `22.2 − 19 = 3.2 ms` more per request.
- **Relative change:** `3.2 / 19 × 100 ≈ 16.84%` increase in mean wait.

An independent way to see the increase is that the 900 fast requests save `900 × 2 = 1,800 ms`, while the 100 slow requests add `100 × 50 = 5,000 ms`. The net addition is 3,200 ms, or 3.2 ms per request. That is why 90% of requests becoming faster does not guarantee a lower mean: the sizes of the improvements and regressions matter. These sums are accumulated user response times, not the wall-clock duration of a concurrent replay. [A24-WORKLOAD]

For the specified 95th percentile, the first 900 sorted values belong to the fast endpoint and positions 901–1,000 belong to the slow endpoint. The 950th value is consequently **100 ms before and 150 ms after**, a 50% increase. [A24-WORKLOAD]

## Why the dashboard averages mislead

### Averaging individual speedup ratios

Fast requests have speedup `10 / 8 = 1.25`; slow requests have speedup `100 / 150 = 2/3`. The dashboard reports:

`0.9 × 1.25 + 0.1 × (2/3) = 1.191666… ≈ 1.192×`.

That is the arithmetic mean of request-level speedup factors. Each factor is normalized by that request's new response time, so it does not preserve how many milliseconds each request contributes to total wait. Averaging ratios is not the same operation as dividing the corresponding averages.

For the product owner's mean-wait question, the relevant old-to-new ratio is:

`19 / 22.2 ≈ 0.856×`.

It is below one because the new mean is worse. The dashboard's average factor answers a different mathematical question and cannot substantiate an improvement in aggregate latency. [Calculation from A24-WORKLOAD; A24-DASHBOARD]

### Giving each endpoint equal weight

The unweighted endpoint means are:

- Before: `(10 + 100) / 2 = 55 ms`.
- After: `(8 + 150) / 2 = 79 ms`.

These describe the mean of two endpoint means, equivalent here to a hypothetical 50/50 request mix. They do not describe the observed 90/10 mix. To measure the average wait of a request in this replay, use the request-count weights and obtain 19 and 22.2 ms. [A24-WORKLOAD; A24-DASHBOARD]

## What the operating interval establishes

Using the supplied stable-interval identity, convert the mean time to seconds:

`L = λW = 200 requests/second × 0.0222 seconds = 4.44 requests`.

Thus **4.44 requests are in the system on average**, including requests executing or waiting. An average population can be fractional even though each instantaneous count is an integer. This is not a count of CPU cores or busy database connections. [A24-OPERATIONS]

The deployment sustained 200 completions per second during that interval, with arrivals matching completions and no net buildup. It might have spare capacity or be near a limiting resource; the packet does not distinguish those possibilities. Stable operation at one offered load is not a saturation experiment, and no before-deployment throughput comparison is supplied.

For a **single sequential client with one outstanding request and no think time**, throughput is the inverse of its mean response time. If that client experienced the same 22.2 ms mean, it would complete approximately `1 / 0.0222 = 45.05` requests per second. That conditional calculation is not the capacity of a deployment serving concurrent clients. Nor is the same latency guaranteed at different concurrency, because the supplied complete response times include waiting. The observed 200 completions per second is compatible with several requests being in flight together. [A24-OPERATIONS]

## Evidence needed for the throughput claim

Compare the old and optimized deployments under the same hardware, configuration, endpoint mix, and payloads. Increase offered load or concurrency through several sustained operating levels, recording completed requests per second, errors, mean and 95th-percentile latency, and queue buildup. Define acceptable latency and error limits so that “capacity” means a sustainable rate under an explicit service requirement.

Measure CPU demand and utilization, database demand and connection limits, and other resource constraints to identify what limits completion rate and whether that limit changes after optimization. Repeated steady measurements before and after would establish a throughput ratio; the isolated CPU-stage improvement cannot do so by itself.

The real fast-endpoint benefit should remain visible: its response time falls from 10 to 8 ms, a **20% reduction** in this replay. That benefit coexists with a larger slow-endpoint regression, worse mean and 95th-percentile user wait, and an as-yet unmeasured change in maximum service capacity. [A24-WORKLOAD]
