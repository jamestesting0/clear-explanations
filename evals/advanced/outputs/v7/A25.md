**Caching a coroutine object fails on reuse; caching a Task enables sharing but also shares that Task's outcome, including cancellation.** Shielding each wait protects the shared fetch from cancellation propagated by a reader, but expiry, eviction, and ownership of background work still need explicit rules. There are three different things a cache might retain:

| Cached object | Meaning | Consequence of another await or lookup |
| --- | --- | --- |
| Coroutine object returned by `raw("x")` | One invocation whose execution can be awaited | Once consumed, it cannot be awaited again |
| Task created with `create_task(fetch())` | One scheduled execution and its eventual outcome | Multiple readers can await it; they share its result, exception, or cancellation |
| Successful result value, such as `"loaded"` | The data produced by execution | Readers can reuse the value without rerunning or awaiting the original coroutine |

The `lru_cache` wrapper caches what calling the async function returns: a coroutine object. It does not await that object and cache its eventual string. The first await produces `loaded:x`; the second retrieves the same already-consumed object and raises `RuntimeError`. [A25-CODE]

## Why the Task runs differ

Both readers obtain the same cached Task. In this fixture, the check and insertion contain no `await`, and one event loop executes them without another reader interleaving in between. Therefore only one fetch is created in each independent `shared_task` experiment. The two sleeps establish that the readers and fetch have started; they implement no expiry. [A25-CODE]

**Without shielding:** A is directly awaiting the shared Task. Cancelling A propagates cancellation to that Task. The fetch leaves `gate.wait()` through cancellation and runs its `finally` block. Both readers then receive `CancelledError`, which their handlers record. Although A and B are separate reader Tasks, their waits depend on the same cancelled fetch. Setting the gate afterward does not restart it. The cache retains the cancelled Task, so the later lookup raises `CancelledError` again. [A25-CODE]

**With shielding:** A awaits a protective wrapper around the same fetch Task. Cancelling A cancels its wait and A records `A:cancelled`; cancellation does not propagate through that wrapper to the fetch. B remains waiting. Opening the gate lets the fetch finish, run `finally`, and deliver `loaded` to B. The cached Task is successfully completed, so the later await also yields `loaded`. Shielding creates neither a new fetch nor a new result. [A25-CODE]

This boundary works in one direction: a reader's cancellation need not cancel the fetch. It does not make the fetch uncancellable. A cache owner can still call `task.cancel()` during eviction or shutdown; cancellation of the underlying Task also reaches shielded waiters. Nor does shielding prevent the caller itself from receiving cancellation: A's request can end while useful shared work continues.

## A concrete lifecycle design

Use a cache owned by one event loop, with separate maps for in-flight Tasks and successful values:

1. **Look up a successful value and check its expiry.** Store `(value, expires_at)` using a monotonic clock. Define the TTL to start when loading succeeds. An entry is usable while the current time is strictly before `expires_at`; otherwise remove it and obtain a fresh fetch.
2. **Share an in-flight fetch.** If no unexpired value exists, reuse the current Task for that key or create and register one without an intervening `await`. Keep a strong reference to each background Task. Each reader awaits `asyncio.shield(task)`.
3. **Handle completion centrally.** On success, publish the value with its expiry and remove the in-flight entry. On failure or cancellation, remove the in-flight entry without storing a successful value, allowing a later request to retry. A cancelled reader must not automatically evict or cancel a fetch that other readers can still use.
4. **Guard every completion-driven cache mutation.** Before removing an entry or publishing a result, confirm that this completion still belongs to the key's current Task or generation. Explicit invalidation should change that ownership so an old completion cannot repopulate an invalidated value.
5. **Choose who owns cancellation.** One concrete policy is to let a fetch finish even if all readers disappear, so its successful value can serve future readers. The cache owner cancels work on explicit invalidation or shutdown and awaits its termination. If the desired policy instead cancels when the last consumer leaves, implement explicit consumer counting and coordinated cancellation; do not let the last unshielded await accidentally decide it.

The essential deletion guard is:

```python
if inflight.get(key) is task:
    del inflight[key]
```

Suppose an old Task finishes after a replacement has already been installed under the same key. An unconditional `del inflight[key]` would delete the replacement, allowing another reader to start duplicate work. Checking object identity prevents that stale callback from deleting someone else's entry. Publishing a successful value needs the corresponding ownership check too.

Completion handling must also observe failures independently of whether readers remain. Check `task.cancelled()` first; for a non-cancelled Task, retrieve its exception and record a failure as appropriate, or retrieve its successful result. This exception handling still matters when the Task is no longer the current cache entry. Shielding does not automatically log exceptions from abandoned work.

The fixture directly demonstrates coroutine reuse failure, propagation of reader cancellation into an unshielded shared Task, retention of that cancelled Task, and successful sharing and later reuse with shielding. It does not exercise transient fetch exceptions, TTL expiry, replacement races, explicit eviction, shutdown, or the disappearance of every consumer. Those are production lifecycle requirements from [A25-INTENT], not guarantees established by the successful shielded run. A dictionary owned by one process also provides no coordination or shared storage across processes.
