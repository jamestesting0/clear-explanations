**The specified merge leaves apple present because tag `a1` was never removed.** The separate cleanup experiment also makes apple reappear, but for a different reason: deleting the removal evidence lets an old, already-removed tag become visible again. [A28-PARTITION] [A28-CLEANUP]

## Derive the partitioned and merged states

An item is visible when at least one of its entries in `Adds` has a tag absent from `Removed`. Removing an item records only the add tags that the removing replica currently knows. [A28-STATE]

| State after the listed actions | `Adds` | `Removed` | Visible apple tags |
| --- | --- | --- | --- |
| R1 | `{(apple,a0), (apple,a1)}` | `{a0}` | `{a1}` |
| R2 | `{(apple,a0), (apple,b1)}` | `{a0,b1}` | `{}` |
| Merged | `{(apple,a0), (apple,a1), (apple,b1)}` | `{a0,b1}` | `{a1}` |

R1's remove records `a0`; its subsequent user add creates `a1`. R2's user add creates `b1`; its subsequent remove records both `a0` and `b1`, because those are the apple tags it knows. R2 has not seen `a1`, so its remove cannot include that tag. Union combines both histories while retaining `a1` as visible. [A28-PARTITION] [A28-MERGE]

Duplicate or reordered state messages do not change the eventual merged result. Set union has three relevant properties: repeating the same input adds nothing, exchanging input order changes nothing, and grouping several merges differently changes nothing. Thus, once both replicas have received the same states, their sets and visible membership agree. This does not require wall-clock ordering. [A28-STATE]

## What the review claims miss

- **“R2's last remove wins globally.”** It removes the tags R2 observed, including its own earlier `b1`. It cannot remove the unseen concurrent add `a1`. Being R2's last local button press does not establish a global ordering rule. The chosen rule lets an add survive a remove that did not observe that add.
- **“Two add tags mean quantity two.”** Tags identify additions for conflict handling. The UI asks whether any surviving tag exists, yielding a presence/absence answer. Neither the total number of historical tags nor the number of surviving tags is a numeric quantity under this contract.
- **“A delivery retry creates a new tag.”** A fresh user add creates a fresh globally unique tag. Redelivery of that same add preserves its tag. Creating a tag on every delivery would turn retransmission into a new user operation and could defeat a removal that recorded only the original tag. [A28-STATE] [A28-MERGE]

## Why the cleanup resurrects an old item

In the separate experiment, R2 initially has:

```text
Adds   = {(apple,a0), (apple,b1)}
Removed = {a0,b1}
visible = absent
```

After deleting both add entries and both removal markers, R2 has empty sets. Merging R3's offline state then produces:

```text
Adds   = {} ∪ {(apple,a0)} = {(apple,a0)}
Removed = {} ∪ {}          = {}
visible = present
```

No new user add occurred. The old `a0` returned without the evidence that it had been removed. Keeping a removal marker for `a0` would suppress that old tag even if its matching add entry had been discarded. The problem is therefore unsafe reclamation of removal evidence, not the intended survival of a previously unseen fresh add. [A28-CLEANUP]

## What safe reclamation would require

The two-set protocol alone supplies no safe cleanup condition. A separate protocol must establish that discarded tags cannot later be reintroduced by a valid replica state or old message without still being recognized as removed. Possible designs need the following elements:

- **Track which replicas must acknowledge removal.** A removal is causally stable when every replica still permitted to contribute state has durably incorporated the relevant removal, and the protocol has dealt with older contributions that could restore the tag. Per-replica sequence tracking can summarize how far each replica has progressed.
- **Account for offline replicas.** R3 has not acknowledged the removal, so it blocks reclamation under an all-member acknowledgement policy. Alternatively, explicitly retire R3's old replica identity. On return, it must obtain a current snapshot and rejoin under a new identity or epoch rather than merge its old state as authoritative.
- **Reject obsolete messages and states.** An epoch is a protocol generation attached to replicas and messages. A controlled epoch change can make old-generation states inadmissible. Another design can retain compact progress metadata that rejects tags already covered by a stable removal. Either way, a delayed pre-removal message must not become admissible merely because individual markers were deleted.

Acknowledgements alone are insufficient if a previously queued state can still reintroduce `a0` after all markers have been reclaimed. The design must also prevent that replay or retain enough compact information to suppress it. Simply waiting a while does not establish this condition. In the supplied experiment, there is no acknowledgement, retirement, or old-message rejection mechanism, so the proposed deletion lacks the required protection. [A28-CLEANUP]

## The contract's limits

Union provides convergence when replicas receive the same information **while preserving the defined add and removal history**. The observed-remove rule specifies which conflicting operations affect membership; it does not promise a globally latest wall-clock remove, numeric item quantities, or an inventory reservation that prevents competing users from claiming the same stock. Those require additional semantics and, where necessary, coordination.

It also does not promise immediate agreement while disconnected: after the partitioned operations, R1 shows apple and R2 does not. Their eventual agreement after merge is exactly the guarantee demonstrated here. [A28-PARTITION] [A28-STATE]
