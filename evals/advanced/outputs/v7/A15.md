**The deployed SDK uses milliseconds in `timeoutMs`; legacy `timeout` is ignored because `legacyMode=false`.** Resolution selects call `timeoutMs`, then constructor `timeoutMs`, skipping absent/null values; otherwise it converts the environment value, or defaults to 1500 ms. [A15-MIGRATION] [A15-IMPLEMENTATION]

Applying those rules to [A15-REQUESTS]:

| Request | Client wait timer | Transmitted `x-deadline-ms` | Server computation budget |
| --- | ---: | ---: | ---: |
| R1 | 6000 ms | 6000 | 5000 ms |
| R2 | 2500 ms | 2500 | 2500 ms |
| R3 | None: validation fails | No request sent | Not applicable |

R1's call value overrides the constructor and environment. The server applies `min(6000,5000)`; this cap does not shorten the client's timer or change its transmitted header. R2's call `timeout:1` is ignored, leaving constructor `timeoutMs:2500` effective. [A15-MIGRATION] [A15-IMPLEMENTATION] [A15-SERVER]

For R3, `timeout:30` is ignored and neither options object supplies `timeoutMs`. JavaScript `Number("2s")` produces `NaN`, which fails validation before networking. It does not fall back to 1500 ms. The server's absent-header default of 1000 ms is irrelevant because no request reaches the server. [A15-IMPLEMENTATION] [A15-SERVER]

**R1's 5030 ms trace is consistent with the limits.** The 5000 ms server budget starts when computation begins; transit and response delivery add wall time. Receiving its deadline error after 5030 ms of client waiting is compatible with that computation limit and occurs before the client's 6000 ms timer. The trace does not isolate the timing components.
