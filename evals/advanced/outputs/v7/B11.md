**The customer’s experience of a note “coming back” is consistent with the trace, but the recorded mobile update did not restore the server note.** The app displayed a local draft and later exported its title. The update was rejected, and the subsequent direct server read found the deletion marker still at epoch 5. [B11-S3–S4]

## Two meanings of “resurrection”

A note can reappear **visually** because an app retains and displays local content. Canonical restoration is a different claim: the primary server has accepted content as the current note again.

The interface explicitly permits an offline draft to remain visible with “pending sync.” After a conflict response, it preserves that draft for copying in a conflict tray, separate from the ordinary synchronized note list. Neither behavior means the draft was committed to the server. [B11-S3]

## Why this mobile update returns 409

An **epoch** is a server-controlled generation of the note. Deletion advances that generation and leaves a **tombstone**, a marker recording the deletion after current content is removed. A revision orders accepted updates only within one epoch. [B11-S1]

The incident follows that distinction:

| Time | Relevant state or event | Consequence |
| --- | --- | --- |
| 09:00 | Phone has epoch 4, revision 8 | It has the earlier synchronized copy |
| 09:10 | Browser deletion creates tombstone at epoch 5 | The server advances beyond epoch 4 |
| 09:30 | Phone displays its epoch-4 draft, local revision 9 | Local content is visible as “pending sync” |
| 09:40 | Phone submits epoch 4; stored epoch is 5 | Handler returns 409 |
| 09:41 | Local CSV includes the draft’s title | Export exposes retained local content |
| 09:42 | Direct GET returns 404, tombstone epoch 5 | The primary note is deleted at that observation |

These are the supplied trace events, interpreted using the current contract and interface specification. [B11-S1–S4]

In the handler, the first condition compares the requested epoch with the stored epoch. Because **4 differs from 5**, it returns **409 immediately**. It does not reach the tombstone check that would return 410, and it does not reach the content write. A request matching epoch 5 would reach the tombstone check and be rejected with 410 instead. [B11-S2]

The draft’s local revision 9 cannot outrank epoch 5. The accepted-update path also assigns the next revision from the stored revision; it does not use a large client revision to override the generation check. The lock covers the read and write and is shared with deletion, preventing those protected operations from interleaving between validation and writing. [B11-S1–S2]

The old timestamp sketch does not govern this deployment. The current contract and deployed handler compare epochs, and neither makes a newer phone timestamp an override for deletion. An earlier search-result position is not evidence that the sketch was implemented. [B11-S2]

## Why the CSV does not prove restoration

The exporter reads **local app state**, including conflict-tray items, and provides no status column. Under the specification, the 409 leaves the rejected draft in that tray, so its title can appear in the CSV without an accepted server write. The CSV does not distinguish retained work from synchronized notes. [B11-S3]

This makes the customer’s confusion understandable. “Pending sync” can sound like eventual acceptance is merely delayed, and an ordinary-looking export can reinforce that impression. But the direct GET supplies the relevant server observation: at 09:42, note N has no current content and retains tombstone epoch 5. [B11-S4]

## The scope of the conclusion and a product fix

The evidence establishes the rejection of this mobile update and the later deleted server state. It does not establish a universal guarantee across all administrative imports, backups, other notes or unobserved write paths. Missing traces of those operations do not prove they never occurred.

A broader guarantee would require reviewing every route that can write or restore content: authorization for explicit restore, epoch handling in imports and backup recovery, tombstone preservation, and whether those writers enforce equivalent atomic checks. The contract itself permits explicit restoration, so the useful guarantee would be prevention of restoration **without the required authorized operation**, rather than permanent impossibility of recreating a note. [B11-S1, B11-S4]

A product clarification could label retained content as a **local draft awaiting server acceptance**. After a conflict and a server check confirming deletion, the app could say: “This note was deleted on the server. Your draft is retained so you can copy it.” The exporter could default to synchronized notes, with an explicit option to include retained drafts and a status column distinguishing them. These would be proposed changes; the supplied interface describes the current exporter as still including both kinds of item. [B11-S3]
