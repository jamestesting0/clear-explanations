The required charge is **1.01**, allocated as **34 cents to line 10, 34 cents to line 20, and 33 cents to line 30**. Whole-line refunds must return those stored amounts. Decimal arithmetic can preserve the inputs accurately, but the rounding, allocation, and refund policies must still be implemented explicitly. [A21-POLICY]

## What the experiments print

| Printed label | Printed value | Explanation |
| --- | ---: | --- |
| `line-rounded` | `1.02` | Each exact `0.335` rounds half-up to `0.34`; three such amounts sum to `1.02`. |
| `invoice-rounded` | `1.01` | The exact raw sum is `1.005`, which rounds half-up once to `1.01`. |
| `float-constructor` | `1.00` | The binary float passed into `Decimal` is slightly below exact `1.005`. |
| `text-constructor` | `1.01` | The text constructs exact decimal `1.005`, an exact halfway case. |
| `half-up` | `0.33` | Exact `0.325` is halfway between `0.32` and `0.33`; half-up chooses `0.33`. |
| `half-even` | `0.32` | At the same tie, half-even chooses the result whose last retained digit is even: `2`. |
| `binary-round` | `2.67` | The binary float for `2.675` is slightly below the halfway point between `2.67` and `2.68`. |

These are the results of the supplied expressions. [A21-CODE]

In `Decimal(1.005)`, Python first creates a binary floating-point number. Its exact value begins `1.004999999999999893…`; `Decimal` then preserves that existing value. It cannot recover an intended decimal value that was already changed before the conversion. In `Decimal("1.005")`, the constructor receives decimal text directly and creates exactly `1.005`.

Likewise, the float written `2.675` is approximately `2.674999999999999822…`. Its rounding result does not demonstrate that ties always go downward: this input is below the relevant decimal tie. Python's `round` uses ties-to-even for exact halfway cases. Half-up and half-even are different policies, as the exact decimal `0.325` example demonstrates. For positive ties, half-up chooses the larger result; half-even chooses the even final retained digit.

Displaying two decimal places does not remove these distinctions. A tiny representation difference can move an input across a rounding boundary and change the displayed amount by one cent.

## Where rounding and allocation belong

Under the supplied contract, retain exact raw amounts until the invoice total is calculated:

`0.335 + 0.335 + 0.335 = 1.005 → 1.01 = 101 cents`.

Each raw line is `33.5` cents. Taking each floor gives `33 + 33 + 33 = 99` cents, leaving **2 cents** to allocate. All fractional remainders are `0.5`, so ascending line identifier breaks the tie. [A21-POLICY; A21-INVOICE]

| Line identifier | Raw cents | Floor in cents | Fractional remainder | Extra cent | Stored cents |
| --- | ---: | ---: | ---: | ---: | ---: |
| 10 | 33.5 | 33 | 0.5 | 1 | 34 |
| 20 | 33.5 | 33 | 0.5 | 1 | 34 |
| 30 | 33.5 | 33 | 0.5 | 0 | 33 |
| **Total** | **100.5** | **99** | | **2** | **101** |

The old implementation disagrees even with exact decimal arithmetic because **rounding each component and rounding their sum are different operations**. It commits three upward half-cent adjustments, producing `1.02`. The invoice policy rounds the combined `1.005` once, producing `1.01`.

Both policies cannot hold for this invoice: three independently half-up-rounded lines must each be 34 cents and therefore total 102 cents, while the required invoice charge is 101 cents. No choice of numeric representation can make those two totals equal. Allocation resolves the conflict by making stored line amounts shares of the invoice charge, rather than independently rounded raw amounts.

## Why the proposed repairs fail

The **independently recalculated refund** still returns 34 cents for every line. Refunding all three lines would return 102 cents against a 101-cent charge. It would also overrefund line 30 by one cent relative to that line's original allocation. [A21-INVOICE]

The **display-only repair** stores 102 cents while displaying 101 cents. Because reconciliation and refunds use stored values, changing the receipt string cannot correct their disagreement. [A21-REVIEW]

Instead, persist the original 101-cent charge and the allocation keyed by line identifier. Use those integer-cent values for both the receipt and whole-line refunds, and record which lines have already been refunded so a repeated request cannot refund the same line twice. For example:

| Refund action | Refund in cents | Charge remaining in cents |
| --- | ---: | ---: |
| Refund line 30 | 33 | 68 |
| Refund line 10 | 34 | 34 |
| Refund line 20 | 34 | 0 |

For any subset of refunded lines, subtracting their stored allocations from 101 gives exactly the sum of the unrefunded lines' allocations. The order does not matter. Do not rerun the allocation among remaining lines or round the original raw amount anew when processing a refund.

Implementation therefore needs exact decimal-text parsing, sufficient decimal precision for intermediate calculations, one explicit half-up invoice rounding step, deterministic allocation, and stored integer-cent refund entitlements.

## What later extensions must specify

**Negative amounts:** define how credits participate in allocation, whether positive and negative lines share one pool, how floors and fractional remainders are interpreted for negative values, and whether reversing signs must reverse the allocation. Mathematical floor differs from truncation toward zero for negative numbers. `ROUND_HALF_UP` rounds exact negative ties away from zero, but that fact alone does not define a signed allocation policy.

**Partial-line refunds:** define the quantity or proportion being refunded, when and how fractional cents are rounded, and which partial refund receives any residual cent. A policy could track cumulative entitlement and give the final refund the remaining allocated cents, but the supplied contract does not choose such a rule. Whatever extension is selected must make complete return of a line refund exactly its original stored allocation, without creating extra cents through repeated rounding. [A21-POLICY]
