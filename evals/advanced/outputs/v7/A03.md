`copied` freezes which element references occupy its list positions; it does not freeze the `StringBuilder` objects those references point to. `wrapped` additionally remains tied to the source list's contents through `window`. Neither therefore satisfies the complete snapshot contract. Returning an unmodifiable `List<String>` built from each builder's current text does satisfy it for this example. [A03-CODE, A03-API]

## The four objects share different things

Immediately after construction, the selected elements are the builders containing `B` and `C`.

| Name | Relationship to the source | What it initially refers to |
| --- | --- | --- |
| `base` | Owns the mutable list of four element references | Builders for `A`, `B`, `C`, `D` |
| `window` | A view of positions 1 and 2 in `base` | The builders currently occupying those positions |
| `copied` | An independent, unmodifiable sequence of selected references | The original `B` and `C` builders |
| `wrapped` | An unmodifiable interface delegating to `window` | Whatever `window` currently exposes |

“Independent” here concerns list membership and order. It does not mean the builders were copied. Both `copied` and `wrapped` initially expose the very same `C` builder as `base`. [A03-CODE]

### Replacing B changes a list position

```java
window.set(0, new StringBuilder("B2"));
```

Position 0 of `window` corresponds to position 1 of `base`. This operation replaces the reference in that position with a reference to a new builder. It does not edit the original `B` builder.

Consequently, `base`, `window`, and `wrapped` now expose `B2`. `copied` still holds the reference to the original builder containing `B`. This replacement does not change the list's length and is not the structural modification that invalidates the view later. [A03-CODE]

### Appending to C changes a shared object

```java
base.get(2).append("!");
```

This time, the list position keeps the same reference. The operation changes the contents of the builder that reference identifies. Because all four lists expose that builder, each now sees `C!`.

The distinction is between **replacing a reference in one list structure** and **editing an object shared by multiple lists**. Copying the references separates the first kind of change, but leaves the second kind visible. [A03-CODE]

## What succeeds and what fails

The supplied OpenJDK 21 observation corresponds to these printed lines:

```text
base=[A, B2, C!, D]
copied=[B, C!]
wrapped=[B2, C!]
copied-add=blocked
window-size=invalidated
copied-after=[B, C!]
```

`copied.add(...)` throws `UnsupportedOperationException` because the returned list is unmodifiable. This also prevents replacing its elements through list operations. It does not prevent mutating an element: for example, a caller could still obtain its `C` builder with `copied.get(1)` and call `append` on that builder. The failed `add` therefore establishes a restriction on the list interface, not deep immutability of everything reachable through it. [A03-API]

Next, `base.add(...)` changes the backing list's size outside the `window` view. The supplied API rule says that the view's semantics are then undefined. OpenJDK 21 detects the incompatible backing-list modification when this program calls `window.size()` and throws `ConcurrentModificationException`. That is the reported implementation behavior; the portable conclusion is that subsequent use of the view is no longer supported by its stated contract. It is not safe to require every implementation, or every access method, to throw that exact exception. [A03-API, A03-OBSERVATION]

Nothing requires a second thread for this situation. The program itself modifies the backing list through one reference and later accesses a dependent view through another. The exception's name is not evidence that a thread was created.

`wrapped` still delegates to this same view, so making the interface unmodifiable does not remove the view's invalidation boundary. The program does not access `wrapped` afterward, and its trace establishes no particular exception from such an access. `copied`, however, has independent list membership, so `base.add` does not add `E` to it or invalidate its list structure. It still prints `B, C!`; later edits to its shared builders could still change their displayed text. [A03-CODE, A03-API]

## Construct the report from immutable values

Convert the selected builders to strings while capturing the report, then return an unmodifiable list of those strings:

```java
static List<String> snapshotLabels(List<StringBuilder> labels) {
    var values = new ArrayList<String>(labels.size());
    for (StringBuilder label : labels) {
        values.add(label.toString());
    }
    return List.copyOf(values);
}
```

At the original capture point, the library can use:

```java
List<String> report = snapshotLabels(base.subList(1, 3));
```

The temporary view is traversed before any later backing-list change. The returned report contains strings `"B"` and `"C"`, with no exported references to the builders or the view. Later replacing B, appending to C, or adding E cannot change that report. The strings preserve the captured characters, and the unmodifiable list prevents callers from changing membership or order.

Under the stated single-threaded conditions, nothing changes the source during this synchronous capture. If concurrent writers are introduced later, obtaining a snapshot of one consistent instant would additionally require coordination covering both list changes and builder changes; that is separate from the sharing problem demonstrated here.

Calling `List.copyOf` twice does not perform the text conversion. It still copies or reuses a list of references to the same builders; an already suitable unmodifiable list may even be reused. A second call provides no deeper element-copy policy. [A03-API]

A safe contract for the replacement is: **“The report is an unmodifiable list of immutable string values captured when the report is requested. Later source-list edits and builder edits cannot change those values.”** For more complex element types, an equivalent promise requires a defined policy for every mutable nested component: convert it to immutable values, or copy it without retaining mutable aliases and prevent callers from mutating the exported representation. Merely copying the outer list cannot establish that broader guarantee.
