**The current query accumulates whole timestamp groups, and `LAST_VALUE` stops at the end of the current group.** The intended report instead needs a filtered population, an event order that includes `id`, a running frame for the balance, and a whole-population frame for the repeated final status. [A20-FRAMES, A20-CONTRACT]

## Why the observed totals are 5, 10, 10, 9

A window's *frame* is the set of rows used to calculate its value for a particular output row. Here, the default frame starts at the beginning of the account and ends at the current timestamp's entire peer group. Peers are rows tied on the window's ordering values; because that ordering is only `ts`, ids 2 and 3 are peers. [A20-FRAMES]

| Output id | Current event status | Rows in the default frame | `SUM(delta)` |
| --- | --- | --- | --- |
| 1 | `open` | 1 | 5 |
| 2 | `review` | 1, 2, 3 | 5 + 7 − 2 = 10 |
| 3 | `paid` | 1, 2, 3 | 5 + 7 − 2 = 10 |
| 4 | `closed` | 1, 2, 3, 4 | 5 + 7 − 2 − 1 = 9 |

Thus id 2's calculation already includes id 3's −2. The total 10 for both timestamp-20 rows is invariant to the order between those two peers for these integer inputs. [A20-DATA, A20-FRAMES]

Their observed `LAST_VALUE(status)` of `paid` has a different status: it reflects `paid` being last within the tied group in that run. The window specifies no order between ids 2 and 3, so it does not guarantee that choice. Either `paid` or `review` can be the final peer's status; both rows share the same frame and therefore the same chosen last peer. The outer `ORDER BY ts,id` does not supply a tie-breaker inside the window. [A20-OBSERVATION, A20-FRAMES]

`LAST_VALUE` means the last value **in the current frame**, not automatically the last value in the account partition. At id 1, that frame ends with `open`. At timestamp 20 it ends with one of the tied statuses. Only at timestamp 30 does it reach `closed`. Consequently, the current event's `status`, the last status among timestamp peers, and the account's final status are distinct quantities.

## Correct query for the selected report

```sql
SELECT id, ts, status,
       SUM(delta) OVER (
           PARTITION BY account
           ORDER BY ts, id
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_total,
       LAST_VALUE(status) OVER (
           PARTITION BY account
           ORDER BY ts, id
           ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
       ) AS final_status
FROM event
WHERE ts <= 20
ORDER BY ts, id;
```

Each part has a separate job:

- **Population:** `WHERE ts <= 20` in this query filters rows before window evaluation. The account partition contains ids 1, 2, and 3.
- **Grouping:** `PARTITION BY account` keeps each account's calculations separate.
- **Logical event order:** each window's `ORDER BY ts,id` applies the specified business tie-breaker.
- **Balance frame:** `ROWS ... CURRENT ROW` includes events from the beginning through this individual event, producing a step after each event.
- **Final-status frame:** `... UNBOUNDED FOLLOWING` extends through the partition's last selected event for every output row.
- **Presentation:** the last `ORDER BY` sorts returned rows; it does not define either calculation's frame or ordering. [A20-CONTRACT, A20-FRAMES]

I verified this query with SQLite. It returns:

| id | ts | status | running_total | final_status |
| --- | --- | --- | --- | --- |
| 1 | 10 | `open` | 5 | `paid` |
| 2 | 20 | `review` | 12 | `paid` |
| 3 | 20 | `paid` | 10 | `paid` |

The balances are 5, then 5 + 7 = 12, then 5 + 7 − 2 = 10. The last selected event by `(ts,id)` is id 3, so `paid` repeats on every row. Id 4 is outside the reporting population. [A20-DATA, A20-CONTRACT]

## Filter placement and the proposed repairs

**Filtering an outer query after the windows have been evaluated does not redefine their population.** If the corrected windows above run over all four events and an outer query then hides `ts > 20`, the displayed balances are still 5, 12, and 10, but every displayed final status is `closed`. The balance frames for those rows never extend to id 4; the full-partition final-status frames do. Filtering first gives the same displayed event rows but repeats `paid` instead. The latter satisfies the contract. [A20-CONTRACT]

There is a subtle limit to that example: with the *original* default prefix frames, id 4 is already beyond the end of every retained row's frame. Moving this cutoff alone therefore leaves the original balance results at 5, 10, and 10 and does not repair the final-status semantics. In the supplied run, the outer filter would retain `open`, `paid`, and `paid`; the peer choice remains unspecified. The small example's lack of future-row influence under those faulty frames is not evidence that an outer filter implements the intended report.

**Adding `id` only to the outer ordering does not repair the windows.** That outer ordering already contains `id` in the supplied query. Even adding `id` to the windows would fix the balance's tie ambiguity without making default-frame `LAST_VALUE` a whole-partition calculation: with unique `(ts,id)` ordering, its default frame would end at the current event, yielding that event's status. The final-status frame still needs to extend to the last selected event. [A20-QUERY, A20-FRAMES]

**Removing the sum's window ordering gives a total, not a running balance.** With a whole-partition frame, all selected rows receive 10 if filtering happens first. If all four events are included during evaluation, they receive 9, even if an outer filter later hides id 4. Neither is the sequence 5, 12, 10. Removing the ordering from `LAST_VALUE` as well would additionally discard the business definition of which event is last. [A20-DATA, A20-CONTRACT]
