All three calls return normally in the shown program, but for different reasons: `clean` returns `"ok"`, `parse` returns `"recovered"`, and `lookup` returns `"forced"`. The `ValueError` is suppressed by the context manager; the `KeyError` survives the context manager and is then suppressed by the outer `finally` return. Seeing `close` in all three logs does not establish that either error reached the caller. [A05-CODE]

## Exact output and event order

The program prints:

```text
clean ok open,body,commit,close,outer-finally
parse recovered open,body,rollback-value,close,after-with,outer-finally
lookup forced open,body,close,outer-finally
```

I ran the supplied program under Python 3.12.14 and obtained these lines.

`@contextmanager` uses the generator's single `yield` as the boundary around the `with` body. Entering the context advances the generator to `yield`. Leaving the body resumes the generator normally if there is no exception, or throws the body's exception into the generator at that `yield` if there is one.

### Clean: normal context exit, then the pending return

Entering the context records `open`; the body records `body` and evaluates `return "ok"`. That return is pending while Python exits the surrounding scopes.

A return from a `with` body is a normal exit for the context manager: it is not an exception injected into the generator. The generator therefore resumes normally after `yield`. Its `try` completes without an exception, so its `else` records `commit`, followed by its `finally` recording `close`.

The pending function return then crosses the outer `finally`, which records `outer-finally` and falls through. The caller receives `"ok"`. `after-with` is skipped because execution is already returning from the function. [A05-CODE]

### Parse: the generator handles and suppresses the error

The body raises `ValueError("bad input")`. During context exit, that exception is thrown into the generator at `yield`. Its matching handler records `rollback-value`, but does not re-raise. The generator then records `close` and terminates normally.

For `contextmanager`, this normal termination after handling the injected exception means the exception was handled. Its exit machinery suppresses the body's `ValueError`. **The decisive suppression point is the generator's `except ValueError` branch finishing without re-raising**, not the cleanup log and not an automatic retry.

With the error suppressed, execution continues after the `with`: it records `after-with` and evaluates `return "recovered"`. The outer `finally` records `outer-finally`, then permits that return. The generator's `else` did not run: its `try` encountered an exception, even though its handler subsequently handled it. [A05-CODE]

### Lookup: context exit propagates, but the function overrides it

The body raises `KeyError("missing")`. The generator has no matching handler, so it skips `commit`, records `close` in its `finally`, and lets the same `KeyError` propagate out of the context manager.

That unwinding reaches the outer `finally`, which records `outer-finally` and executes `return "forced"`. **This return is the suppression point for the `KeyError`.** It replaces the pending exceptional exit with a normal function return. `after-with` is never reached. [A05-CODE]

## What the disputed explanations miss

Catching an exception inside the generator is not equivalent to logging and automatically propagating it. Propagation requires re-raising it. Likewise, selecting an exception for propagation does not make it immune to later control flow: a `return` in `finally` overrides the pending exception or pending return.

The reviewer's proposed explanation is also wrong. Removing the `return "forced"` branch would produce:

| Mode | Outcome after removing that branch |
| --- | --- |
| `clean` | Returns `"ok"` |
| `parse` | Returns `"recovered"` |
| `lookup` | Raises the original `KeyError` |

A return inside `with` does not bypass context exit. That is precisely why the clean path can run `commit` and `close` before returning.

In this synthetic program, `close` proves that execution reached the corresponding event append. It does not establish rollback—the lookup path has none—or exception propagation, which both failing paths eventually suppress. Since `close` is only an event label here, it also does not prove anything about an actual resource or durable transaction. In a future implementation, a log written before a close operation finishes would not even prove successful completion of that close. [A05-CODE, A05-CLAIMS]

## A small refactor for the shown ordinary exceptions

Catch ordinary operation errors, perform rollback, and re-raise. Keep `finally` for unconditional cleanup, but remove its return:

```python
@contextmanager
def transaction():
    events.append("open")
    try:
        yield
    except Exception:
        events.append("rollback")
        raise
    else:
        events.append("commit")
    finally:
        events.append("close")


def work(mode):
    try:
        with transaction():
            events.append("body")
            if mode == "parse":
                raise ValueError("bad input")
            if mode == "lookup":
                raise KeyError("missing")
            return "ok"
    finally:
        events.append("outer-finally")
```

With these successful event appends, the corrected behavior is:

| Mode | Caller observes | Events |
| --- | --- | --- |
| `clean` | `"ok"` | `open,body,commit,close,outer-finally` |
| `parse` | Original `ValueError` | `open,body,rollback,close,outer-finally` |
| `lookup` | Original `KeyError` | `open,body,rollback,close,outer-finally` |

The bare `raise` re-raises the active exception, preserving its identity, type, and traceback instead of replacing it with a generic error. Catching `Exception` here is cleanup followed by propagation, not broad suppression. There is no recovery branch after the `with`, and the outer `finally` performs its action without choosing a new return value.

## If operation and cleanup both fail

Removing the `finally` return also prevents it from hiding a later cleanup exception. But it does not, by itself, define a complete policy for multiple failures. If rollback or close raises while an operation error is active, the new exception becomes the one propagating, usually with the earlier exception retained as Python exception context. A caller inspecting only the top-level exception could therefore classify the failure differently.

A fuller implementation should independently attempt required cleanup, collect its failures, and make their relationship to the operation error explicit:

1. Retain the original operation exception and traceback as the primary failure.
2. Attempt rollback when required. Even if rollback fails, still attempt close, and retain both cleanup exceptions if both fail. Apply the same accounting to any fallible outer cleanup.
3. If cleanup succeeds, re-raise the original operation exception unchanged.
4. If there was no operation failure but cleanup fails, report the cleanup failure rather than silently returning success.
5. If both fail, expose both through a documented error contract.

For this caller's existing type-based retry policy, one suitable contract is to re-raise the original exception with a structured `cleanup_errors` attachment containing the actual cleanup exception objects and their tracebacks. Add a visible diagnostic note and require the error reporter to include those failures. That retains ordinary `except ValueError` and `except KeyError` matching while preventing the cleanup failures from disappearing into an ignored field. Within the original handler, successful recording can still be followed by bare `raise`.

If the caller API can change, Python 3.11 and later also provide `ExceptionGroup`, which can carry the original operation exception alongside all cleanup exceptions. It changes the top-level exception type, so the caller must explicitly inspect the operation component, or use `except*` handling, before applying retry policy. Simply wrapping everything in a group while leaving the old retry handler unchanged would not meet the caller's needs.

These policies concern the ordinary exceptions in the example. The refactor's `except Exception` does not establish a cancellation policy for exceptions outside that class, and none of these control-flow traces proves cleanup during interpreter shutdown or real database durability.
