这次事故表明：**请求的签名可以有效，调用者也可以通过认证，但一次业务操作仍可能被重复执行；同样，签名有效也不代表调用者拥有目标租户的权限。** 两笔订单证明本次重试造成了重复创建，没有证明 HMAC 被攻破。当前 version 3 本来就没有承诺“至多执行一次”。[B06-S1, B06-S3]

## 先分清三个问题

| 问题 | 在这个系统里由什么回答 |
| --- | --- |
| **认证：这个请求对应哪个客户端账号，签名覆盖的内容是否通过验证？** | 网关验证签名、检查 timestamp，并用识别到的 key 确定客户端身份，再添加 X-Client-ID |
| **授权：这个客户端能否对这个 tenant 执行这项操作？** | 服务检查租户成员关系和相应资源权限；现有代码明确检查了 directory.is_member(client, tenant) |
| **重放防护：同一份已签名请求再次到达时，是否会被识别并限制？** | version 3 有 60 秒时间窗口，但没有 nonce store，也没有至多执行一次的保证 |

这里的 nonce 指用来区分单次请求的值；保存已使用的值，才能据此识别重复。时间戳主要限制请求的新鲜程度，并不是唯一请求编号。同一时间可以有多个请求，而窗口内的同一请求也可以再次到达。[B06-S1–S2]

当前签名公式是：

```text
HMAC_SHA256(secret, method + "\n" + path + "\n" + timestamp + "\n" + SHA256(body_bytes))
```

因此，签名把 method、path、timestamp 和 body_bytes 的摘要绑定在一起。把 tenant 写进 path，意味着未经重新签名就改动该路径会影响验证；它没有把“这个客户端属于该 tenant”变成事实。所有涉事 key 都允许 POST，也不能用方法限制来解释本次租户权限差异。[B06-S1]

## 四次响应分别说明什么

### 10:00:08：原始请求返回 201

K 在 10:00:00 签署的 POST /tenants/T1/orders 在 8 秒后到达，处于规定的时间窗口内。网关接受请求；服务通过 X-Client-ID 得到客户端身份，发现 K 属于 T1，随后执行 save_order(tenant, order) 并返回 201。[B06-S2–S3]

这说明原始请求通过了这次认证和成员关系检查，并走到了成功响应。之后客户端的响应连接失败，不会由这段代码自动撤销已经保存的订单。客户端没有可靠收到响应，与服务没有执行操作，是两回事。

### 10:00:15：完全相同的重试再次返回 201

重试的 method、path、timestamp、body 和 signature 都相同，原时间戳仍在 60 秒窗口内。已有签名可以再次通过验证；当前网关没有记录“这份请求已经用过”的 nonce store。[B06-S1, B06-S3]

服务代码也没有针对 order.reference 的唯一性检查、idempotency-key handling，或跨重试共享的事务标识。因此，代码中的成员检查通过后会再次调用 save_order(tenant, order)。两次 201 本身只是两次成功响应；**存储日志里的两个不同 order identifiers、相同 reference R7 和相同 T1，才进一步确认了这次重复创建的实际结果。** [B06-S2–S3]

这与 version 3 的约定一致，不需要假设签名算法失效。材料没有交代 save_order 的所有内部行为，所以不能推出它在任何情形下都没有去重；可以确定的是，这次没有阻止两笔记录产生。

### 10:00:20：修改 path 后被网关拒绝

有人把捕获的 path 改为 /tenants/T2/orders，却没有重新计算 signature。path 属于签名输入，因此这份修改后的请求不再与原签名匹配。网关在转发之前拒绝了它。[B06-S1, B06-S3]

这次结果支持“该请求的路径修改被签名验证挡住了”，不能用来证明服务检查过 T2 成员关系：请求根本没有到达服务。材料也没有给出这次拒绝的具体 HTTP 状态码，不能补写成 401 或 403。

### 10:00:25：为 T2 正确签名，服务返回 403

K 的客户端使用合法 key 对 T2 的 path 正确签名，因此网关接受了请求。但认证出的身份仍然是 K；签名没有让 K 成为 T2 的成员。[B06-S1, B06-S3]

服务中的 directory.is_member(client, tenant) 返回否，于是执行 return 403。按给出的代码，这次在 parse_json(request.body) 和 save_order(tenant, order) 之前就返回了。它展示了认证成功而租户授权失败，正是服务独立检查权限的作用。[B06-S2–S3]

## 哪份文档适用，权限放在哪里

version 1 的概述依赖一个后来被移除的 nonce database，不能拿它替代当前 version 3 的约定。幻灯片中的“签名有效就有访问权”省略了服务授权步骤；99.99 percent availability 描述的是可用性，也不能证明权限正确或请求不会重复执行。[B06-S1, B06-S4]

建议继续把**客户端认证放在网关，把租户和业务资源授权放在服务实际执行操作的位置**。在描述的部署中，服务只能经网关到达，服务使用网关提供的 X-Client-ID，结合 path 中的 tenant 检查权限，然后才能创建订单。现有 directory.is_member(client, tenant) 就承担了成员关系检查；如果创建订单还需要其他资源权限，应按当前合同在服务中补齐，而不能把它们视为签名自动授予的权限。[B06-S1–S2]

## 提议的重试设计：让同一业务操作得到稳定结果

以下是需要新增的设计，**不是现有实现已经具备的能力**。目标是“幂等”：对同一次创建订单操作重试时，返回原来的业务结果，而不再创建一笔新订单。

1. **让客户端明确标识一次业务操作。** 例如新增 operation_id，同一次操作的所有重试都复用它；新的创建意图使用新的标识。把 operation_id 放进 body_bytes 中的约定字段，使现有公式里的 SHA256(body_bytes) 也覆盖它，并同步更新接口和服务处理逻辑。不能直接把 order.reference 当成已有的唯一键：当前没有这种约束，材料也没有规定相同 reference 必然表示同一次操作。

2. **在服务中按明确范围保存操作及结果。** 可以使用客户端账号、tenant、操作路径和 operation_id 共同确定唯一操作，并保存请求内容摘要。已认证且仍获授权的重试，如果标识和内容都相同，就返回原 order identifier 及约定的成功结果；如果标识相同而业务内容不同，应拒绝这种冲突，不能悄悄返回另一份订单。权限检查也必须覆盖结果重取，不能仅凭一个标识就泄露结果。

3. **把防重复检查和订单创建做成原子操作。** 也就是要么一起完成，要么一起不生效。例如，在同一个可靠事务里完成该标识的唯一占用、订单写入和结果记录，使并发重试只能有一个创建成功，其他请求等待后读取已保存结果。先查“没有记录”、再单独创建订单，会让并发请求同时通过。若当前存储无法提供所需事务，需要实现等价保证，不能仅靠增加一个字段。

4. **分开处理请求时间窗口与业务重试期限。** 重试可以使用新的 timestamp 和 signature，同时保留同一 operation_id；这样超过原签名的时间窗口后，仍能安全查询或取得同一次操作的结果。必须约定操作记录的保留时间、过期后的处理，以及“已提交但响应丢失”的恢复方式。删除去重记录后，如果仍把旧标识当成新操作接受，就不能继续承诺它不会再次创建订单。

仅在全局拒绝重复 signature，无法完成这套业务语义：它可能拒绝合理重试，却仍没有把第一次的结果交还给客户端；客户端换一个 timestamp 重新签名后，同一次业务操作又会具有不同 signature。如果另有必要增加 nonce 防重放，可以按每次传输尝试使用不同 nonce，同时让业务层继续复用 operation_id。两者解决的问题不同。[现有缺口见 B06-S1–S2]

这份材料的证据范围是四次描述的请求、给出的服务逻辑和两笔存储记录。它足以解释本次重复创建、一次路径篡改被拒绝和一次租户授权失败；它不能证明所有重放都会成功、所有未授权请求都会被正确阻止，或整个签名实现不存在其他问题。未来能提供多长时间、跨哪些故障的稳定重试保证，还取决于新增的原子写入、结果保存和保留策略是否实际实现并验证。
