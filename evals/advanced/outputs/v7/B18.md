**Q9 establishes a failure of the 10-unit business rule caused by two parsers assigning different meanings to the same authenticated bytes.** The gateway approved a value of 1, while the allocation service executed a value of 40. No broken HMAC or changed request bytes are needed to explain that result. [B18-S1–S3]

## How the request became a 40-unit reservation

The signed body was:

```json
{"units":1,"units":40,"label":"test"}
```

The repeated member name is the decisive detail. The two implementations retain different occurrences of `units`. [B18-S1–S3]

| Stage | Representation or decision | Consequence |
| --- | --- | --- |
| Authenticate | Check the HMAC over the exact body bytes, `POST`, and `/allocations` | The signature matches client K’s key |
| Gateway parsing | Retain the first `units`: `{"units":1,"label":"test"}` | The gateway evaluates 1 against its limit of 10 and permits the request |
| Forwarding | Send the original body, including both `units` members | The downstream service receives the ambiguity unchanged |
| Downstream parsing | Retain the last `units`: `{"units":40,"label":"test"}` | The downstream service obtains a different integer |
| Reservation | Trust the upstream limit check and reserve the downstream parsed value | The service reserves 40 units |

The implementation descriptions explain the sequence, and Q9’s logs and byte capture establish that it happened for this request: `signature_ok=true`, gateway `parsed_units=1`, downstream `parsed_units=40`, and `reserved_units=40`. Method, path, and body bytes remained unchanged. The reservation exceeds the intended per-request maximum by 30 units. [B18-S1–S3]

## Four different meanings of “validated”

**Integrity and authentication:** The valid HMAC establishes that these bytes, method, and path match the signature under K’s key. Byte capture also confirms that the body forwarded downstream was the body signed. Authentication does not make the client trustworthy about resource limits; the contract explicitly allows authenticated clients to choose their own payloads. [B18-S1, B18-S3]

**Semantic agreement:** This means that the components interpret the request as the same operation with the same values. It fails here: the gateway’s object says 1 unit and the service’s object says 40. Identical bytes do not guarantee identical parsed objects. [B18-S1–S2]

**Authorization and business-rule enforcement:** The relevant question is whether the operation actually executed is permitted. Checking 1 ≤ 10 does not establish that a subsequent reservation of 40 meets that rule. The account check succeeded for the correct account, but permission to act within an account does not remove its per-request limit. [B18-S1–S3]

**A person’s intent:** A valid signature under K’s key does not establish that the human account owner deliberately constructed duplicate fields. The packet leaves open intentional construction, serializer behavior, or another person’s control of that key. The observed rule violation is established; personal intent is not. [B18-S3]

Accepting only gateway-originated connections does not close this gap: the genuine gateway forwarded the genuine authenticated body. Likewise, “signature checked upstream” accurately describes authentication without establishing that the downstream value passed the upstream business check. [B18-S2–S3]

## Assess the fixes along the actual data path

### Canonicalizing only the signing input is insufficient

Canonicalization means producing an agreed representation of the data for signing or comparison. If only signature verification uses that representation while authorization and execution continue to parse the original duplicate-containing body differently, the original failure path remains: approve 1, then execute 40. The signing representation alone does not determine what the service reserves. [B18-S1–S4]

A canonicalization procedure also needs an explicit policy for duplicate names. Merely choosing one occurrence when constructing signing input does not force downstream code to choose the same occurrence. If the procedure rejects duplicates before the request proceeds, that rejection could block this case—but the effective fix would include rejecting the ambiguous request.

Changing the verification input would also change version 5’s exact-byte signing contract. Signers and verifiers would need to agree on the new contract; otherwise valid signatures under the old contract could fail. Even an agreed new signing contract would still need to bind authorization to what is executed. [B18-S1, B18-S4]

### Reject duplicates and execute the authorized representation

The second proposal addresses the mismatch directly. Detect duplicate names before authorizing the request; detection must occur before a parser silently discards either occurrence. Then validate the resulting values and ensure downstream execution consumes those same values. [B18-S1–S2, B18-S4]

For example, the gateway could authenticate the incoming bytes, parse with duplicate rejection, enforce the limit, and forward an unambiguous encoding of its validated object through the trusted gateway path. The service must consume that representation consistently. If bytes are rewritten, the original exact-byte HMAC still authenticates the original input; it should not be described as authenticating different output bytes.

### Enforce the limit where capacity is reserved

Moving or repeating the limit check at the allocation service would make it evaluate the integer it is actually about to use. For Q9, that value is 40, so a correctly implemented “at most 10” check would reject the reservation before capacity was allocated. [B18-S2–S4]

Repeating the check supplies an additional enforcement point; moving it makes the service the authoritative enforcement point for that rule. Either approach requires the applicable limit to be enforced consistently. It protects this reservation rule but does not, by itself, establish agreement about every other field or operation.

## What the incident establishes—and its limits

The current version 5 notes govern this explanation: they explicitly say that canonicalization and duplicate rejection were removed. The older checklist cannot be treated as evidence that those protections operated for Q9. Encrypted connections and successful request counts likewise supply no evidence that the parsers agree. [B18-S4]

This incident establishes that an authenticated, correctly routed request for the correct account bypassed the intended per-request resource limit through a parsing mismatch. It does not establish a cryptographic break, malicious intent by the account owner, or cross-account access in Q9. Nor does one observed incident establish general security guarantees for other requests, fields, versions, account-isolation paths, replay prevention, or cumulative resource limits. Those properties would require their own applicable specifications and evidence. [B18-S1–S4]
