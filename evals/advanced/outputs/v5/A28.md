After the partitioned replicas merge, **apple is present because tag `a1` survives**. The separate cleanup experiment also makes apple present, but for a different reason: removing all evidence that `a0` was deleted lets an old copy of `a0` become visible again.

## Partitioned operations and merge

An add tag identifies one particular user add. A removal records the tags that replica has already observed; it cannot remove an unseen add. Visibility requires at least one add tag absent from `Removed`. [A28-STATE]

Starting from `Adds={(apple,a0)}` and `Removed={}`:

| Replica and step | `Adds` | `Removed` | Visible apple? |
| --- | --- | --- | --- |
| R1 removes | `{(apple,a0)}` | `{a0}` | No |
| R1 re-adds | `{(apple,a0),(apple,a1)}` | `{a0}` | Yes, through `a1` |
| R2 adds | `{(apple,a0),(apple,b1)}` | `{}` | Yes |
| R2 removes | `{(apple,a0),(apple,b1)}` | `{a0,b1}` | No |

R2's removal records both `a0` and `b1` because it knows both. It cannot record `a1`, which it has not received. [A28-PARTITION]

Taking the union of the two final states gives:

```text
Adds    = {(apple,a0), (apple,a1), (apple,b1)}
Removed = {a0, b1}
Live add tags for apple = {a1}
```

Both replicas therefore show apple after receiving the other replica's full state. Receiving that state twice or in a different order does not change the result. Set union ignores repeated members, and its result does not depend on message order or grouping. These properties are called idempotence, commutativity, and associativity, respectively. They explain convergence once replicas have received the same updates. [A28-STATE, A28-MERGE]

## What the conflict rule promises

**R2's final local remove does not win globally.** It removes all apple tags R2 observed, including its own earlier add `b1`. R1's new add `a1` was unseen by that removal and survives. This is the specified observed-remove rule: removal applies to observed add identities. The two operations' wall-clock timestamps play no role. [A28-STATE, A28-PARTITION]

**Tags are not quantities.** Even if several live tags existed, the UI would still report the single membership fact “apple is present.” In this particular merged state, only `a1` is live anyway. Neither the total number of stored tags nor the number of live tags defines an inventory quantity under this contract.

**A delivery retry is not a fresh user add.** A new user add creates a globally unique tag. Redelivery carries the existing tag, allowing union to recognize it as the same update. If every retry invented a tag, retrying a removed add could incorrectly create a new live add that the original removal never covered. That would change the protocol's meaning. [A28-STATE, A28-MERGE]

## Why the cleanup resurrects apple

This experiment starts separately with:

```text
R2: Adds={(apple,a0),(apple,b1)}, Removed={a0,b1}
R3: Adds={(apple,a0)},            Removed={}
```

Apple is absent at R2 because both known tags are removed. R2 then erases the add entries and their removal markers, becoming:

```text
R2 after cleanup: Adds={}, Removed={}
```

When R3's old state arrives, union produces:

```text
Adds={(apple,a0)}, Removed={}
```

Now `a0` has no removal marker, so apple is visible. This is a stale add returning after evidence of its removal was lost, not an unseen fresh user add surviving a concurrent removal. [A28-CLEANUP]

The removal markers, often called **tombstones**, preserve the information needed to suppress such old adds. Keeping the marker for `a0` would keep it invisible even if its add entry returned. The basic merge rule only grows sets; deleting removal evidence introduces an operation outside the convergence argument for those growing sets.

## What would justify reclaiming metadata

“Absent here” is insufficient. A cleanup protocol needs to establish that discarded tags cannot later arrive as apparently live adds from any permitted replica or message. That requires more information than these two sets contain.

One approach tracks acknowledgements and each replica's progress through updates. A removal becomes safe to compact only when every relevant active replica has incorporated it and delayed older states are either rejected or still suppressed by retained compact removal knowledge. **Acknowledgement alone is insufficient if an old state message can still be merged after all explicit markers disappear.** Per-replica sequence numbers or similar causal records can preserve the knowledge that older adds have already been removed without retaining each original marker separately.

A concrete alternative is a coordinated **epoch change**, where an epoch is a numbered generation of accepted replica state:

1. Establish a checkpoint that includes the agreed visible state and all removals to be reclaimed.
2. Have every continuing replica adopt the new epoch, or formally retire replicas that cannot participate.
3. Reject messages from earlier epochs. An offline or retired replica must obtain the new checkpoint before participating again; it cannot merge its old snapshot into the new epoch.
4. Only then discard the obsolete add entries and removal markers covered by that checkpoint.

The barrier, membership rules, and rejection of obsolete messages are essential. Simply naming an epoch without enforcing those rules would not prevent resurrection. In the supplied experiment, R3 has neither acknowledged the removal nor been retired, and old messages remain acceptable, so reclamation has no such justification. [A28-CLEANUP]

## Limits of convergence

The defined merge gives replicas the same membership result when they eventually incorporate the same states. It does not provide a globally latest wall-clock remove, a numeric item quantity, or an inventory reservation that prevents separate replicas from promising the same stock. Those require additional semantics and, where necessary, coordination. It also allows replicas to disagree while disconnected: R1 shows apple and R2 does not during this partition. The protocol resolves that disagreement by the precise tag rule above; it does not eliminate every kind of application conflict.
