Caching a coroutine object prevents it from being executed a second time; caching a Task allows requests to share one execution. Shielding each request's await protects that shared execution from that request's cancellation, but expiry, failure recovery, and ownership of background work still need explicit rules.

## What the fixture prints

I ran the supplied program under Python 3.12.14. It printed:

```text
first loaded:x
second-error RuntimeError
shield False cached-cancelled True
events fetch:start,fetch:finally,A:cancelled,B:cancelled
later cancelled
shield True cached-cancelled False
events fetch:start,A:cancelled,fetch:finally,B:loaded
later loaded
```

### Caching the coroutine

Calling an `async def` function produces a **coroutine object**: an object describing work that can be awaited. The `lru_cache` wrapper caches that object when `raw("x")` is called; it does not await the function and cache the eventual string. [A25-CODE]

The first await runs the coroutine and obtains `"loaded:x"`. The second call returns the same, already completed coroutine object. Awaiting it again raises `RuntimeError`, which the fixture catches. The string is reusable; the coroutine that produced it is not reusable this way.

These three objects have different roles:

| Object | Meaning here | Reuse |
| --- | --- | --- |
| Coroutine object | Work returned by calling the async function | Cannot be awaited again after completion |
| Task | One scheduled execution of a coroutine | Multiple readers can await it, including after completion |
| Result value | The string produced by successful execution | Can be stored and returned without another fetch |

A completed Task preserves its outcome: a result, an exception, or cancellation. Keeping a failed or cancelled Task in the cache therefore also preserves that failure for later readers.

### Shared Task without shielding

Both readers get the same Task. The cache lookup and insertion contain no `await`, so in this single event loop there is no opportunity for the other reader to interleave between the check and insertion. The two sleeps establish that the readers and fetch have started; they define no cache lifetime. [A25-CODE]

When `a.cancel()` cancels A, A is directly awaiting the shared Task. Cancellation propagates to that Task. The fetch exits through its `finally` block, and both A and B receive `CancelledError` from their awaits. Each reader catches it and records its cancellation, so the surrounding function can continue.

Setting `gate` afterward cannot restart a cancelled Task. The cache still contains it, so `cached-cancelled` is `True` and the later lookup also raises `CancelledError`. Separate reader coroutines did not isolate the cancellation of the shared work.

### Shared Task with shielding

`asyncio.shield(task)` creates a cancellation boundary around each caller's await. Cancelling A still interrupts A's await and gives A `CancelledError`; it does not forward that cancellation to the shared fetch. A therefore records `A:cancelled` while the useful work continues.

After `gate.set()`, the fetch returns `"loaded"`, running `finally` on its way out. B receives the result. The successful Task remains cached, and the later lookup returns that same result without starting another fetch. [A25-CODE]

Shielding does not make the Task impossible to cancel. A cache owner can still call `task.cancel()` directly during eviction or shutdown, and cancellation of the underlying Task can still reach its shielded waiters. Merely deleting a dictionary entry does not itself cancel the Task.

## A concrete cache lifecycle

One design meeting the stated intent uses a cache manager with two maps: `inflight[key]` for owned Tasks and `results[key]` for successful values plus their expiry times. [A25-INTENT]

1. **Look up a successful result first.** Return it only while its expiry time is in the future. Use a monotonic clock, which measures elapsed time without depending on wall-clock adjustments. Define the TTL explicitly—for example, from successful fetch completion—and discard expired entries.
2. **Join or start one fetch.** If no valid result exists, reuse the current in-flight Task or create and insert one without yielding between the check and insertion. Every consumer awaits it through `shield`. This needs synchronization if the design later permits access from multiple threads or event loops.
3. **Publish successful completion.** Store the value and its expiry time, then remove the corresponding in-flight entry. Publish only if the task still belongs to the current cache entry or generation; a task invalidated during its run must not overwrite a newer result.
4. **Evict failed and cancelled executions.** Remove their matching in-flight entries so the next request can retry. A lookup should also recognize a completed failed or cancelled Task if its completion callback has not run yet. Do not retain a permanent failure unless a separate, explicit failure-caching policy requires it.
5. **Give the manager cancellation ownership.** A concrete policy is to let a fetch finish even when all consumers disappear, so its result may serve a later request. Keep strong references to owned background tasks. Explicit invalidation and shutdown can cancel them and await their termination. If the desired policy instead cancels when the last consumer leaves, count consumers and decrement in `finally`; make the zero-consumer decision inside the manager rather than relying on cancellation propagation from a particular reader.
6. **Observe background failures.** Completion handling must retrieve and appropriately record exceptions even when nobody remains to await the Task. Check `task.cancelled()` before inspecting its exception. Shielding provides no automatic exception-reporting policy.

The key removal guard is:

```python
if inflight.get(key) is completed_task:
    del inflight[key]
```

Without this identity check, an old Task's delayed callback could delete a newer Task installed under the same key. Result publication needs the same protection, potentially with a generation number if invalidation must distinguish successive versions. Exception observation should still happen even when an old Task is no longer the current entry.

The fixture demonstrates coroutine reuse failure, cancellation propagation through an unshielded shared Task, and isolation of caller cancellation through shielding. It does not implement or test TTL expiry, transient fetch exceptions, replacement races, abandoned-work handling, or shutdown ownership. Those remain design responsibilities. Its dictionary shares work within the stated process and event loop; shielding adds no cross-process cache coordination.
