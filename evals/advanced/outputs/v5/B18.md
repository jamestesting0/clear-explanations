**Q9 bypassed the per-request limit because the gateway checked one meaning of the signed bytes and the allocation service executed another.** The signature could be valid throughout: authenticating bytes does not guarantee that two parsers interpret duplicate JSON member names identically. [B18-S1–S3]

## The actual request path

The body was:

```json
{"units":1,"units":40,"label":"test"}
```

| Stage | Relevant operation | Result for Q9 |
| --- | --- | --- |
| Authentication | Check the HMAC over the exact body bytes, method, and path | Valid under client K's key |
| Gateway parsing | Retain the first occurrence of each member name | `{"units":1,"label":"test"}` |
| Gateway limit check | Permit at most 10 units | 1 passes |
| Forwarding | Send the original body bytes unchanged | Both `units` members remain present |
| Service parsing | Retain the last occurrence of each member name | `{"units":40,"label":"test"}` |
| Allocation | Trust the upstream limit check and reserve the parsed quantity | 40 units reserved |

The two displayed parsed objects summarize the meanings produced by the specified parsers; they are not replacement bodies observed on the wire. Byte capture confirms that the original body was forwarded unchanged, and the logs connect both parsed values and the reservation to Q9. Method and path also stayed `POST /allocations`. [B18-S1–S3]

The service's restriction to gateway-originated connections does not prevent this failure. The gateway itself forwards the ambiguous request after approving its own interpretation. The separate account check also does not enforce the quantity limit; Q9 used the correct account. [B18-S2; B18-S3]

## What “validated” must distinguish

- **Integrity and authentication:** The supplied bytes, method, and path match the HMAC under K's key. There is no need to posit a signature forgery or an in-transit modification to explain this incident. [B18-S1; B18-S3]
- **Semantic agreement:** The components must assign the same meaning to the request. Here they demonstrably disagree: the gateway sees 1 unit and the service sees 40. Cryptographic verification does not settle that disagreement. [B18-S1–S3]
- **Authorization and business-rule enforcement:** An authenticated client is still limited to at most 10 units per request. The gateway approved a quantity of 1, but the action actually performed reserved 40. The rule therefore failed at the boundary between the checked interpretation and execution. [B18-S1; B18-S2]
- **Human intent:** A valid HMAC attributes the request to use of K's key, not conclusively to a particular person's deliberate action. The packet does not establish whether the owner constructed the duplicates, a serializer produced them, or somebody else controlled the key. [B18-S3]

## Which fixes change the failing data path?

**Reject duplicates before authorizing the parsed request.** Duplicate detection must happen before an ordinary parser discards one occurrence; after that, the evidence of ambiguity may already be lost. Rejecting Q9's repeated `units` member prevents this specific disagreement. Version 5 does not currently promise such rejection. [B18-S1; B18-S4]

**Make execution consume the representation that passed the business checks.** A coherent path is to authenticate according to the applicable signature contract, reject ambiguous input, construct one authoritative parsed representation, validate its fields and quantity, and pass that meaning to the allocator. If it is serialized and parsed again, the boundary must preserve that meaning. Rewriting bytes also requires handling the authentication contract correctly: an HMAC checked over the original bytes is not automatically an HMAC over newly serialized bytes. [B18-S1; B18-S4]

**Canonicalizing only the signature input is insufficient.** Canonicalization means converting input to a standardized representation. Changing what is signed or verified would require agreement with clients and would change the current exact-byte contract. More fundamentally, it leaves the original failure intact if the gateway still checks a first-occurrence interpretation and forwards original bytes for a last-occurrence interpretation downstream. A standardized signing form only helps this problem when the checked and executed meanings are also aligned; it cannot substitute for that alignment. [B18-S1; B18-S2; B18-S4]

**Enforce the quantity limit at the allocation service before reservation.** Whether moved there or checked again there, the rule would evaluate the actual quantity about to be used. For Q9, it would see 40 and reject the request before reserving capacity. This directly protects the resource at the point of use, although it does not by itself resolve every possible ambiguity in other fields. [B18-S2; B18-S4]

The older checklist cannot establish current duplicate rejection or canonicalization: version 5's implementation notes explicitly say both were removed. Encrypted transport and successful requests likewise provide no evidence of parser agreement. [B18-S4]

## What the incident establishes

The records establish a concrete failure of the 10-unit per-request limit: a validly authenticated Q9 reserved 40 units through the documented parser mismatch. They do not establish malicious human intent, cross-account access, or a failure of the HMAC algorithm. Nor does one incident establish general security of the signature implementation, confidentiality, enforcement of other quotas, or behavior for every other payload. Those guarantees would require their own specifications and evidence. [B18-S1–S4]
