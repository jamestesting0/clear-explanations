The note “came back” in a visible local draft and then in an export, but the supplied trace shows **no restoration of the canonical server note**. The mobile update was rejected, and the subsequent direct server read still found the deletion tombstone at epoch 5. The confusion comes from presenting preserved local work in places a user may interpret as synchronized data. [B11-S3, B11-S4]

### What the server actually checks

An **epoch** is a server-controlled generation number for a note. Deletion advances that number and leaves a **tombstone**, a record that the note is deleted. A revision orders accepted edits only within one epoch. Thus local revision 9 in epoch 4 cannot outrank deletion in epoch 5, regardless of the phone's timestamp. The old timestamp-based design sketch does not describe the current deployed contract or handler. [B11-S1, B11-S2]

The incident follows this sequence:

| Time | Local or server event | What it establishes |
| --- | --- | --- |
| 09:00 | Phone synchronizes epoch 4, revision 8 | The phone's last known server version |
| 09:10 | Browser deletes N; server writes epoch-5 tombstone | The primary note is deleted |
| 09:30 | Offline phone shows its epoch-4 draft as “pending sync” | A local draft is visible; no server acceptance is shown |
| 09:40 | Mobile update returns 409 | The submitted update is rejected |
| 09:41 | Local CSV export includes the draft's title | The exporter included locally retained work |
| 09:42 | Direct GET returns 404 with tombstone epoch 5 | The primary record remains deleted at that read |

Events from [B11-S4], interpreted using [B11-S1–S3].

For the 09:40 update, the handler loads epoch 5 and compares it with the request's epoch 4. They differ, so it takes the **first branch and returns 409**. It never reaches the tombstone check or `write_content`. A request carrying the current epoch against that tombstone would instead reach the second branch and return 410. Neither path writes note content. [B11-S2]

The shared lock matters because deletion cannot slip between this handler's check and its write. If an otherwise valid update runs before deletion, deletion subsequently removes its content; an old-epoch update running after deletion fails the epoch check. That prevents the stale-check-then-write race along this mobile update path. [B11-S1, B11-S2]

### Why the CSV does not demonstrate restoration

The interface explicitly permits an offline draft to appear with “pending sync.” After a 409, it preserves that draft in the conflict tray so the user can recover their work. Conflict items are excluded from the ordinary synchronized list, but the current CSV exporter combines both kinds of local item without a status column. It does not read the primary database. [B11-S3]

A title in that CSV is therefore evidence of retained **local content**, not evidence that the rejected update was committed. “Resurrection” can mean a deleted title reappearing to the user, a saved draft surviving a conflict, or server content being restored. The first two describe this experience; the observed mobile response and server GET do not support the third. [B11-S3, B11-S4]

### What this proves—and the limit of the claim

For this incident, the current contract, deployed code, response, and later server read agree: the stale mobile update did not restore N. That conclusion does not require treating the customer's visible experience as mistaken. [B11-S1–S4]

Claiming deletion can **never be bypassed anywhere** would require reviewing every route that can write or rebuild a note: administrative imports, backup recovery, explicit restore, and any other applicable write paths. The review would need to establish that deployed implementations preserve the intended epoch and tombstone rules, including during concurrent operations. Authorized explicit restoration must also be distinguished from an unintended bypass. The current contract's scope and this trace do not establish those system-wide properties; they contain no evidence of imports or backups participating here. [B11-S1, B11-S4]

A product clarification should say, after rejection, **“Deleted on server. Your unsynced draft is saved in Conflicts.”** The exporter could default to synchronized notes and offer an explicit option to include conflicts with a status column identifying them as local, uncommitted drafts. Those would be proposed changes: the supplied specification says the current exporter still combines the items without that distinction. [B11-S3]
