The callbacks retain different things: `late` shares one variable referring to the original second dictionary; `objects` retains each original dictionary; `values` retains each original number. None of them follows the replacement now occupying `rows[1]`.

## Exact output

```text
S1 [2, 2] [10, 2] [1, 2]
S2 [99, 99] [10, 99] [1, 2]
rows [{'n': 10}, {'n': 20}]
buckets [['x', 'y'], ['x', 'y']]
outer-copy [['x', 'y'], ['x', 'y']]
```

## What each callback retains

Call the original dictionaries **D1**, initially containing `{"n": 1}`, and **D2**, initially containing `{"n": 2}`. Initially, `rows` refers to D1 and D2, and `saved_second` also refers to D2.

| Construction | Evaluated while building callbacks | Evaluated when `f()` runs |
| --- | --- | --- |
| `lambda: row["n"]` | Each function captures access to the same comprehension variable `row` | Read that variable, then look up `"n"` in its dictionary |
| `lambda row=row: row["n"]` | The right-hand `row` is evaluated for each function and stored as its default argument | Use that dictionary reference, then look up its current `"n"` |
| `lambda n=row["n"]: n` | Look up `"n"` immediately and store the resulting integer as the default | Return the stored integer |

The `late` comprehension has its own variable scope, but it does **not** create an independent `row` variable for each iteration. Both functions share that variable, whose final value is a reference to D2. The later comprehensions have their own scopes; they do not change this captured variable. [A17-CODE]

The two mutations before S1 do different things:

1. `rows[0]["n"] = 10` changes D1 itself. The first `objects` callback refers to D1, so it now returns `10`.
2. `rows[1] = {"n": 20}` creates a new dictionary, D3, and changes the second slot of `rows` to reference D3. It does not modify D2 or redirect existing references to it. D2 remains reachable through `saved_second`, the `late` functions, and the second `objects` function.

Consequently, S1's `late` functions both read D2's `2`; `objects` reads D1's `10` and D2's `2`; and `values` returns its captured `1` and `2`.

Next, `saved_second["n"] = 99` mutates D2. Both `late` functions and the second `objects` function see `99` at S2. The source list still contains D1 and D3, so its display remains `10` and `20`. A dictionary need not remain in `rows` to remain alive and observable through other references.

## Which behavior each interface offers

| Callback list | Historical number at construction | Later edits to each original row object | Current occupant of each list position |
| --- | --- | --- | --- |
| `late` | No | No as a per-row interface; both follow D2 | No |
| `objects` | No | Yes | No |
| `values` | Yes, for these integer values | No | No |

Thus the reviewer predicting `20` for every second callback is mistaken: none of these callbacks looks up the source-list slot when invoked. An interface that intentionally follows positions would retain access to the intended source list and a fixed index, then retrieve that index's current object on each call. Its behavior on deletion or reordering would also need a contract. [A17-INTENT, A17-REVIEW]

The default argument in `objects` captures a dictionary **reference**, not a deep snapshot. Mutations to that dictionary remain visible. In `values`, the captured values are immutable integers: changing a dictionary entry replaces the entry's reference rather than modifying the previously captured integer. That explains the historical behavior here. If the captured value were itself a mutable list or nested object, a default argument would retain that object instead; it would not automatically freeze or recursively copy its contents. Historical behavior for arbitrary values needs an explicit decision about which nested state to copy or convert.

## Why both buffers change

There are two separate sharing operations:

1. `[[]] * 2` creates one inner list and repeats the reference to it in two outer slots. It does not create two independent buffers.
2. `buckets.copy()` creates a different outer list but copies those same references. All four slots across the two outer lists therefore point to the single inner list.

Appending `"x"` through `buckets[0]` changes that shared inner list. Appending `"y"` through `outer_copy[1]` changes it again. Both outer lists consequently display the same `['x', 'y']` contents twice. The reviewer is right that the outer identity changes, but wrong that the inner identities change. [A17-CODE, A17-REVIEW]

Independent per-row buffers require creating a distinct mutable buffer for each row. Copying an outer container is insufficient whenever the state that must be independent lives in its referenced inner objects. That requirement is settled here; the callback policy remains a product choice among the distinct behaviors above.
