**The outbox made the order and its event atomic locally; it did not make remote reservation creation atomic with the local “sent” flag.** The lost response left a reservation that the sender could not confirm, and the retry used a new key that allowed another reservation.

## The transaction boundaries and the incident

The first local transaction commits order O8 and event E8 together. The dispatcher later calls a separate system, then uses a second local transaction to mark E8 sent. The receiver's database participates in neither local transaction. [B29-S1]

| Step | Sender's durable state | Receiver's effect |
| --- | --- | --- |
| 09:00: local transaction commits | One order O8; one unsent event E8 | None yet |
| Send E8 with key A1; response is lost | E8 remains unsent | Creates R101 |
| 09:01: retry E8 with key A2 | E8 remains unsent until acknowledgment is recorded | Creates R102 |
| Success is received and recorded | E8 is marked sent | Both reservations remain |

This is the supplied incident sequence. Nothing requires two local event rows for two delivery attempts or two external effects. [B29-S3]

A missing response is ambiguous: the request might not have reached the receiver, or the receiver might have completed it and lost the response. A dispatcher crash after remote creation can produce the same ambiguity. Even after receiving success, the dispatcher can crash before committing the sent flag; recovery then finds an unsent event and retries it. These are gaps between separate operations, not a failure of the order/outbox transaction. [B29-S1]

## Why the current keys defeat duplicate protection

The receiver recognizes retries through **Idempotency-Key within its account and route scope**, not through `event_id` in the body. An idempotency key tells the receiver that repeated requests represent the same intended operation. A1 and A2 instead identify different attempts, so the receiver treats them as separate operations despite their identical bodies. [B29-S2, B29-S3]

Use a stable key derived from E8 for every delivery of E8, preserving the account, route, and payload. During the retention period, retrying after R101 was created would return R101's original result without creating R102. Reusing that key with a changed payload would instead return 409 under the stated contract. [B29-S2, B29-S4]

## Why marking sent first does not solve it

If the dispatcher commits “sent” before calling the receiver, a crash between those steps leaves an event marked sent that was never transmitted. The normal unsent-event dispatcher then skips it, so the committed order can have no external reservation. Moving the flag changes the failure mode from a retry that can duplicate an effect to a possible lost delivery; it cannot join two databases into one atomic operation. [B29-S1, B29-S4]

Keeping the flag update after success, with a stable key, allows retries while the receiver suppresses duplicate creation.

## The bounded guarantee and old replays

Under the given receiver contract, a stable key supports **at most one reservation for the matching requests while the original key remains protected**, provided their account, route, and payload are unchanged. It does not guarantee that a request will eventually succeed, and it does not prevent duplicate creation forever. The guaranteed retention is 24 hours after first use; retries do not establish a fresh guaranteed 24-hour window. [B29-S2]

A manual replay after 36 hours falls outside that guarantee. The receiver may have forgotten E8's key and may create another reservation even if the sender uses the correct stable key. Addressing that case requires an additional design, such as:

- Receiver-side uniqueness for the business operation or event, enforced atomically with reservation creation and retained for the required lifetime.
- Durable idempotency records covering the full permitted replay horizon, with replay limits that keep attempts inside that horizon.
- A reliable reconciliation process for old ambiguous outcomes, instead of blindly replaying them; any subsequent creation must also be protected against duplicate or concurrent creation.

Those protections are not supplied by the packet. The stable-key fix also does not remove the already-created R101 and R102; that incident needs reconciliation. The overview's “exactly-once delivery” phrase therefore overstates the architecture: durable local event creation, repeated transmission attempts, and remote effects have different guarantees.
