**`structuredClone` comes closest to the report contract, but it drops the symbol-keyed marker and rejects the demonstrated function value.** Spread shares the mutable nested objects; the JSON round trip loses the `Date` type and the present-with-`undefined` property. None is interchangeable without an explicit data contract.

## Results of the three copies

After the two source mutations, the results are:

| Property or diagnostic | `spread` | `json` | `cloned` |
| --- | --- | --- | --- |
| `meta.tag` | `"new"` | `"old"` | `"old"` |
| Type of `created` | `Date` | string | `Date` |
| Value represented by `created` | `2030-01-01T00:00:00.000Z` | `"2025-01-01T00:00:00.000Z"` | `2025-01-01T00:00:00.000Z` |
| Printed `year` field | `2030` | `"2025-01-01T00:00:00.000Z"` | `2025` |
| `optionalOwn` | `true` | `false` | `true` |
| `secretOwn` | `true` | `false` | `false` |
| `hiddenOwn` | `false` | `false` | `false` |
| `inheritedOwn` | `false` | `false` | `false` |

| Printed `amountGetter` field | `"undefined"` | `"undefined"` | `"undefined"` |

Where `optional` remains present, its value is `undefined`. The retained symbol-keyed property's value in `spread` is `"token"`. These results follow the construction and mutation order in [A18-CODE].

**Spread copies property values into a new outer object.** It includes the source's own enumerable properties, including the symbol-keyed marker. But the values of `meta` and `created` are references to the original objects. The later tag edit and `Date` mutation therefore appear through `spread`. A different outer object does not imply independent nested objects.

**The JSON round trip converts the data to JSON text and parses that text.** The resulting `meta` object is independent and keeps `"old"`. The `Date` is serialized as an ISO date string and remains a string after parsing. The `optional` object property is omitted because its value is `undefined`; the symbol-keyed property is omitted too. Those demonstrated losses already disprove the claim that this technique preserves every JavaScript value.

**`structuredClone` independently copies the demonstrated nested object and `Date`.** It preserves the date's type and original 2025 value, and retains the own `optional` property with value `undefined`. It does not copy the symbol-keyed marker.

All three omit the nonenumerable own property `hidden` and the inherited property `inherited`. They also do not preserve this source's custom prototype, so the copies do not inherit its `inherited: 9` value through another route. These are property-selection and prototype differences, separate from whether nested data is shared.

## Why the getter produces three different amounts

Each technique reads the source's enumerable `amount` once, in this order:

1. Spread invokes the getter, increasing `reads` to `1`, and stores the returned number `1`.
2. `JSON.stringify(source)` invokes it, increasing `reads` to `2`. The JSON text and parsed object contain the number `2`.
3. `structuredClone(source)` invokes it, increasing `reads` to `3`, and stores the returned number `3`.

**Running a getter while copying is different from copying the getter itself.** Each result has an ordinary data property holding a number; none retains the accessor that increments the counter. Its property descriptor has no `get` member, so `typeof ... .get` produces the string `"undefined"`. Reading the reports for printing does not invoke the source getter again. The final counter line is therefore:

```text
reads 3
```

This also refutes both parts of the third reviewer's claim: `structuredClone` does not preserve the original accessor descriptor, and this built-in does run user-defined getter code during copying. [A18-CODE, A18-CLAIMS]

## Choosing the report contract

For the demonstrated fields, `structuredClone` supplies independent `meta` and `created` objects, a usable `Date`, a present `optional`, and a fixed `amount`. Those properties fit the report's stated needs. Its marker loss remains a contract violation until deliberately addressed. [A18-CONTRACT]

There are two legitimate ways to address that marker:

- Preserve the known marker explicitly under the same symbol key. Here its value is a string, so retaining that value introduces no shared mutable nested state.
- Agree to remove or replace the marker requirement, document the new representation, and migrate the consumer before relying on its omission.

For a helper named `snapshot`, I would define an explicit report shape and its supported values, rather than promise to reproduce arbitrary JavaScript objects. Specify that `amount` is evaluated once during report creation and stored as data. If even that construction-time getter side effect is unacceptable, the input contract must require plain data or reject accessors before reading them; this fixture does not obtain that guarantee merely by using a built-in.

The function experiment prints:

```text
function-clone DataCloneError
```

The own enumerable `run` property contains a function that `structuredClone` cannot clone. The operation throws instead of returning a report with that function preserved. This demonstrates a function limitation; it does not imply that every non-plain object is unsupported—the successful `Date` clone demonstrates otherwise. Nor does the successful fixture establish support for all other object categories. [A18-CODE]

A future plugin therefore needs a declared boundary: for example, reject unexpected or unsupported report fields with a clear error, or explicitly exclude plugin behavior from the report representation. Silently changing to another copying technique on failure would change the API's preservation rules. The treatment of an omitted field must be intentional, just as it must be for the marker.

Finally, equal-looking JSON is insufficient evidence of equal API behavior. A `Date` and its ISO string can serialize alike; absent properties and properties containing `undefined` can disappear alike; symbol keys and getter descriptors are not shown. Consumers can still distinguish these objects by calling date methods, checking ownership of properties, or observing mutations and getter effects.
