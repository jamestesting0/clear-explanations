The plan has two separate problems: **the initial data cannot support unique normalized identities, and old writers can create new conflicts after any backfill.** A safe rollout must resolve ownership conflicts and bring every identity writer under the new rules before treating case-insensitive login as unambiguous.

## Where the checklist fails

Adding nullable `email_norm` preserves version 1's existing column and allows its inserts to continue. The first backfill can also succeed while that column has no unique index, but it produces:

| Account | `email` | Backfilled `email_norm` |
| --- | --- | --- |
| 1 | `Li@EX.test` | `li@ex.test` |
| 2 | `li@ex.test` | `li@ex.test` |
| 3 | `sam@ex.test` | `sam@ex.test` |

The subsequent unique-index creation fails because accounts 1 and 2 have the same non-null normalized value. Creating the index first would merely move the failure to the colliding backfill update. Neither order resolves which account owns the identity. [A16-OLD, A16-DATABASE]

Later steps have additional compatibility problems:

- **Enabling version 2's proposed login:** a normalized lookup can find accounts 1 and 2, violating its expectation of exactly one result. Calculating a fallback does not remove that ambiguity.
- **Setting `NOT NULL` during the mixed fleet:** existing nulls prevent enforcement; even after clearing them, version 1 inserts omit the column and would fail. Version 1 email updates can also leave an already populated `email_norm` stale.
- **Replacing the original column:** even if the rename and drop are arranged in a legally executable sequence, the replacement destroys the old representation and changes its meaning. Version 2 also references `email_norm`, so renaming it requires coordinating those readers and writers too. [A16-NEW, A16-PLAN]

A column still being named `email` preserves only part of the old SQL syntax. Version 1 relies on case-sensitive identity and accepts raw addresses without normalizing them. Putting normalized values under that name does not preserve those behaviors or ensure future old-version writes stay normalized. Keeping rollback possible requires preserving the data and write semantics that the rollback binary needs, not merely a familiar column name.

## Why the race passes the index

In the later race, the stored normalized values are:

| Account | `email` | `email_norm` |
| --- | --- | --- |
| 4 | `PAT@EX.test` | null |
| 5 | `Pat@ex.test` | `pat@ex.test` |

The index sees a permitted null and one non-null value. It never compares `lowercase(email)` across both rows. Their original emails also differ under version 1's case-sensitive comparison. Both inserts therefore satisfy the described constraints, although both effective normalized identities are `pat@ex.test`. [A16-RACE]

A lookup that includes the null fallback finds both accounts. A lookup that checks only stored normalized values overlooks account 4. Neither lookup strategy enforces uniqueness. Version 2's local transaction keeps its own two fields consistent, but does not make version 1 populate or validate its field. A completed backfill describes rows processed at that time; it imposes no rule on later writes. [A16-NEW, A16-DATABASE]

## A staged rollout

1. **Expand while preserving rollback.** Add the nullable column and retain the original `email` and its existing meaning. Introduce compatible dual writers, but keep the new unambiguous-login assumption disabled until the required invariants hold. If ambiguous lookups must be exposed earlier, they need explicit handling that cannot silently select an owner.

2. **Reconcile identities through an ownership policy.** Group accounts by `lowercase(email)`, including rows whose normalized field is null or stale. Accounts 1 and 2, and later 4 and 5, require an ownership decision. The product must decide how to verify ownership, whether a verified merge is allowed, how purchases and account identifiers survive it, and how different owners obtain distinct login identities. Choosing the lowest ID, deleting a row, or merging histories because strings match is not justified by this packet. Version 2 has no verification workflow to make that decision. [A16-OLD, A16-NEW, A16-RACE]

3. **Transition every identity writer.** Account creation and email changes must eventually go through code that writes both fields atomically and enforces the agreed identity policy. Include old instances, background jobs, imports, and rollback paths. During an unrestricted mixed fleet, continue reconciliation and treat any nullable unique index as only partial protection. If global case-insensitive uniqueness is needed before old binaries disappear, their identity writes must be stopped or routed through a compatible enforcing path, or an actual database enforcement mechanism must be introduced. None exists in the supplied setup. Unrestricted version 1 writes and a global normalized-uniqueness guarantee cannot coexist here.

4. **Close the write gap and verify.** Once old identity writes are fenced off and in-flight writes have completed, finish backfill and reconciliation against the current data. Verify zero nulls, `email_norm = lowercase(email)` for every account, and no duplicate normalized identities. Confirm that every remaining writer preserves those properties and that concurrent conflicting creates or changes are rejected. A scan while bypass writers remain active is insufficient evidence. Build or validate the unique index and enforce `NOT NULL` only after these conditions hold. `NOT NULL` alone does not prove that a stored value is correctly normalized.

5. **Contract after readers and rollback have moved.** Activate the new login behavior after verification. Remove or rename the old representation only when all deployed readers and writers use the intended schema, old-version jobs and instances are gone, ownership reconciliation is complete, and the supported rollback target no longer requires the original representation. Coordinate any rename with code that still names `email_norm`; retain original address data separately if the product still needs it.

The decisive evidence is both a clean data check and control over future writes. Until both are established, a successful backfill or index build cannot justify treating normalized identity as globally enforced.
