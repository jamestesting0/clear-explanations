The caller receives `"ok"`, `"recovered"`, and `"forced"` respectively; **none of the three modes raises to the caller in the shown program**. The parse error is suppressed by the context manager. The lookup error leaves the context manager but is then suppressed by the outer `finally` return.

## Exact results and event order

Running [A05-CODE] on Python 3.12.14 produced:

```text

parse recovered open,body,rollback-value,close,after-with,outer-finally

```

### `clean`: the pending return survives both exits

Entering `with transaction()` advances the generator to `yield`, logging `open`. The body logs `body` and starts returning `"ok"`.

A return from inside a `with` block still invokes the context manager’s exit behavior. Since no exception is leaving the body, `contextmanager` resumes the generator normally after `yield`. The generator’s `try` completed without an exception, so its `else` logs `commit`, and its `finally` logs `close`.

The pending return then passes through the outer `finally`, which logs `outer-finally` and does not override it for this mode. The caller receives `"ok"`. `after-with` is skipped because the function is returning; normal context-manager exit does not cancel that return.

### `parse`: the generator suppresses `ValueError`

The body logs `body` and raises `ValueError("bad input")`. The context-manager machinery throws that exception into the suspended generator at `yield`.

The generator catches it in `except ValueError`, logs `rollback-value`, and **finishes without re-raising it**. Its `finally` logs `close`. For a generator-based context manager, handling the injected exception and then terminating normally tells the `with` machinery that the exception was suppressed.

This is the exact suppression point: normal generator completion after the `except ValueError` handler, interpreted by `contextmanager` as successful handling. Logging an exception does not implicitly re-raise it.

Because the body’s exception was suppressed and no return was reached inside that body, execution continues after the `with`: it logs `after-with` and returns `"recovered"`. The outer `finally` logs its event and preserves that return.

### `lookup`: the outer `finally` suppresses `KeyError`

`KeyError("missing")` is also thrown into the generator at `yield`, but `except ValueError` does not match it. The generator runs `finally`, logging `close`, and lets the original `KeyError` escape. There is no rollback event on this path.

The `with` therefore does not suppress the error, and `after-with` is skipped. While the function is unwinding toward the caller, its outer `finally` logs `outer-finally` and executes:

```python
return "forced"
```

That return replaces the pending exception. This is the exact suppression point for `KeyError`.

## What the claims get wrong

The author’s two explanations are incorrect for different reasons. A generator context manager must explicitly re-raise an exception it wants to remain visible; the `with` statement does not automatically revive a handled exception. Separately, a pending exception can still be replaced during `finally`. Selecting a propagation path does not make that path irrevocable.

The reviewer is also wrong. Removing only the outer `return "forced"` would leave:

| `clean` | `"ok"` |
| `parse` | `"recovered"` |

A successful return from a `with` body uses normal context-manager exit, which is precisely why the generator’s `else` executes.

Seeing `close` proves only that execution reached that event append in the generator’s `finally`. In this fixture it does not establish a real resource operation, and it proves neither that rollback occurred nor that the original failure reached the caller. ## Small refactor for the stated ordinary exceptions

Catch the ordinary operation exceptions, perform rollback, and re-raise. Keep unconditional cleanup in `finally`, but remove its overriding return and remove the recovery path:

```python
@contextmanager
def transaction():
    events.append("open")
    try:
        yield
    except Exception:
        events.append("rollback")
        raise
    else:
        events.append("commit")
    finally:
        events.append("close")

def work(mode):
    try:
        with transaction():
            events.append("body")
            if mode == "parse":
                raise ValueError("bad input")
            if mode == "lookup":
                raise KeyError("missing")
            return "ok"
    finally:
        events.append("outer-finally")
```

Assuming these event operations complete normally, the outcomes become:

| Mode | Caller observes | Events |
| --- | --- | --- |
| `clean` | `"ok"` | `open,body,commit,close,outer-finally` |
| `parse` | Original `ValueError` | `open,body,rollback,close,outer-finally` |
| `lookup` | Original `KeyError` | `open,body,rollback,close,outer-finally` |

The bare `raise` re-raises the active exception, preserving its object, type, and traceback. It does not invent a replacement “transaction failed” exception. Catching `Exception` here covers both specified failures, but it does not suppress them: the handler performs its action and then propagates them.

`finally` is useful for arranging cleanup on both normal and exceptional exits. The dangerous operation here was **returning from it**, which can replace an earlier return or hide an operation or cleanup exception.

## If cleanup can also fail

The small refactor assumes the event appends succeed. Replacing them with fallible rollback or close operations introduces an additional policy decision. If rollback raises before the bare `raise`, or close raises while the operation error is propagating, the cleanup error can become the exception delivered to the caller. Python normally retains the earlier exception through exception chaining, but the top-level type then changes, which matters to the retry policy.

A more complete design should attempt required cleanup steps independently, retain each failure, and explicitly represent the combined outcome:

| Operation outcome | Cleanup outcome | Defined handling |
| --- | --- | --- |
| Succeeds | Succeeds | Return the successful value |
| Fails | Succeeds | Re-raise the original operation exception |
| Succeeds | Fails | Raise the cleanup error, or a group if several cleanup steps fail |
| Fails | Fails | Preserve the operation exception and every cleanup exception together |

On Python 3.11 or later, an `ExceptionGroup` can represent the last case while retaining the actual original exceptions as members. The same collection policy should cover a successful-completion action that fails followed by a failing close, and should still attempt close after a rollback failure. Merely putting one operation after another inside a handler would not guarantee that attempt.

An `ExceptionGroup` changes the outer exception type, so adopting it requires the caller to classify its members, for example with `except* ValueError` and `except* KeyError`. It would be misleading to claim that an unchanged `except ValueError` retry policy already handles that representation.

If keeping the original operation exception as the top-level exception is mandatory even when cleanup also fails, retain and report the cleanup exceptions through a separate explicit error record or reporting channel, then re-raise the original. That channel must make the cleanup failure observable; silently catching it would violate the requirement. The choice between grouped propagation and separate reporting is part of the interface contract.

This treatment covers the ordinary exceptions discussed here. It does not establish correct handling of cancellation, `KeyboardInterrupt`, `SystemExit`, or interpreter shutdown; those require a separate policy and analysis.
