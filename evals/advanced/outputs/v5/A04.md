The current query multiplies each order’s lines by its refunds before aggregating. It also removes customers without paid orders through the `WHERE` clause. Those are separate defects: preserving every customer or correcting the order count does not repair the monetary sums.

All monetary values below are **integer cents**.

## What the current query returns

Executing [A04-QUERY] against [A04-DATA] returns:

| name | paid_orders | gross | refunds | net |
| --- | ---: | ---: | ---: | ---: |
| Ada | 4 | 320 | 40 | 280 |
| Ben | 1 | 40 | `NULL` | 40 |

Cy is absent.

The crucial intermediate rows for Ada’s paid order 10 are:

| Order | Line amount | Refund amount |
| --- | ---: | ---: |
| 10 | 2 × 50 = 100 | 15 |
| 10 | 100 | 5 |
| 10 | 1 × 60 = 60 | 15 |
| 10 | 60 | 5 |

Each of the two lines matches each of the two independent refund records. The resulting grain—what one row represents—is **a line/refund pair within an order**. It is neither one order nor one line nor one refund.

Consequently:

- `COUNT(o.id)` counts four joined rows containing order 10, giving 4.
- Gross is `100 + 100 + 60 + 60 = 320`.
- Refunds are `15 + 5 + 15 + 5 = 40`.
- Net is `320 − 40 = 280`.

Ada’s cancelled order 11 is removed by the paid-status filter, so its 999-cent line does not contribute.

Ben’s order 20 has one line and no refunds. The refund `LEFT JOIN` preserves one row with a `NULL` refund value. Gross is 40, but `SUM(r.amount)` is `NULL` because it has no non-null input. The net expression alone replaces that null refund total with zero, giving 40.

Cy initially receives a null-filled row from the orders `LEFT JOIN`. However, `WHERE o.status = 'paid'` does not evaluate to true for that row, so it is discarded. A customer with only unpaid orders would also disappear.

## Correct business result

Counting paid orders and independently summing their child records gives:

| name | paid_orders | gross | refunds | net |
| --- | ---: | ---: | ---: | ---: |
| Ada | 1 | 160 | 20 | 140 |
| Ben | 1 | 40 | 0 | 40 |
| Cy | 0 | 0 | 0 | 0 |

These values follow directly from the definitions in [A04-CONTRACT]: Ada has one paid order with lines totaling `100 + 60` and refunds totaling `15 + 5`.

## A query with a safe grain

Aggregate each child table to one row per order **before joining the children together**:

```sql
WITH line_totals AS (
    SELECT order_id,
           SUM(quantity * unit_price) AS gross
    FROM line
    GROUP BY order_id
),
refund_totals AS (
    SELECT order_id,
           SUM(amount) AS refunds
    FROM refund
    GROUP BY order_id
),
paid_order_totals AS (
    SELECT o.id AS order_id,
           o.customer_id,
           COALESCE(l.gross, 0) AS gross,
           COALESCE(r.refunds, 0) AS refunds
    FROM orders o
    LEFT JOIN line_totals l ON l.order_id = o.id
    LEFT JOIN refund_totals r ON r.order_id = o.id
    WHERE o.status = 'paid'
)
SELECT c.name,
       COUNT(p.order_id) AS paid_orders,
       COALESCE(SUM(p.gross), 0) AS gross,
       COALESCE(SUM(p.refunds), 0) AS refunds,
       COALESCE(SUM(p.gross), 0)
           - COALESCE(SUM(p.refunds), 0) AS net
FROM customer c
LEFT JOIN paid_order_totals p ON p.customer_id = c.id
GROUP BY c.id, c.name
ORDER BY c.id;
```

I executed this rewrite against the supplied dataset; it produces the three correct rows above.

| Relation or stage | Grain |
| --- | --- |
| `customer` | One customer |
| `orders` | One order |
| `line` | One line record |
| `refund` | One refund record |
| `line_totals` | At most one row per `order_id` |
| `refund_totals` | At most one row per `order_id` |
| `paid_order_totals` | Exactly one row per paid order |
| Final join, before grouping | One row per paid order, or one null-filled row for a customer with none |
| Final output | One customer |

The two `GROUP BY order_id` operations make each child total unique on its join key. Because `orders.id` is unique, neither child-total join can duplicate an order. `COUNT(p.order_id)` therefore counts orders without needing `DISTINCT`.

Filtering inside `paid_order_totals` is safe: that relation intentionally contains only paid orders. The final query starts from all customers and has no later predicate that rejects customers without a matching paid order.

### Orders with no lines still count

A paid order with no lines remains in `paid_order_totals`, with gross zero. If it also has no refunds, its monetary totals are zero and it still contributes one to `paid_orders`.

If it has refunds but no lines, the stated formula gives zero gross minus those refunds, potentially a negative net. The query preserves that result rather than inventing a special rule. As a separate execution check, adding a paid order for Cy with no lines and a 7-cent refund produced `Cy, 1, 0, 7, -7`.

## Why the review proposals are insufficient

**Moving the status predicate into the orders `ON` clause repairs customer inclusion.** It prevents cancelled orders from joining while preserving a null-filled row for a customer with no paid orders. It does not change the line/refund multiplication for orders that do match.

**`COUNT(DISTINCT o.id)` repairs the count.** For Ada, four occurrences of order 10 become one distinct order. Both monetary sums still include duplicated contributions. Cy’s monetary totals also still need zero handling; fixing the count does not fix them.

**`SUM(DISTINCT ...)` deduplicates values, not business records.** It happens to recover Ada’s totals in this dataset because the distinct line amounts are 100 and 60, and the distinct refund amounts are 15 and 5. But two legitimate 50-cent lines must contribute 100, whereas `SUM(DISTINCT line_amount)` would contribute only 50. Equal unit prices alone do not necessarily imply equal extended amounts, because quantities can differ; whenever the calculated amounts are equal, the proposed sum would wrongly merge them. Identical refund amounts from different records or different orders are equally legitimate and would also be lost.

## Missing records, zero values, and `COALESCE`

An **absent refund** means no refund record exists. A **zero refund** means a record exists whose amount is zero. Both contribute zero money under this contract, but they are different facts if a later report needs refund counts or activity history.

For a customer with no paid orders, the final left join produces a null-filled row. `COUNT(p.order_id)` is zero because the order ID is null; `COUNT(*)` would incorrectly count that placeholder row. The sums have only null inputs, so outer `COALESCE(..., 0)` supplies the requested displayed zero.

`COALESCE` replaces a null result with a chosen value. It cannot restore customers already removed by `WHERE`, identify duplicated records, or correct an inflated non-null sum.

Finally, pre-aggregation is safe only while subsequent joins preserve its grain. Joining `paid_order_totals` to several tags or events per order before summing would repeat the order totals again. Aggregate that additional relation to a compatible key first, use an existence check when only filtering is needed, or compute its metric separately before combining results.
