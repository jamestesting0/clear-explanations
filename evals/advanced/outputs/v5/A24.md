The isolated path's complete-latency speedup is **1.43×**, with a theoretical limit of **1.67×** if its CPU stage takes no time. In the separate representative replay, mean response time **increases from 19 to 22.2 ms**, and the 95th percentile **increases from 100 to 150 ms**. The operating interval demonstrates 200 completed requests per second at that load; it does not establish maximum capacity.

## 1. The microbenchmark: only one stage becomes four times faster

Because the two stages are serial, their times add:

| Quantity | Calculation | Result |
| --- | --- | ---: |
| Original complete latency | `8 + 12` | 20 ms |
| Optimized CPU time | `8 / 4` | 2 ms |
| Optimized complete latency | `2 + 12` | 14 ms |
| Complete-latency speedup | `20 / 14` | **1.4286×** |
| Reduction in complete latency | `(20 − 14) / 20` | **30%** |

The unchanged database wait accounts for 60% of the original latency. Even an arbitrarily fast CPU stage leaves that entire 12 ms:

\[
\text{Limiting complete-latency speedup}=\frac{20}{12}
=\frac53\approx\boxed{1.67\times}.
\]

Thus the fourfold CPU improvement does not produce a fourfold improvement in complete latency. This calculation concerns the specified isolated path and cannot be applied to every request in the separate replay. [A24-MICRO]

## 2. The replay: mean wait and the slowest part of the distribution worsen

The requested mean gives each of the 1,000 requests equal weight. Because the counts stay fixed, endpoint weights are 90% fast and 10% slow:

\[
\bar t_{\text{before}}=\frac{900(10)+100(100)}{1000}
=\boxed{19\text{ ms}},
\]

\[
\bar t_{\text{after}}=\frac{900(8)+100(150)}{1000}
=\boxed{22.2\text{ ms}}.
\]

The mean increases by 3.2 ms, or:

\[
\frac{22.2-19}{19}\times100\%
\approx\boxed{16.84\%}.
\]

The first 900 sorted response times belong to the fast endpoint, and positions 901–1000 belong to the slow endpoint. The specified 950th value is therefore **100 ms before and 150 ms after**, a 50% increase in the 95th percentile. [A24-WORKLOAD]

The fact that 90% of requests improve does not determine the mean: the sizes of improvements and regressions matter. The fast requests save `900 × 2 = 1,800 ms` of accumulated response time, while the slow requests add `100 × 50 = 5,000 ms`. The net increase is `3,200 ms / 1,000 = 3.2 ms` per request.

The fast endpoint's benefit is nevertheless real: **10 → 8 ms is a 20% latency reduction, or a 1.25× speedup**, for 90% of this replay's requests. [A24-WORKLOAD]

## 3. Why the dashboard's averages answer different questions

### Averaging individual speedup ratios

The dashboard computes:

\[
0.9\left(\frac{10}{8}\right)+0.1\left(\frac{100}{150}\right)
=1.125+0.06667\approx\boxed{1.1917}.
\]

That is the mean of the requests' individual old/new ratios. It is not the ratio of their mean response times. Each ratio contributes equally even though the requests have different durations; a 2 ms saving on a short request and a 50 ms regression on a long request affect user wait very differently.

If “overall speedup” is intended to describe aggregate mean latency, the appropriate ratio is:

\[
\frac{\bar t_{\text{before}}}{\bar t_{\text{after}}}
=\frac{19}{22.2}\approx\boxed{0.856\times}.
\]

A value below one means that mean response time worsened. The dashboard's 1.1917 is a valid calculation of a different statistic, but its label invites an incorrect conclusion about mean user wait. [A24-DASHBOARD; A24-WORKLOAD]

### Averaging endpoint means equally

Equal endpoint weighting gives `(10 + 100) / 2 = 55 ms` before and `(8 + 150) / 2 = 79 ms` after. Those figures treat the two endpoints as equally important, equivalent here to a hypothetical **50/50 request mix**. They do not describe the observed **90/10 request mix**. An endpoint-level summary can be useful, but it must be labeled accordingly; mean user wait requires weighting endpoint means by their request counts.

## 4. The operating interval: concurrency is not capacity

Convert the observed mean time to seconds: `22.2 ms = 0.0222 s`. Using the supplied accounting identity:

\[
L=\lambda W
=(200\text{ requests/s})(0.0222\text{ s})
=\boxed{4.44\text{ requests}}.
\]

So **4.44 requests are in the system on average**, including requests executing or waiting. An average can be fractional even though the instantaneous number of requests is an integer. This does not tell us how many CPU cores or database connections are busy. [A24-OPERATIONS]

The stable interval shows that this deployment sustained the observed 200 requests/s with the stated mean time and no net buildup during that interval. It does not show how much additional load it could handle, which resource would limit it, or whether 200 requests/s was already near its maximum.

Taking the inverse mean time gives `1 / 0.0222 ≈ 45.05 requests/s`. That comparison is meaningful for a **single sequential client with one request outstanding, no think time, and a mean response time of 22.2 ms under that client's workload**. It is not a ceiling for a deployment handling concurrent requests. The observed 200 requests/s is consistent with 4.44 requests being present on average. Moreover, changing concurrency can change waiting time, so the observed mean need not remain 22.2 ms in a sequential-client experiment.

The replay's accumulated request response times likewise cannot be treated as its elapsed wall-clock duration if requests overlap. Complete response times already include replay waiting; no microbenchmark stage times should be added to them.

## 5. Evidence needed for the throughput claim

Measure **before-and-after sustainable throughput under increasing load** on comparable deployments, keeping hardware, configuration, data, payloads, and representative endpoint mix controlled. Record achieved completions per second together with offered load, concurrency, queue growth, mean and percentile latency, errors, timeouts, and dropped work. Use steady measurement intervals and repeated runs, and define any latency or reliability requirement that capacity must satisfy.

Resource measurements—CPU service demand and core capacity, database demand and connection limits, and utilization—would help explain the eventual bottleneck. A faster CPU stage can improve capacity when CPU capacity limits completion rate, but another resource can constrain the benefit. None of that follows from the isolated latency calculation alone. [A24-MICRO; A24-OPERATIONS]

The supported claim is therefore specific: the optimization improves the isolated path and the fast endpoint, while the representative replay shows worse mean and 95th-percentile wait. A fourfold increase in saturation throughput remains untested.
