**The current implementation ends with value 7.** Its token check stops an older leader from overwriting a newer token already seen by storage, but it does not stop commands within the same token from arriving out of order.

### What each arrival does

Initially, X has `max_token=40` and `value=0`. Storage accepts any token greater than or equal to its remembered token and ignores sequence numbers. [A07-STORAGE]

| Arrival | Command: token, sequence, value | Decision | State afterward |
|---|---|---|---|
| 1 | A: 41, 1, 6 | Accept: 41 > 40 | Token 41, value 6 |
| 2 | B: 42, 2, 8 | Accept: 42 > 41 | Token 42, value 8 |
| 3 | A: 41, 2, 9 | Reject: 41 < 42 | Token 42, value 8 |
| 4 | B: 42, 1, 7 | Accept: 42 = 42 | Token 42, value 7 |

These decisions follow directly from the supplied acceptance rule and arrival order. [A07-STORAGE; A07-ARRIVALS]

The first engineer is wrong because lease expiration does not retract a request already in transit. A can send while its lease is valid and its message can arrive after B has acquired a newer lease. The lock service can grant nonoverlapping leases while storage still receives that delayed message. [A07-LEASE]

The second engineer correctly identifies protection against arrival 3, but overlooks arrival 4. B’s sequence 1 is older than B’s sequence 2 even though both carry token 42. The third proposal—rejecting every equal token—would prevent that overwrite, but would also reject legitimate subsequent updates from the same leader. [A07-REVIEW; A07-ARRIVALS]

### Compare the token and sequence together

Store a **revision**, meaning the pair `(token, sequence)`, with the value. Compare tokens first; compare sequences only when the tokens match. Thus every command with token 42 ranks above every command with token 41, while `(42,2)` ranks above `(42,1)`.

For each resource, perform the following decision and any resulting update as one atomic operation:

| Incoming revision compared with stored revision | Action |
|---|---|
| Greater | Apply the replacement value; store the revision and command payload; report one new change. |
| Equal, identical payload | Leave state unchanged; return an “already applied” result identifying the same command. |
| Equal, different payload | Reject as a conflicting reuse of a command revision; leave state unchanged. |
| Smaller | Reject as superseded; leave state unchanged and do not report a new change. |

Payload comparison should cover the command’s actual contents, so an equal revision cannot silently acquire a different meaning. Retries must retain their original token, sequence, and payload, as the exercise specifies. [A07-ARRIVALS]

Under this rule, arrivals 1 and 2 apply; arrivals 3 and 4 are superseded. The final revision is `(42,2)` and the final value is **8**. Applying sequence 2 without first receiving sequence 1 is valid here because values are complete replacements and the stated business rule gives larger sequences precedence. [A07-ARRIVALS]

A retry of the current revision receives “already applied.” A retry of a previously applied revision that has since been superseded receives “superseded”; neither changes the value nor counts as a new business change. If callers also need the original success response for every historical command, retain a durable command-result history. Remembering only the greatest revision cannot distinguish an older command that once applied from an older command that never arrived.

### Where the check must happen

The remembered revision must live in the storage system that enforces the write, durably alongside the value. Every write path must share the same atomic comparison and update. Replicas or failover servers must preserve that ordering; a restart must not forget revision 42 and accept revision 41 again.

A client-side record cannot stop another client’s delayed request. Comparing client clocks does not encode the required token-and-sequence order, and checking a lease before sending leaves time for the request to be delayed after the check. The storage check protects the point where the effect actually happens. [A07-LEASE; A07-STORAGE]

The correction establishes that **accepted revisions never decrease**, and that an identical retry creates no new business change. It does not prove that every accepted writer still holds a valid lease: before storage sees token 42, it can still accept an eligible token-41 request. If exclusion must begin exactly when a new lease is granted, the lease handover needs additional coordination with storage.

Nor does the rule deliver messages, recover lost responses, or guarantee progress through a long network partition. It can preserve ordering while no useful writes complete; eventual completion still requires communication and retries to succeed.
