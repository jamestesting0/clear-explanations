`copied` freezes the list’s membership, but it still contains references to mutable `StringBuilder` objects. `wrapped` does less: it blocks edits through that wrapper while continuing to show the live `window`. Neither satisfies the full snapshot contract. [A03-CODE, A03-INTENT]

## The four structures

Immediately after construction, all four lists expose some of the same builder objects:

| Variable | List structure | Initial elements |
| --- | --- | --- |
| `base` | Mutable owning list | Builders A, B, C, D |
| `window` | View of positions 1 through 2 in `base` | The same B and C builders |
| `copied` | Unmodifiable list with membership captured at `copyOf` | The same B and C builders |
| `wrapped` | Unmodifiable wrapper around `window` | Whatever `window` currently exposes |

A reference points to an object. Copying a list of references does not copy the objects themselves. That distinction explains the two different kinds of mutation.

### Replacing B changes a list entry

```java
window.set(0, new StringBuilder("B2"));
```

This puts a **new builder** into the backing list’s position 1. Consequently, `base`, `window`, and `wrapped` expose B2 there. `copied` retains its reference to the original B builder, which has not changed.

This replacement does not change the list’s size and does not structurally invalidate `window`. It changes which object occupies an existing position.

### Appending to C changes a shared object

```java
base.get(2).append("!");
```

This finds the existing C builder and changes its contents. It does not replace a list entry. `copied` still refers to that very same builder, as do `base`, `window`, and `wrapped`, so all expose `C!`.

The first printed lines are therefore:

```text
base=[A, B2, C!, D]
copied=[B, C!]
wrapped=[B2, C!]
```

These match the supplied OpenJDK 21 observation. [A03-OBSERVATION]

## What the successful and failing operations establish

`copied.add(...)` throws `UnsupportedOperationException`, producing:

```text
copied-add=blocked
```

That establishes that the attempted list modification is unsupported. It does not establish that the list’s element objects are immutable. List-level operations such as adding, removing, or replacing entries are separate from operations such as `copied.get(1).append("?")`, which would mutate the shared builder directly. The supplied `copyOf` specification explicitly preserves this distinction. [A03-API]

Next, `base.add(...)` changes the backing list’s structure outside `window`. Although the added E is beyond the original window’s range, the documented condition still applies: the semantics of that existing `subList` are now undefined. [A03-API]

In the supplied OpenJDK 21 run, `window.size()` detects the incompatible structural change and throws `ConcurrentModificationException`, giving:

```text
window-size=invalidated
```

“Concurrent” in the exception’s name does not establish a second thread. The single thread shown changed the backing list in a way the view did not accommodate. The observed exception is useful evidence of this implementation’s detection, but the API boundary is broader: after that modification, do not rely on any particular later access succeeding or throwing this exact exception. `wrapped` delegates to the same invalidated view, so wrapping it does not repair that boundary.

`copied` has independent list membership, so changing `base`’s structure does not invalidate it. It still contains its original references to B and the modified C builder:

```text
copied-after=[B, C!]
```

This is structural independence, not a deep snapshot of element contents.

## A return type that meets the contract

Return an unmodifiable `List<String>` and convert each builder to a string **while constructing the report**:

```java
static List<String> snapshot(List<StringBuilder> labels) {
    var values = new ArrayList<String>(labels.size());
    for (StringBuilder label : labels) {
        values.add(label.toString());
    }
    return List.copyOf(values);
}
```

Call this with a valid current list or view, before an outside structural modification invalidates that view. At the original publication point, `snapshot(window)` captures `[B, C]`. Later replacement of B with B2, appending to C, or adding E to `base` cannot change that report.

Both parts of the construction are necessary:

- `toString()` captures each builder’s current text as an immutable string value. The library can continue modifying the builders afterward.
- `List.copyOf(values)` makes the returned list unmodifiable and independent of later changes to the temporary list’s membership.

Calling `List.copyOf` twice would not perform the first step. Neither call converts builders into immutable values or recursively copies their state.

For this single-threaded example, a safe contract is:

> The report is an unmodifiable list of immutable string values captured when the report is constructed. Subsequent edits to the source list or its builders do not change the report.

The requested “instant” is meaningful here because no source mutation occurs during construction. If the library later allows other threads to mutate labels while a report is being captured, it must add a consistent capture mechanism, such as appropriate synchronization, to preserve the stronger claim that the whole report represents one instant.

For more complex exported elements, an unmodifiable outer list alone still would not justify calling the complete report immutable. The library would need a defined policy for every reachable mutable component: convert it to an immutable value or copy it deeply enough that later source edits cannot affect the report. The policy must also prevent callers from modifying the captured values if the public contract promises a read-only report throughout its lifetime.
