At both `after-gather` checkpoints, A is still pending and its 30 units remain reserved. B’s failure makes `gather` raise, but does not cancel A or wait for A to release its reservation. The second run restores all 100 available units because it explicitly cancels **and then awaits** A.

## Exact output and event order

Running the supplied program on Python 3.12.14 produced:

```text
after-gather {'available': 70, 'committed': 0} False False
final {'available': 70, 'committed': 30}
trace A:reserved,B:reserved,B:released,B:cleanup,caller:caught,A:committed,A:cleanup
after-gather {'available': 70, 'committed': 0} False False
final {'available': 100, 'committed': 0}
trace A:reserved,B:reserved,B:released,B:cleanup,caller:caught,A:released,A:cleanup,caller:cancel-observed
```

Both runs begin with the same sequence in [A01-CODE]:

1. A subtracts 30, logs `A:reserved`, and suspends at the closed gate. Availability is 70.
2. B subtracts 20, logs `B:reserved`, and suspends at `sleep(0)`. Availability is 50.
3. B resumes and raises `ValueError`. Its handler restores 20 and logs `B:released`; its `finally` logs `B:cleanup`. Availability is now 70.
4. `gather` propagates B’s exception. The caller logs `caller:caught` and prints the first checkpoint. A is neither done nor cancelled, so both Boolean values are `False`.

The branches then differ:

- **`scenario(False)`:** `gate.set()` lets A continue. A adds 30 to `committed`, logs `A:committed`, and runs its `finally`. Awaiting A completes normally. Committing does not add anything back to `available`, so the final quantities are 70 available and 30 committed.
- **`scenario(True)`:** `a.cancel()` requests cancellation. When A resumes at `gate.wait()`, `CancelledError` is raised there. A’s `except BaseException` restores its 30 units and re-raises; its `finally` logs cleanup. Only after that does `await a` raise `CancelledError` to the caller, which records `caller:cancel-observed`. The final quantities are 100 available and 0 committed.

At either first checkpoint, `available + committed` is 70 because A still holds an uncommitted reservation of 30. At both final checkpoints the sum is 100, but it describes different outcomes: a completed commitment in the first run and a released reservation in the second. These are quantities, not success flags.

## What each mechanism guarantees

**`gather` propagates the first failure here; it does not establish a rollback boundary.** With its default `return_exceptions=False`, another task’s ordinary exception does not automatically cancel unfinished siblings. B’s own handlers finish before B becomes a failed task, but A remains active. Thus the first reviewer’s prediction of 100 available units at the exception handler is wrong.

**Cancellation runs normal exception unwinding.** It does not skip handlers and `finally`, so the second reviewer’s explanation is also wrong. Calling `cancel()` alone does not prove cleanup has finished. Awaiting the explicitly cancelled task provides the completion boundary in this example: A’s release and cleanup happen before the caller observes its cancellation.

Short experiments that end immediately can conceal this distinction. When `asyncio.run` shuts down its loop, it cancels remaining tasks. That later shutdown behavior can look like cancellation caused by `gather`. Here the enclosing coroutine remains alive and deliberately determines A’s fate.

**Changing `BaseException` to `Exception` would break this cancellation cleanup.** In Python 3.12, `asyncio.CancelledError` is outside the `Exception` hierarchy. B’s `ValueError` would still trigger release, but A’s cancellation would bypass the release handler. Its `finally` would still log `A:cleanup`; the second run would finish with 70 available and 0 committed. The missing 30 would be a leaked reservation. A cleanup log is therefore not evidence that the release code ran.

## A concrete group boundary

Use a coordinator that owns every participant, waits for them to finish, and emits participant responses only after the group outcome is known. Within this example, a structure such as this supplies that lifetime boundary:

```python
async def run_group():
    async with asyncio.TaskGroup() as group:
        tasks = [
            group.create_task(reserve("A", 30)),
            group.create_task(reserve("B", 20)),
        ]
    # Reached only when the group completed successfully.
    return [task.result() for task in tasks]
```

Here `reserve` refers to the existing worker in its enclosing scope. With the gate closed and B failing as shown, `TaskGroup` cancels A and waits for its release and finalizer before exiting with an `ExceptionGroup`. Handle that group outside the `async with` block; a plain `except ValueError` is not the corresponding handler for an `ExceptionGroup`. No worker should independently send a success response before the coordinator’s decision.

The worker also needs a clear ownership rule: release a reservation on every unsuccessful exit **only while it remains uncommitted**. A `finally` block can enforce that rule using explicit reservation and commitment state, without swallowing the exception. If release becomes asynchronous or fallible, its completion, further cancellation, and failure need their own recovery policy. Waiting for a task proves it ended; it does not by itself prove a fallible release succeeded.

## Where external transfers change the problem

`TaskGroup` coordinates task completion; it does not make transfers atomic. A sibling can commit before another fails, and cancellation cannot undo that completed external effect. Under the stated requirement, retain that commitment, release the remaining uncommitted reservations, and report the group failure without sending participant success responses.

A production design therefore needs a durable record of each participant’s state and a way to resolve uncertain outcomes. For example, a timed-out transfer may already have succeeded externally; blindly retrying or treating it as uncommitted can duplicate or reverse money movement. Idempotency keys, transfer-status checks, and reconciliation can address those cases, subject to the external service’s actual guarantees.

Separating reservation/preparation from commitment can prevent commitments when preparation already failed. It still cannot guarantee all-or-nothing external commits if a failure occurs during the commitment phase. That stronger property requires support from the persistence and transfer protocols. The toy’s synchronous counter update proves neither that support nor the reliability of real cleanup.
