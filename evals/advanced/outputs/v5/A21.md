The required invoice total is **1.01**, allocated as **34 cents to line 10, 34 cents to line 20, and 33 cents to line 30**. Whole-line refunds must use those stored allocations. Exact decimal arithmetic preserves the inputs, but it does not decide when to round, how to allocate a remainder, or what to refund. [A21-POLICY]

## What the printed results mean

The code produces:

```text
line-rounded 1.02
invoice-rounded 1.01
float-constructor 1.00
text-constructor 1.01
half-up 0.33
half-even 0.32
binary-round 2.67
```

Each result exposes a different choice or representation issue. [A21-CODE]

| Result | Explanation |
| --- | --- |
| `line-rounded 1.02` | Each exact `0.335` is halfway between `0.33` and `0.34`. Half-up rounds it to `0.34`; three such amounts total `1.02`. |
| `invoice-rounded 1.01` | Adding the raw amounts first gives exactly `1.005`. Half-up then rounds this single total to `1.01`. |
| `float-constructor 1.00` | The literal `1.005` becomes a binary floating-point number before `Decimal` receives it. Its value is slightly below exact `1.005`, approximately `1.0049999999999998934`. `Decimal` preserves that existing value, which rounds to `1.00`. |
| `text-constructor 1.01` | The string `"1.005"` supplies the exact decimal value directly. It is an exact halfway case, so half-up gives `1.01`. |
| `half-up 0.33` | Exact `0.325` is halfway between `0.32` and `0.33`; half-up chooses `0.33`. |
| `half-even 0.32` | At that same tie, half-even chooses the result whose last retained digit is even: `0.32`. |
| `binary-round 2.67` | The binary floating-point value for `2.675` is slightly below the decimal midpoint between `2.67` and `2.68`, so this call returns `2.67`. It does not demonstrate a tie being rounded downward. |

Python's built-in float rounding uses ties-to-even for actual halfway cases; for example, `round(3.5)` is `4`. The key distinction is whether the value being rounded really is halfway. Likewise, half-even and half-up differ specifically at some ties, regardless of whether the final output has two decimal places.

Thus `Decimal(1.005)` and `Decimal("1.005")` are not equivalent: the first converts an already approximated binary value, while the second reads exact decimal text. A tiny representation difference can change the displayed result by a whole cent when it crosses a rounding boundary. The number of displayed decimal places does not prevent that.

## Where rounding and allocation belong

For this invoice, the contract requires the following sequence:

1. Read the decimal text exactly and calculate the raw amounts without intermediate cent rounding.
2. Add the raw amounts: `0.335 + 0.335 + 0.335 = 1.005`.
3. Round that invoice total once using half-up: `1.005 → 1.01`, or **101 cents**.
4. Allocate those 101 cents to the lines using the specified remainder rule. [A21-POLICY]

Each raw line is `33.5` cents. Its floor—the greatest integer no larger than that amount—is 33 cents, with a remainder of 0.5 cent. The floors sum to 99 cents, leaving `101 − 99 = 2` cents to allocate.

| Line identifier | Raw cents | Initial floor | Fractional remainder | Extra cent | Stored cents |
| --- | ---: | ---: | ---: | ---: | ---: |
| 10 | 33.5 | 33 | 0.5 | 1 | **34** |
| 20 | 33.5 | 33 | 0.5 | 1 | **34** |
| 30 | 33.5 | 33 | 0.5 | 0 | **33** |
| **Total** | **100.5** | **99** | | **2** | **101** |

All remainders are equal, so ascending identifiers give the extra cents to lines 10 and 20. These stored amounts are allocations of the rounded invoice total; they need not all equal independently rounded raw line amounts.

The old policy and the required policy disagree even with exact arithmetic because rounding does not generally commute with addition: rounding each input and then adding can differ from adding first and rounding once. Here, requiring all three lines to round independently to 34 cents requires a total of 102 cents. Requiring the invoice-level result requires 101 cents. Both requirements cannot hold for this invoice. [A21-INVOICE; A21-POLICY]

## Refunds must preserve the original allocation

The draft refund repair is incomplete. Independently rounding each refunded raw amount still produces three refunds of 34 cents, totaling **102 cents against a 101-cent charge**. The discrepancy returns through the refund calculation. [A21-INVOICE]

Persist the original invoice total and each line's allocated integer cents, tied to its identifier. Record which lines have been refunded, and refund each whole line using its stored amount exactly once. Do not rerun allocation on the remaining lines or reconstruct refunds from raw amounts.

For example, refunding line 30 returns 33 cents and leaves 68 cents; refunding line 10 then returns 34 cents and leaves 34; refunding line 20 returns the final 34. Any order of distinct whole-line refunds satisfies:

`remaining charge = 101 − sum(refunded stored cents) = sum(unrefunded stored cents)`.

The display-only repair also fails: storing three 34-cent lines leaves a 102-cent ledger, whatever the receipt displays. Because reconciliation and refunds use stored values, the actual allocation must be corrected, not merely its presentation. [A21-REVIEW]

For larger calculations, sufficient decimal precision must also be maintained through the raw arithmetic; choosing `Decimal` alone does not guarantee that every possible calculation is exact.

## Extensions that need an explicit policy

For **negative or mixed-sign amounts**, specify how credits and reversals are allocated, how signed remainders are handled, and how ties preserve the intended total. `ROUND_HALF_UP` itself rounds negative halfway cases away from zero, but whether that and an extension of this positive allocation procedure meet the intended credit policy must be decided. An exact reversal should be defined against the original stored allocation if it must undo that charge exactly.

For **partial-line refunds**, specify what fraction is refundable, whether the basis is the stored allocation or another quantity, how fractional cents and ties are handled across successive partial refunds, and who receives any final remainder. Track cumulative refunded cents so splitting one line into several refunds cannot create extra money; a complete refund of the line should reconcile to its original allocated cents. Those rules are not supplied by the positive whole-line contract. [A21-POLICY]
