The current running total advances by **timestamp peer group**, so both events at timestamp 20 include both deltas. Its `LAST_VALUE` returns the last status in that same growing frame, not the final status of the whole reporting population.

## What the current windows calculate

With `ORDER BY ts` and the supplied default `RANGE` frame, the frame includes all earlier timestamps and every row tied at the current timestamp. [A20-FRAMES]

| Current row ID | IDs included in its frame | `running_total` | `LAST_VALUE(status)` |
| --- | --- | --- | --- |
| 1 | 1 | `5` | `open` |
| 2 | 1, 2, 3 | `5 + 7 - 2 = 10` | Last status among the timestamp-20 peers |
| 3 | 1, 2, 3 | `5 + 7 - 2 = 10` | Same last peer status |
| 4 | 1, 2, 3, 4 | `5 + 7 - 2 - 1 = 9` | `closed` |

This explains the observed `5,10,10,9`. Timestamp 20's frame contains both `review` and `paid`, but the window specifies no ordering between those tied rows. The local result of `paid` means it was last in that run's peer ordering; the query does not guarantee that choice over `review`. Both peers share the frame, so both display its last status. The sum `10` is invariant to the order of these supplied integer deltas. [A20-DATA, A20-QUERY, A20-OBSERVATION]

There are three distinct status meanings here:

- The plain `status` column belongs to the current event: `review` for ID 2 and `paid` for ID 3.
- The current `LAST_VALUE` reaches the last row of the current timestamp group, including tied rows beyond the current event.
- The required `final_status` belongs to the last event in the entire selected reporting population, with ties resolved by ID.

`LAST_VALUE` gets its boundary from its frame. The current frame ends at the current peer group, so timestamp 10 sees `open` rather than the later `closed`.

## Correct query for the report through timestamp 20

```sql
SELECT id, ts, status,
       SUM(delta) OVER (
           PARTITION BY account
           ORDER BY ts, id
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_total,
       LAST_VALUE(status) OVER (
           PARTITION BY account
           ORDER BY ts, id
           ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
       ) AS final_status
FROM event
WHERE ts <= 20
ORDER BY ts, id;
```

The result is:

| `id` | `ts` | `status` | `running_total` | `final_status` |
| --- | --- | --- | --- | --- |
| 1 | 10 | `open` | 5 | `paid` |
| 2 | 20 | `review` | 12 | `paid` |
| 3 | 20 | `paid` | 10 | `paid` |

Each part has a separate job:

- **Selected population:** `WHERE ts <= 20` in the same query block removes ID 4 before the windows are evaluated.
- **Account boundary:** `PARTITION BY account` keeps each account's calculations separate.
- **Logical event order:** `ORDER BY ts, id` inside each window implements the business tie-break. ID 2 precedes ID 3.
- **Running frame:** `ROWS ... CURRENT ROW` includes events through the current event, producing `5`, then `12`, then `10`.
- **Final-status frame:** `... UNBOUNDED FOLLOWING` extends through the end of the selected account population on every row. That last event is ID 3, with status `paid`.
- **Presentation:** the outer `ORDER BY ts, id` sorts the finished output. It does not define either window's calculation.

These choices implement the ordering and population requirements in [A20-CONTRACT].

## Filtering before versus after the windows

An outer filter removes already calculated output rows; it does not remove those rows from the population used by an inner window calculation.

For this exact cutoff, the original growing frames of IDs 1–3 already exclude the later timestamp-30 event. Thus wrapping the **current** query in an outer `WHERE ts <= 20` happens to retain the same `5,10,10` totals and the same frame-limited statuses as filtering first. The filter does not repair either the peer-group running total or the meaning of `final_status`.

The difference becomes decisive when the final-status frame is corrected to cover the whole partition. If that window runs over all four events and is only then filtered outside, every displayed row still says `closed`: ID 4 contributed to the calculation before being hidden. Filtering first instead makes ID 3 the last eligible event and gives `paid` on every row. Showing the same three rows does not imply calculating over the same population.

With the corrected running frame, filtering out only later events still leaves the earlier balances `5,12,10` unchanged. That is specific to this prefix cutoff; removing earlier contributing events could change running balances too. The contract requires choosing the population first, rather than relying on a particular window being unaffected by hidden rows.

## The other proposed repairs

**Adding `id` only to the outer ordering does nothing here:** it is already present in [A20-QUERY]. Even if it were absent, adding it there would only stabilize presentation. The tie-break belongs inside each window that needs it. Adding it inside would make the growing `LAST_VALUE` deterministic, but would still not make that frame cover the whole partition.

**Removing window ordering gives a partition total, not a running balance.** The whole-account sum is `9` on every row for the unfiltered population, or `10` on every row after selecting `ts <= 20`. Neither represents applying events one at a time. A running balance needs its event order and its advancing frame; a repeated final status needs a different frame over the same deliberately selected population.
