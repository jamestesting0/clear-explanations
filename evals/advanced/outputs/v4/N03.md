**JWT is not a replacement for OAuth.** JWT describes a token's format; OAuth describes how an application obtains and uses permission to access a service. They can work together.

| | JWT | OAuth 2.0 |
| --- | --- | --- |
| What it is | A format called JSON Web Token | A framework for granting limited access |
| What it defines | How to package statements such as who issued a token and when it expires | How an application obtains and uses access tokens |
| What it doesn't require | Using OAuth | Using JWTs |

For example, suppose a scheduling app needs permission to read your calendar:

1. Through an OAuth flow, the calendar service lets you authorize that access without giving the scheduling app your password.
2. The app receives an **access token**, a credential it presents when requesting calendar data.
3. That token might be a JWT containing information the calendar service can validate. It could also be an **opaque token**: a string whose meaning the service looks up.

JWTs are often signed, allowing a recipient to verify who signed the contents and that they haven't changed. Signing does **not** hide the contents; encryption is separate.

Choosing JWT as your token format still leaves you needing rules for requesting permission, issuing tokens, and checking access. OAuth supplies a framework for those interactions.
