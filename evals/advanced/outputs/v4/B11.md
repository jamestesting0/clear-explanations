The customer saw a deleted note’s content again, but the evidence shows that the mobile update was rejected and the primary server still held the deletion. “Resurrection” can therefore describe a real display or export problem without establishing that the authoritative server record was restored.

## What happened to each copy

An **epoch** is a server-controlled generation number for the note. A **revision** orders accepted edits within one generation. A **tombstone** is the retained record that the note has been deleted; it is not the note’s former content. Under version 2, deletion advances the epoch and removes the current content. A high revision within an earlier epoch cannot override that deletion. [B11-S1]

## Why the handler rejects this update

The handler loads the stored note under a lock shared with deletion. Its **first** condition compares the request’s epoch 4 with the stored epoch 5. They differ, so it returns **409 immediately**. It never reaches the tombstone check or `write_content`. The phone’s local revision 9 does not alter that branch. [B11-S2]

The next branch, returning **410**, would reject an update supplying the current epoch while the stored note is still a tombstone. The final write happens only after both checks pass, and the server chooses the next revision as `stored.revision + 1`.

Because the shared lock covers the read, checks, and write, deletion cannot slip between a successful check and the write. If an update completes first, a later deletion removes it; if deletion completes first, the stale update encounters the newer epoch. This reasoning applies to the supplied mobile handler and deletion path.

The old timestamp sketch does not change that behavior. It is an earlier proposal, whereas the current contract and deployed code explicitly use epochs. Appearing first in search results gives the sketch no authority over the implemented rule. [B11-S1–S2]

## Why the CSV is not proof of restoration

There are three distinct claims: content reappeared on screen, content appeared in an exported file, and content became the primary server’s current note again. The first two occurred; the third is not supported by this trace.

After 409, the interface preserves the rejected draft in a conflict tray so the user can recover their work. The ordinary synchronized list excludes it, but the current CSV exporter reads local state and includes both kinds of item without a status column. A title in that CSV consequently cannot distinguish committed content from an uncommitted draft. The behavior under discussion has not yet been changed. [B11-S3]

The supported incident conclusion is specific: **this mobile request did not restore N, and the direct server read at 09:42 found N deleted**. It does not certify every possible writer or every moment in the system’s history.

## What a broader guarantee would require

To claim deletion cannot be bypassed anywhere, engineers would need to identify and review every path capable of writing note content or changing epochs and tombstones. That includes any administrative imports, backup restores, migrations, or direct database access that actually exist, plus the authorized explicit restore operation. They would need evidence that the relevant checks and concurrency protections apply consistently, with tests or stronger verification of those invariants. The packet supplies no such review, and the primary-service contract explicitly does not cover every administrative import tool. An intentional, authorized restore must also be distinguished from a stale update bypassing deletion. [B11-S1, B11-S4]

For the product, retain the recoverable draft but clarify its status. Once the app confirms the server deletion, show “Deleted on server; your unsynced draft is saved separately,” with a copy action. Default CSV exports could exclude conflict drafts, or include explicit status and source columns with a clear option to export them. Either change would address the customer’s understandable impression without presenting a rejected draft as a saved server note.
