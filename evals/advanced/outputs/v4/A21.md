The required charge is **1.01**, allocated as **34 cents to line 10, 34 cents to line 20, and 33 cents to line 30**. Whole-line refunds must return those stored amounts. `Decimal` can preserve decimal inputs, but it does not choose where to round, which rounding rule to use, or how to allocate and refund cents.

## What the experiments print

```text
line-rounded 1.02
invoice-rounded 1.01
float-constructor 1.00
text-constructor 1.01
half-up 0.33
half-even 0.32
binary-round 2.67
```

These results expose three separate decisions: the value represented by an input, the rule for resolving a rounding tie, and the stage at which rounding occurs. [A21-CODE]

| Experiment | Why it produces that result |
| --- | --- |
| `line-rounded 1.02` | Each exact `0.335` rounds half-up to `0.34`; three such amounts total `1.02`. |
| `invoice-rounded 1.01` | The exact raw sum is `1.005`; rounding that sum once, half-up, gives `1.01`. |
| `float-constructor 1.00` | The binary floating-point value supplied to `Decimal` is slightly below exact `1.005`, so it rounds to `1.00`. |
| `text-constructor 1.01` | The text creates exact decimal `1.005`, which is a tie between `1.00` and `1.01`; half-up selects `1.01`. |
| `half-up 0.33` | Exact `0.325` is halfway between `0.32` and `0.33`; for this positive amount, half-up chooses the higher value. |
| `half-even 0.32` | At the same tie, half-even chooses the result whose last retained digit is even: the `2` in `0.32`. |
| `binary-round 2.67` | The binary value represented by `2.675` is slightly below the exact decimal midpoint, so the result is `2.67`. |

In `Decimal(1.005)`, Python first evaluates `1.005` as a binary floating-point number. Converting it to `Decimal` preserves that already approximated value:

```text
1.00499999999999989341858963598497211933135986328125
```

In `Decimal("1.005")`, the constructor receives decimal text and creates exact `1.005`. Removing the quotes changes the input type and therefore the value reaching the constructor; visual similarity of the source text does not make the two equivalent.

Likewise, the binary input for `round(2.675, 2)` is approximately `2.674999999999999822…`. Python's built-in `round` uses nearest rounding with ties to even; this result does **not** establish that ties always round downward. For exact decimal `2.675`, decimal half-even rounding to cents would give `2.68`.

A tiny representation difference can matter when it crosses a rounding boundary. The final display having only two decimal places does not prevent that difference from changing the last displayed cent. Conversely, the difference between half-up and half-even is a policy difference even for perfectly represented decimal inputs, as `0.325` demonstrates.

## Where rounding and allocation belong

The supplied contract requires the following calculation. [A21-POLICY]

1. Preserve the exact decimal inputs and calculate each raw line exactly.
2. Add the raw amounts: `0.335 + 0.335 + 0.335 = 1.005`.
3. Round the invoice total once, half-up: `1.005 → 1.01`, or **101 cents**.
4. Allocate those 101 cents using the specified floor-and-remainder procedure.

Each raw line is `33.5` cents. Its floor is 33 cents and its fractional remainder is 0.5 cent. The three floors total 99 cents, leaving `101 − 99 = 2` cents to distribute. All three remainders are equal, so ascending line identifier gives the extra cents to lines 10 and 20.

| Line identifier | Raw cents | Floor cents | Extra allocated cent | Stored cents |
| --- | ---: | ---: | ---: | ---: |
| 10 | 33.5 | 33 | 1 | **34** |
| 20 | 33.5 | 33 | 1 | **34** |
| 30 | 33.5 | 33 | 0 | **33** |
| Total | 100.5 | 99 | 2 | **101** |

There are two different tie rules here: half-up resolves the invoice's decimal rounding tie; ascending identifier resolves equal allocation remainders. The latter intentionally assigns different stored cents to otherwise equal raw amounts.

The old policy and the new policy disagree because rounding does not commute with addition:

\[
3\times\operatorname{round}(0.335)=1.02,
\qquad
\operatorname{round}(3\times0.335)=1.01.
\]

Both calculations use exact decimal arithmetic. They implement different policies. Requiring all three stored lines to equal their independently rounded 34-cent values forces a 102-cent sum, which cannot simultaneously equal the required 101-cent invoice. Changing the number type cannot remove this arithmetic contradiction.

## Refunds and stored values

The draft refund repair still rounds every raw `0.335` independently to 34 cents. Refunding all three lines would therefore return 102 cents against a 101-cent charge. It abandons the allocation at the moment that allocation is needed. [A21-INVOICE]

The display-only proposal has the same underlying defect: storing three 34-cent lines stores a total of 102 cents. Showing `1.01` on the receipt does not change the amounts used for refunds or reconciliation. [A21-REVIEW]

Store the original invoice total in integer cents and each line's original allocated integer cents, attached to its stable identifier. Keep the original allocation fixed. Record which lines have been refunded so that a repeated request cannot refund the same line again. Retaining the exact raw amounts and the applicable policy version also makes the calculation auditable.

For example, refunding lines 30, 10, and 20 in that order gives:

| Action | Refund cents | Cumulative refund cents | Remaining charged cents |
| --- | ---: | ---: | ---: |
| Refund line 30 | 33 | 33 | 68 |
| Refund line 10 | 34 | 67 | 34 |
| Refund line 20 | 34 | 101 | 0 |

For any set of refunded lines, the original 101 cents equals the refunded allocated cents plus the unrefunded allocated cents. Order does not affect that equality. Do not reallocate the remaining invoice or independently round a remaining raw subtotal after each refund: after refunding line 30, the remaining original allocations are 68 cents, even though the two remaining raw amounts sum to `0.670`.

For implementation, construct decimal values from the supplied text and use enough arithmetic precision to preserve the required exact calculations. Explicitly select half-up at the invoice rounding step; do not rely on a default rounding mode.

## What future cases would need specified

The supplied contract covers positive amounts and whole-line refunds. Extending it requires additional decisions:

- **Negative amounts:** Specify how positive and negative lines participate in allocation, whether they are allocated together or separately, how signed remainders and tie breaks work, and how credits or reversals relate to original allocations. Mathematical floor differs from truncation toward zero for negative numbers, so that distinction must be deliberate. If retaining `ROUND_HALF_UP`, negative exact ties round away from zero; that consequence must fit the intended signed-amount policy.
- **Partial-line refunds:** Specify how a line's original allocated cents are divided among quantities or portions, where partial amounts are rounded, and which portion receives any leftover cent. Track cumulative refunded cents and the remaining entitlement so that splitting a refund cannot create extra cents and a final full refund returns exactly the original allocation.
