The query has two independent problems: the final `WHERE` removes customers without paid orders, and joining both child tables before summing multiplies their monetary contributions. Fixing the customer population or the order count does not fix that multiplication.

## A query with safe intermediate grains

First aggregate each independent child table to one row per order. Then join those totals to the paid orders, and finally aggregate the paid orders per customer:

```sql
WITH line_totals AS (
    SELECT order_id,
           SUM(quantity * unit_price) AS gross
    FROM line
    GROUP BY order_id
),
refund_totals AS (
    SELECT order_id,
           SUM(amount) AS refunds
    FROM refund
    GROUP BY order_id
),
paid_order_totals AS (
    SELECT o.id AS order_id,
           o.customer_id,
           COALESCE(l.gross, 0) AS gross,
           COALESCE(r.refunds, 0) AS refunds
    FROM orders o
    LEFT JOIN line_totals l ON l.order_id = o.id
    LEFT JOIN refund_totals r ON r.order_id = o.id
    WHERE o.status = 'paid'
)
SELECT c.name,
       COUNT(p.order_id) AS paid_orders,
       COALESCE(SUM(p.gross), 0) AS gross,
       COALESCE(SUM(p.refunds), 0) AS refunds,
       COALESCE(SUM(p.gross), 0)
           - COALESCE(SUM(p.refunds), 0) AS net
FROM customer c
LEFT JOIN paid_order_totals p ON p.customer_id = c.id
GROUP BY c.id, c.name
ORDER BY c.id;
```

This query produces the three correct rows above in SQLite. Its grains and keys explain why:

| Relation | Grain and relevant uniqueness |
| --- | --- |
| `line_totals` | At most one row per `order_id`, enforced by grouping |
| `refund_totals` | At most one row per `order_id`, enforced by grouping |
| `paid_order_totals` | Exactly one row per paid order; `orders.id` is unique |
| Final join before grouping | One row per paid order with its customer, or one null-filled row for a customer with none |
| Final result | One row per customer, grouped by unique `c.id` and its name |

Joining an order to either pre-aggregated child relation can match at most one row. Neither join can multiply that order. Joining these order rows to customers intentionally produces one row per paid order, so counting and summing at the customer level now use each paid order exactly once.

The paid filter is inside the order relation. The outer query starts from every customer and does not subsequently filter out its null-filled rows.

### Paid orders with no lines

The left joins inside `paid_order_totals` preserve a paid order even if it has no lines, no refunds, or neither. Missing line totals become gross zero; missing refund totals become refunds zero. `COUNT(p.order_id)` still counts the real order, regardless of its children.

If a line-less paid order has a 7-cent refund, its contribution is one order, gross 0, refunds 7, and net −7 under your stated definition. An order with neither child type contributes one order and zero money. I also checked these cases with additional in-memory test rows; neither order was lost.

## Why the review proposals are incomplete

**Moving the paid predicate into the first `ON` clause repairs which customers survive**, provided it is removed from the final `WHERE`:

```sql
LEFT JOIN orders o
  ON o.customer_id = c.id AND o.status = 'paid'
```

`COUNT(DISTINCT o.id)` also repairs the order count because the business metric counts distinct orders. But the four line/refund pairings for Ada's order still exist. Her gross and refund sums remain doubled, and empty monetary sums still need zero handling. A correct count is not evidence that the joined rows have the right grain for summing money.

**`SUM(DISTINCT ...)` deduplicates numeric values, not business records.** For this dataset, distinct line amounts happen to be 100 and 60, and distinct refund amounts happen to be 15 and 5, so the technique can appear to work. It would discard legitimate repeated amounts elsewhere in a customer's group, including across separate orders.

For example, two different lines each worth 50 cents should contribute 100 cents; `SUM(DISTINCT quantity * unit_price)` contributes only 50. Equal unit prices create that problem when the resulting line amounts are equal; differing quantities may produce different amounts. Likewise, two genuine 5-cent refunds should total 10, but `SUM(DISTINCT r.amount)` gives 5. Separate records remain separate contributions even when their values match.

## Absence, zero, and `COALESCE`

An absent refund means there is no refund record. A left join represents that absence with null columns. A zero-valued refund is an existing record whose amount is 0. They have the same monetary contribution under this contract but different record counts and meanings.

A customer with no paid orders has no non-null order totals to sum. The final left join still supplies a customer row, `COUNT(p.order_id)` returns 0, and the monetary `SUM` expressions return `NULL` before `COALESCE` changes them to zero. Using `COUNT(*)` would incorrectly count that placeholder row as an order.

`COALESCE(value, 0)` chooses zero when `value` is null. It can implement the contract's empty-total display rule. It cannot restore a customer already removed by `WHERE`, remove multiplied contributions, identify genuine duplicate records, or turn a line/refund combination into an order.

The pre-aggregation protection also depends on later joins. Adding a table with several tags per order directly to `paid_order_totals` before the customer sums would repeat the already correct monetary totals once per tag. Keep later inputs at most one row per joined key, aggregate them first, or use `EXISTS` when only presence is needed. Every new one-to-many join requires checking the grain again.
