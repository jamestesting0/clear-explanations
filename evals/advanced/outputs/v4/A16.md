The checklist fails first at creating the unique index: accounts 1 and 2 both normalize to `li@ex.test`. Even after resolving that collision, the proposed deployment cannot enforce normalized identity while unrestricted version 1 writers remain, and its early schema contraction breaks the mixed fleet and the promised rollback.

## What fails, and when

| Proposed step | Consequence under the supplied rules |
| --- | --- |
| Add nullable `email_norm` | Compatible with version 1: its inserts can omit the new column. |
| Backfill existing rows | Without the proposed index, this succeeds but produces duplicate `li@ex.test` values for ids 1 and 2. |
| Create the unique index | Fails on those duplicate non-null values. Creating it before backfill instead would make the conflicting backfill fail. |
| Deploy version 2 to half the fleet | Its expectation of one account per normalized address is unsafe until collisions are resolved and every identity writer obeys the new rule. |
| Set `email_norm NOT NULL` | Fails if any nulls remain. Even if it succeeds at that instant, subsequent version 1 inserts fail because they omit the column. |
| Replace the original `email` with the normalized column | Discards the old representation and changes what old code reads. Removing the name `email_norm` also breaks deployed version 2 code that still references it. |

A completed backfill describes the rows it processed, not future writes. Version 1 can insert more nulls afterward. It can also change `email` on an already backfilled row without updating `email_norm`, leaving a non-null but stale value. Checking only for nulls therefore misses part of the problem.

## Why the race remains possible

In the supplied race, the two rows are:

| id | `email` | `email_norm` |
| --- | --- | --- |
| 4 | `PAT@EX.test` | null |
| 5 | `Pat@ex.test` | `pat@ex.test` |

The original case-sensitive constraint accepts both `email` strings. The nullable unique index accepts id 4's null and id 5's sole non-null `pat@ex.test`. Neither constraint compares id 4's calculated lowercase address with id 5's stored normalized address.

A fallback lookup that includes both stored normalized values and `lowercase(email)` for null rows finds **two candidates**. A lookup that returns a stored match before considering null rows may hide id 4, but hiding a conflict does not resolve ownership. Later filling id 4's `email_norm` fails against the index.

Fallback reads make missing values searchable; they do not reserve normalized identities or prevent competing writes. Version 2's transaction keeps its own pair of values consistent, but it does not bring version 1 writes into that transaction or its validation. Even an application check before insertion would need concurrency control covering every writer to prevent another writer inserting between the check and the insert.

## A staged migration

1. **Expand while retaining the old contract.** Add nullable `email_norm` and keep the original `email`, its values, and its case-sensitive constraint. Deploy a compatibility release that can use both representations, but keep single-result normalized login disabled until its prerequisites hold. During the initial rollback window, version 1 must still be able to read and write the original representation. The proposed version 2 needs a feature gate or additional handling for ambiguous lookup results; its stated assumption is not safe during this phase.

2. **Reconcile identities explicitly.** Inventory collisions by `lowercase(email)` across all accounts, including null and stale normalized values. Ids 1 and 2 require an ownership decision; so would ids 4 and 5. Preserve account ids, purchase histories, and access while carrying out the approved resolution. Backfill can proceed in resumable batches, but reconciliation must be repeated while old writers can create new conflicts. Do not create the unique index until the values it will index satisfy uniqueness.

3. **Transition every identity writer.** Upgrade or remove version 1's ability to create accounts and change email, covering application instances, background jobs, administrative tools, and transactions already in flight. Old instances could remain for compatible reads if identity writes are routed to the new path. Under the mechanisms actually supplied, a short pause in account creation and email changes is a straightforward way to drain old writes, perform final reconciliation, and establish the new constraints before accepting new writes again. Continuous writes would require an additional shared enforcement mechanism that covers old and new callers; none exists in the packet.

4. **Verify and enforce under that writer boundary.** Confirm that every row has `email_norm = lowercase(email)`, no normalized value belongs to multiple accounts, and no nulls remain. Establish the unique constraint and `NOT NULL` without a gap in which an uncontrolled writer can invalidate those checks. Resume identity writes only through paths that write both columns consistently and handle uniqueness failures. A nullable unique index may be an intermediate safeguard, but it is not evidence that the global identity rule already holds. Enable normalized login only after the one-account rule is established.

5. **Contract after the compatibility period.** Keep the old representation while any active code or approved rollback depends on it. Remove it only after deploying and verifying readers and writers that no longer need it, and after ending the version 1 rollback window. If a later schema must rename `email_norm`, coordinate that as another compatible schema transition; current version 2 cannot survive simply removing a column it names. Keeping an original address for display or recovery may remain a product requirement even after identity uses lowercase.

## Ownership and the evidence required

The product must decide how different owners can retain access when their addresses collapse to the same login name. Possible policies include verified address changes, an additional account identifier, or a verified consolidation process where ownership actually permits it. Selecting the lowest id, deleting the other row, or automatically moving purchases would decide ownership without evidence. Version 2 does not implement the verification necessary for a merge.

`NOT NULL` is justified by both a clean data check **and** evidence that all future accepted writes supply the value. Correct identity additionally requires equality with `lowercase(email)` and global uniqueness. Removing the old representation requires evidence that active consumers and rollback targets no longer rely on its name, original values, or write behavior—not merely that a backfill once finished.

A database still having a column named `email` preserves one piece of syntax. It does not preserve case-sensitive lookups, original address values, accepted inserts, uniqueness behavior, or the columns another binary names. Raw version 1 rollback must end before enforcing requirements that version 1 cannot satisfy, unless a separate compatibility mechanism is introduced and verified.
