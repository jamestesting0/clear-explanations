None of the three modes raises to the caller in the shown program. `clean` returns `ok`; `parse` returns `recovered` because the context manager suppresses its `ValueError`; `lookup` returns `forced` because the outer `finally` suppresses its `KeyError`.

## Exact output and why it occurs

Running the supplied program produces:

```text
clean ok open,body,commit,close,outer-finally
parse recovered open,body,rollback-value,close,after-with,outer-finally
lookup forced open,body,close,outer-finally
```

The `@contextmanager` wrapper runs the generator up to `yield` when entering the `with` block. That records `open`. On exit, it resumes the generator: normally if the block completed without an exception, or by raising the block's exception at the suspended `yield` if the block failed.

### `clean`: a return still exits the context normally

The body records `body` and evaluates `return "ok"`. Before the function can return, Python must exit the `with` block.

For the context manager, this is an exit without an exception. The generator resumes normally after `yield`, so its `try` completes successfully and its `else` records `commit`. Its `finally` records `close`. The pending function return then proceeds through the outer `finally`, which records `outer-finally` without replacing the return.

The caller receives `ok`. `after-with` is skipped because control is still following the return from inside the block. Normal context exit does not imply that execution continues at the next statement after the `with`.

### `parse`: the generator handles the exception

The body records `body` and raises `ValueError("bad input")`. Context-manager exit raises that same exception at the generator's `yield`. Its `except ValueError` records `rollback-value` and then finishes without re-raising. Its `finally` records `close`.

**The suppression happens when this exception handler finishes and the generator terminates normally.** The `contextmanager` wrapper interprets that normal termination after handling the injected exception as a handled exception. It does not automatically raise the original error again.

The `with` statement therefore completes, execution reaches `after-with`, and `work` selects `return "recovered"`. The outer `finally` records its event without overriding that return. The caller receives `recovered`.

The generator's `else` does not run: an exception was raised in its `try` and handled by its `except`. Handling an exception is not the same path as the `try` completing without one.

### `lookup`: the outer finalizer replaces the exception

The body raises `KeyError("missing")`, which is raised at the generator's `yield`. `except ValueError` does not match it, so no rollback event is recorded. The generator's `finally` records `close`, and the original `KeyError` remains unhandled by the context manager.

Execution is unwinding `work`, so it does not reach `after-with`. It enters the outer `finally`, records `outer-finally`, and executes `return "forced"`.

**That return is the suppression point for `KeyError`.** A return from `finally` replaces the pending exception, just as it can replace a return value selected earlier. Propagation is not irrevocably “selected” before finalization finishes. The caller consequently receives `forced`.

## What the claims and logs establish

The author is wrong about both suppression sites. Catching an exception inside the generator without re-raising can tell `contextmanager` that it was handled. Returning from a finalizer can discard an exception that otherwise would have reached the caller.

The reviewer is also wrong: a return from inside a `with` block still invokes context-manager exit. Removing only the outer finalizer's `return "forced"` would leave `clean` returning `ok` and `parse` returning `recovered`; only `lookup` would then raise `KeyError`.

Seeing `close` establishes that the append of that event executed. In this example it proves neither rollback nor exception propagation: `lookup` has `close` without rollback, and both failure modes have `close` without a caller-visible exception. Since these are event labels, they also establish no database action. If real cleanup is later added, the location of a log relative to that action matters as well.

## A small refactor for the stated ordinary failures

Handle both ordinary error types, re-raise after rollback, and let the outer finalizer perform cleanup without returning:

```python
@contextmanager
def transaction():
    events.append("open")
    try:
        yield
    except Exception:
        events.append("rollback")
        raise
    else:
        events.append("commit")
    finally:
        events.append("close")

def work(mode):
    try:
        with transaction():
            events.append("body")
            if mode == "parse":
                raise ValueError("bad input")
            if mode == "lookup":
                raise KeyError("missing")
            return "ok"
    finally:
        events.append("outer-finally")
```

For these event-only actions, the resulting behavior is:

| Mode | Caller observes | Events |
| --- | --- | --- |
| `clean` | `ok` | `open,body,commit,close,outer-finally` |
| `parse` | Original `ValueError` | `open,body,rollback,close,outer-finally` |
| `lookup` | Original `KeyError` | `open,body,rollback,close,outer-finally` |

The bare `raise` re-raises the active exception, preserving its identity, type, and existing traceback. It tells the context manager that rollback did not resolve the request failure. The caller's retry policy can therefore still distinguish `ValueError` from `KeyError`.

The outer `finally` remains useful: it runs on both normal and exceptional exits. The harmful behavior was its replacement return, not the existence of a finalizer. With no return or new exception from that finalizer, the pending result or exception continues outward.

## When cleanup itself can fail

The small refactor suffices for the supplied event appends. Replacing them with fallible rollback or close operations requires a more explicit error policy. A new exception from cleanup can become the outward exception, with the original available through Python's exception chaining. That is better than silently returning success, but it can still change which type a simple caller-side `except` sees.

A complete policy for ordinary exceptions should be:

1. Retain the original operation exception, if one occurred.
2. Attempt rollback on the operation-failure path. Record any rollback exception separately.
3. Attempt close even if rollback failed. Record its failure separately too. Apply the same principle to any fallible outer cleanup.
4. If the operation failed and cleanup succeeded, re-raise the original operation exception.
5. If only one completion or cleanup action failed, raise that failure rather than returning success.
6. If several failures occurred, report them together. On Python 3.11+, an `ExceptionGroup` can retain the actual original exception objects, for example an original `KeyError` plus a rollback error and a close error.

An exception group is one exception containing several constituent exceptions. Its outer type is `ExceptionGroup`, so callers must use group-aware handling, such as `except* KeyError`, or explicitly inspect the constituent failures. Preserving the original exception as a group member does **not** mean an ordinary `except KeyError` will catch the whole group. That caller contract must be updated deliberately if this representation is chosen.

If preserving the original top-level exception type is mandatory even during a simultaneous cleanup failure, define an explicit primary-error interface that carries the secondary cleanup errors and re-raises the original. Merely dropping the secondary errors, returning success, or replacing every error with one generic exception would violate the information requirements.

A failure of a real commit action also needs a persistence-specific policy; the event name `commit` supplies no evidence about whether an external change happened or can be reversed. Finally, this refactor deliberately addresses ordinary `Exception` failures. It does not establish a correct cancellation or interpreter-shutdown policy; those need separate reasoning about their exception classes and what cleanup is still possible.
