The final rejection handler runs and logs `outer:audit-failed`. The write failure is converted to `fallback`, but the later exception from `finally` replaces that successful outcome.

## Observable order

Running the supplied script on Node v24.22.1 produced:

```text
start | end | first | peer | await-resumed | nested | write:row | caught:write-failed | audit | outer:audit-failed | timer
```

This order follows from the queue and dependency rules in your assumptions:

1. **The initial script runs synchronously.** It logs `start`, arranges the promise callbacks, queues `peer`, starts the async function, schedules the timer, and logs `end`. The async function reaches `await 0` and suspends. Neither the promise callbacks nor the queued microtasks interrupt this running script.
2. **The initially queued microtasks begin in order:** the first promise callback, `peer`, and the continuation that logs `await-resumed`.
3. **The first callback logs `first` and queues `nested`.** Queueing puts the callback at the end of the microtask queue; it does not call it immediately. `peer` and the async continuation are already waiting, so both run before `nested`.
4. **The first callback returns the fulfilled promise for `"row"`.** Its downstream promise adopts that promise's outcome. This does not synchronously invoke the next `.then` callback. Promise reactions run as queued jobs, and `nested` is already queued before the dependent `write` reaction can run. Thus `nested` precedes `write:row`.
5. **The chain settles one dependent step at a time.** The write callback logs `write:row` and throws. The catch callback logs `caught:write-failed` and returns `fallback`. The finally callback logs `audit` and throws `audit-failed`. The final rejection callback then logs `outer:audit-failed`.
6. **The timer runs after this microtask work finishes.** It appends `timer` and prints the array.

`await` does not imply I/O. Even the immediately available value `0` causes this async function to resume later through a queued continuation. Its position here comes from when that continuation was queued, before `nested` was created.

Likewise, “already fulfilled” describes a promise's state, not permission to invoke a `.then` callback synchronously. Even returning a plain value from the first callback would leave the downstream callback asynchronous. No count of internal promise-adoption jobs is needed to establish the displayed order.

## What is wrong in the incident summary

The nested microtask does not run immediately: the currently running callback finishes, and work already ahead of it stays ahead. The async function does not wait for the timer: its continuation is a microtask and runs before the timer in this program.

The claim about the catch is correct: returning `fallback` changes the rejected chain into a fulfilled one. The claim about `finally` is incomplete. A finally callback normally preserves the incoming result or error, but only if it completes successfully. If it throws, or returns a promise that rejects, the chain takes that new failure instead. Here `audit-failed` replaces the fallback value. If the catch had re-thrown the original write error, this same finally callback would have replaced that error too.

The `success` and `error` callbacks passed to the last `.then` are alternatives. Because the incoming promise is rejected with `audit-failed`, only its error callback runs.

## Preserve the save outcome while observing audit failures

Here is an illustrative correction with an explicit policy: **wait for audit; if audit fails, also wait for an attempt to send that failure to the collector.** If collector delivery fails, retain both errors in a separate local diagnostic record. This local retention is the terminal policy in this sketch; it does not claim that a retry or durable delivery has happened.

```javascript
const undeliveredAuditFailures = [];

async function auditAndReport() {
  try {
    await audit();
  } catch (auditError) {
    try {
      await errorCollector.send(auditError);
    } catch (deliveryError) {
      // Policy: preserve both failures for local inspection/manual retry.
      // This local recording operation is assumed to be nonthrowing.
      undeliveredAuditFailures.push({ auditError, deliveryError });
    }
  }
}

// fallback is a previously determined result:
// { available: false }, or { available: true, value: draft }.
function saveWithAudit(fallback) {
  return Promise.resolve()
    .then(() => write())
    .catch(writeError => {
      if (fallback.available) return fallback.value;
      throw writeError;
    })
    .finally(auditAndReport);
}
```

The function names `write`, `audit`, and `errorCollector.send` represent the application's operations. Each asynchronous operation must return a promise representing its completion. Starting `write` inside `.then` also turns a synchronous throw from `write()` into the rejection handled by the catch.

The outcome rules are now:

| Save outcome | What the caller receives after the audit path finishes |
| --- | --- |
| Write succeeds | The original successful result |
| Write fails and a fallback exists | The fallback draft |
| Write fails and no fallback exists | The original write error |

`throw writeError` preserves the original error object on the no-fallback path. Audit and collector failures are handled inside `auditAndReport`, so its returned promise fulfills after either successful audit or the defined reporting policy. Consequently, `.finally(auditAndReport)` preserves whichever of the three save outcomes entered it. There is no detached collector promise whose rejection is left unhandled.

This deliberately catches failures of the auxiliary audit/reporting path; it does not suppress the primary write failure when no fallback exists. The retained record also avoids treating failed collector delivery as successful reporting. A production implementation could replace local retention with durable storage or a bounded retry policy, but the final failure of that mechanism must still have an explicit disposition.

Waiting affects response latency: a stalled audit or collector can delay the result. If you add deadlines, handle their failures through the same reporting policy. If you choose independent background audit instead, document that timing change and attach the rejection handling to every background promise.

Neither waiting nor detaching guarantees that audit finishes before a browser page closes. Durable delivery requires an additional mechanism appropriate to that environment. Timer delays and unrelated host scheduling can vary, but those caveats do not change the relative order forced by this self-contained program and its stated assumptions.
