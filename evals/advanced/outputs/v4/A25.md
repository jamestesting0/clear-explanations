Caching a Task fixes the reuse problem, and shielding each reader's await fixes cancellation spreading from that reader to the shared fetch. Neither change, by itself, supplies expiry, recovery from failed fetches, or ownership of background work.

## What the fixture prints

### Why caching the coroutine fails

Calling an `async def` function creates a **coroutine object**: one execution that has not yet been driven to completion. Here, `lru_cache` stores that object returned by `raw("x")`; it does not await it and cache the eventual string.

The first await runs the coroutine and obtains the reusable result value, `"loaded:x"`. The second call retrieves the same, already completed coroutine object. Awaiting it again raises `RuntimeError`, which the fixture catches and reports as `second-error RuntimeError`. [A25-CODE]

The three objects have different roles:

| Object | Meaning here | Reuse behavior |
|---|---|---|
| Coroutine object | One invocation of `raw` or `fetch` | Cannot be repeatedly awaited as a reusable result |
| Task | An event-loop-managed execution of a coroutine | Multiple readers can await the same execution and its completed outcome |
| Result value | The string produced by successful execution | Can be stored and returned without executing the coroutine again |

A completed Task retains its outcome, including an exception or cancellation. Reusability therefore does not necessarily mean a successful result.

### Without shielding

Both readers receive the same Task. Under the stated single-event-loop conditions, neither reader can interrupt the other's cache check and insertion: that portion contains no `await`. Only one `fetch()` Task is created.

Once both readers are awaiting it, `a.cancel()` propagates cancellation into the Task that A is directly awaiting. The fetch is interrupted at `gate.wait()`, and its `finally` block records `fetch:finally`. Because B is awaiting that same now-cancelled Task, B also receives `CancelledError`. Each reader catches the exception and records its cancellation; consequently, `await a` does not abort the enclosing experiment.

Setting the gate afterward cannot restart a cancelled Task. The dictionary still contains that Task, so `cached-cancelled` is `True`, and the later lookup receives cancellation again. This is a poisoned entry: no new fetch is attempted. [A25-CODE]

### With shielding

`asyncio.shield(task)` places a cancellation boundary between each reader's await and the shared Task. Cancelling A cancels A's wait and raises `CancelledError` in A, but it does not forward that cancellation to the fetch. A records `A:cancelled` while the useful work continues.

After A finishes, the gate opens. The existing fetch completes, records `fetch:finally`, and supplies `"loaded"` to B. Its Task remains successfully completed in the cache, so the later lookup returns `"loaded"` from the same execution. Shielding creates no fresh fetch. [A25-CODE]

Shielding also does not make the inner Task impossible to cancel. The cache owner can call `task.cancel()` directly during eviction or shutdown; cancellation originating inside the fetch can also reach its waiters. Shield protects the inner Task from cancellation propagated through this particular caller's wait, while the caller itself remains cancellable.

## A concrete cache lifecycle

Use separate records for **in-flight work** and **successful values with expiry times**, with the cache owning the work:

1. **Look up a successful value.** Return it if its expiry time is still in the future. Otherwise remove it. Measure elapsed TTL with a monotonic clock, such as the event loop's clock, and explicitly define the TTL to start at successful completion.
2. **Share an in-flight Task.** If the key already has a current fetch, use it. Otherwise create and register one without yielding between the check and insertion. Keep a strong reference to every owned Task until its completion is handled.
3. **Shield each consumer's wait.** A consumer's cancellation ends that consumer's wait; it does not decide the shared fetch's lifetime.
4. **Handle every completion.** On success, publish the value and expiry only if that Task still owns the key. On failure or cancellation, remove its in-flight entry so a later lookup can start a fresh attempt. Do not convert a failed Task into a permanent cached result.
5. **Observe background failures.** Register an owner-controlled completion handler that checks cancellation and retrieves and records exceptions from failed Tasks, even if every consumer has departed. Shielding does not do this reporting automatically.

For this design, choose an explicit policy: **continue an admitted fetch when all consumers leave**, so it can populate the cache. The cache may separately impose a fetch deadline or resource limit. A different policy could cancel when the last consumer leaves, but that requires consumer registration and release in `finally`, with the owner checking that the count reaches zero for the same current Task. It must not arise accidentally from an unshielded await. [A25-INTENT]

On explicit invalidation, discard the successful value and detach the current in-flight entry; this design can also cancel that owned Task and await its cleanup. On shutdown, stop accepting new work, cancel remaining owned Tasks, and await their termination while handling their outcomes. Retain ownership references even for Tasks detached from a key until their cleanup finishes.

### Why completion needs an identity check

Suppose old Task T1 was detached, and a later lookup installed T2 under the same key. T1's completion callback can run afterward. An unconditional `del in_flight[key]` would delete T2's entry, allowing another fetch to start and breaking sharing.

The removal must be conditional:

```python
if in_flight.get(key) is completed_task:
    del in_flight[key]
```

The same ownership check, or an explicit generation number, must guard publication of successful values: an obsolete completion must not repopulate an invalidated key or overwrite a newer result. The check and associated map changes should contain no `await` under the fixture's concurrency assumptions.

The fixture establishes coroutine reuse failure, shared cancellation without shielding, and cancellation isolation plus successful reuse with shielding. It contains no failing-fetch example, expiry mechanism, all-consumers-gone policy, or shutdown implementation. Those need the lifecycle rules above. The two sleeps only establish scheduling order; they are unrelated to TTL. Sharing through this dictionary is local to its owning process and event loop, with no distributed-cache guarantees.
