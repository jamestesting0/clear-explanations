One committed outbox event can produce two reservations because **creating the local event, creating a remote reservation, and marking the event sent are separate operations**. The outbox protects the order–event relationship inside the order service's database. The current retry keys prevent the receiver from recognizing that two requests represent the same intended reservation.

## The transaction boundaries and the incident

The first local transaction commits order O8 and event E8 together. The external reservation API's database is outside that transaction. A second local transaction later records that E8 was sent; it does not retroactively include the remote reservation (B29-S1).

| Step | Sender's durable state | Receiver's state |
| --- | --- | --- |
| 09:00: order transaction commits | O8 exists; E8 is unsent | No reservation from E8 yet |
| E8 sent with key A1; response lost | E8 remains unsent | R101 exists |
| 09:01: E8 retried with key A2 | E8 remains unsent until success is recorded | R102 is also created |
| Success received and sent flag committed | E8 is marked sent | R101 and R102 both exist |

The lost response leaves the sender unable to distinguish “the receiver did nothing” from “the receiver succeeded but I did not learn that.” Retrying is consistent with its instructions. The same ambiguity can arise if the sender receives success and then crashes before committing the sent flag. A crash before the first request reaches the receiver also leaves an unsent event, but in that case retrying can be necessary to obtain any reservation at all.

These windows explain why counting local orders or outbox rows cannot establish the number of remote effects. The local transaction created one event; the dispatcher made two requests, and the receiver accepted each as a distinct operation (B29-S3).

## Why the current keys defeat deduplication

The receiver recognizes a retry by its `Idempotency-Key`, within the same account and route. It does not independently recognize the `event_id` in the body. Consequently, preserving E8 in both bodies offers no protection when the headers contain different keys, A1 and A2.

Within the receiver's retention period, the same key and payload would return the original result. A changed payload with that key would return 409. Neither protection applies to this incident because the sender supplied a fresh key, despite keeping the payload unchanged (B29-S2).

## Comparing the proposed changes

**Marking sent before sending creates a loss window.** If the process commits the sent flag and crashes before making the request, normal dispatch will skip that event because it is already marked sent. The order and event exist, but no reservation was requested. A request lost before reaching the receiver creates a similar problem. Changing the order of these operations moves the failure window; it cannot make the local flag and remote effect atomic.

**Using a stable event-derived key addresses the demonstrated duplicate.** Every attempt for E8 should reuse the same collision-free key in the same account/route scope, with the same payload. In the observed one-minute retry, the receiver would then return R101's original result rather than create R102. The dispatcher could record success afterward; if it crashed before that update, another retry within retention would still refer to R101.

The resulting guarantee is bounded: **during the receiver's 24-hour retention period after first use, retries using that same scoped key and payload produce at most one reservation under the stated contract**. Multiple delivery attempts still occur. This does not guarantee eventual successful delivery under arbitrary failures, and it does not establish uniqueness after the receiver may forget the key.

## Old replays require an additional design

A manual replay at 36 hours is outside retention. Even a stable key may then create a new reservation. Suitable changes include:

- A durable receiver-side uniqueness rule for the business operation, such as account plus `event_id`, enforced atomically with reservation creation and retaining the original result for later requests.
- An explicitly bounded retry/replay horizon, with receiver deduplication retained for that entire horizon and enforcement preventing older requests from being blindly resubmitted.
- A reconciliation process for older or ambiguous outcomes that uses an authoritative durable operation record before deciding whether anything remains to be done. A separate lookup followed by an unprotected create can race, so the design must also prevent concurrent duplicate creation.

None of these additional protections is supplied by the packet. The existing R101/R102 incident also needs reconciliation; changing future retry keys does not remove an existing duplicate.

The overview's “exactly-once delivery” claim therefore exceeds the architecture. What is established is atomic local order-and-event creation, retrying when success is unrecorded, and—after the key change—bounded receiver deduplication. Those are distinct properties with distinct failure boundaries.
