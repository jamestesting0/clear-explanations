The gateway authenticated the request's bytes, but enforced its limit against a different interpretation from the one the allocation service executed. **The gateway checked `units = 1`; the service reserved `units = 40`.** Nothing in that sequence requires a broken HMAC algorithm or altered bytes.

## How Q9 passed the gateway and reserved 40 units

The signed body was:

```json
{"units":1,"units":40,"label":"test"}
```

1. **Authenticate the supplied bytes.** The gateway verified the HMAC over the exact body, method, and path using client K's key. The signature was valid, and the method and path remained `POST /allocations`. This establishes that the supplied bytes match the signature under that key; it does not establish that their resource request is permitted. [B18-S1, B18-S3]

2. **Parse and check the gateway's interpretation.** Its current parser keeps the first occurrence of a duplicate member name, so the resulting object is effectively `{"units":1,"label":"test"}`. The gateway checks 1 against the maximum of 10 and permits the request. Its `parsed_units=1` log confirms this interpretation. [B18-S1, B18-S3]

3. **Forward the original body.** The gateway sends the unchanged bytes, including both occurrences of `units`. The byte capture confirms that this is the same body that was signed. It does not send a new, unambiguous representation of the object it just checked. [B18-S1, B18-S3]

4. **Parse again and execute a different interpretation.** The service's parser keeps the last occurrence, producing `{"units":40,"label":"test"}`. It trusts the gateway's earlier limit check and does not enforce the limit itself. Its logs show both `parsed_units=40` and `reserved_units=40`. [B18-S2–S3]

The failure is therefore in the connection between the checked meaning and the executed meaning. The authenticated body reaches the service intact, yet the service acts on a value the gateway never approved.

## What “validated” means at each boundary

| Property | What Q9 establishes |
| --- | --- |
| **Integrity and authentication** | The signature was valid for K's key, and the forwarded body matched the signed body. |
| **Semantic agreement: assigning the same meaning to the bytes** | The parsers disagreed because they selected different duplicate fields. |
| **Authorization or business-rule enforcement** | The intended maximum of 10 was checked against 1 but not against the executed value of 40. |
| **A person's intent** | The records do not identify who constructed the body or why. |

Authenticated clients are permitted to submit their own payloads and are not trusted to obey resource limits. Authentication therefore cannot replace the limit check. Likewise, accepting only gateway-originated connections establishes the request's route, not agreement about what it requests. The account check succeeded for the correct account; this incident does not require cross-account access. [B18-S1–S3]

A valid signature under K's key does not prove that the human account owner deliberately exploited the mismatch. Intentional construction, serializer behavior, and another person's control of the key remain unresolved possibilities. [B18-S3]

## Fix the actual data path

**Reject duplicate member names before authorizing the parsed request.** Detection must occur while parsing can still identify the duplicates; checking an ordinary object after a first-wins or last-wins parser has discarded one occurrence can be too late. This would reject Q9 before its ambiguous content could pass the business-rule check. [B18-S4]

**Make the checked representation authoritative downstream.** Parse with defined rules, validate the integer value and its permitted range, and have the service execute that same validated representation. For example, the gateway could create an unambiguous internal request from the checked object instead of forwarding the ambiguous original body. The service's actual reservation value must remain tied to the value that passed validation.

**Enforce the per-request maximum at the allocation service.** Checking the service's parsed `units` immediately before reserving capacity would reject 40 even if an upstream parser mismatch remained. This places the rule beside the operation it governs; using it alongside duplicate rejection and representation agreement provides additional protection. [B18-S2, B18-S4]

**Changing only the signing representation is insufficient.** Canonicalization means converting a document into a prescribed representation. If signature verification uses that representation while the original ambiguous bytes still reach the service, the service can still select a different value. If canonicalization rejects duplicates, that rejection helps; merely choosing one duplicate value for signing does not ensure that the executed value matches it. Also, version 5 currently signs exact bytes, so changing verification to use canonicalized bytes requires a corresponding protocol change for signers—it cannot be silently substituted into the existing contract. [B18-S1, B18-S4]

The older checklist describes behavior explicitly removed in version 5. It cannot establish that current requests are canonicalized or duplicate-free. Encrypted connections and a high transport success rate likewise provide no evidence that the two parsers agree. [B18-S4]

## Scope of the finding

Q9 establishes an authenticated request reserving **40 units despite an intended per-request maximum of 10**, through the documented parser disagreement and missing downstream check. It does not establish signature forgery, transit tampering, the human sender's intent, or cross-account access. Nor can one incident establish the total extent of exploitation, the safety of other endpoints or versions, or broader guarantees about key custody and account isolation.
