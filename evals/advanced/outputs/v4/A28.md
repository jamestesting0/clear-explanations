After the partitioned operations merge, **apple is present because tag `a1` survives**. That is the specified observed-remove behavior: a remove cancels only add tags that the removing replica has seen. The separate cleanup experiment also makes apple present, but for a different reason: R2 discarded the evidence needed to suppress the old tag `a0`.

## States during the partition and after merging

An item is visible whenever at least one pair in `Adds` has that item and a tag absent from `Removed`. The tags distinguish additions; they do not represent units of quantity. [A28-STATE]

Both replicas start with:

```text
Adds    = {(apple, a0)}
Removed = {}
```

On **R1**, removing apple records `a0`. Re-adding apple creates the fresh tag `a1`, which has no removal marker:

```text
Adds    = {(apple, a0), (apple, a1)}
Removed = {a0}
Visible = {apple}
```

On **R2**, adding apple creates `b1`. Its subsequent remove sees both `a0` and `b1`, so it records both:

```text
Adds    = {(apple, a0), (apple, b1)}
Removed = {a0, b1}
Visible = {}
```

Neither remove deletes entries from `Adds`; it adds removal evidence. Neither replica knows the other replica's new tag during the partition. [A28-PARTITION]

Merging takes the union of each corresponding set:

```text
Adds    = {(apple, a0), (apple, a1), (apple, b1)}
Removed = {a0, b1}
Visible = {apple}
```

`a0` is suppressed by a removal marker. So is `b1`. Only **`a1`** remains unremoved, and that single surviving tag is sufficient to make apple visible.

## Delivery order and the review claims

Receiving the same state twice adds no new set elements. Reversing message order also leaves the final unions unchanged. Set union is **idempotent** (repeating it has no additional effect), **commutative** (order does not matter), and **associative** (grouping does not matter). Once replicas receive the same information, they reach the same state under this merge. Their intermediate views can differ while information is still missing. [A28-STATE; A28-MERGE]

The three review claims conflict with the specified rules:

- **“R2's last remove wins globally.”** Its remove wins over the additions it observed, `a0` and `b1`. It cannot remove `a1`, which R2 had not seen. A last local button press establishes local order, not knowledge of another replica's disconnected operation. Wall-clock timestamps have no role here. The survival of an unobserved concurrent add is part of the chosen conflict rule.
- **“Two tags mean quantity two.”** Visibility is a yes/no test for any surviving tag. Even several surviving tags would still mean one visible item membership. This protocol defines no numeric quantity.
- **“A retried delivery needs a fresh tag.”** A fresh user add creates a new tag; redelivery preserves the original tag. Giving a retry a fresh tag would turn duplicate delivery into a new operation. That new tag could escape an existing removal marker and create unintended presence. [A28-STATE; A28-MERGE]

## The separate cleanup experiment

Before cleanup, R2 has:

```text
Adds    = {(apple, a0), (apple, b1)}
Removed = {a0, b1}
Visible = {}
```

R2 then erases both sets. Its local view still shows no apple, but it has lost the distinction between “this tag was removed” and “this tag has never been seen.” R3 still holds:

```text
Adds    = {(apple, a0)}
Removed = {}
```

Their later union is therefore:

```text
Adds    = {(apple, a0)}
Removed = {}
Visible = {apple}
```

Apple has returned through the old tag `a0`, without a fresh user add. Keeping R2's `a0` removal marker would have suppressed it. This is unsafe reclamation of removal evidence, not the same situation as the valid survival of the fresh, unseen `a1` in the partition example. [A28-CLEANUP]

The merge can still converge after this mistake: both replicas can agree that apple is present. Agreement alone does not prove that cleanup preserved the intended removal history.

## What would justify reclaiming metadata?

A removal marker, often called a tombstone, cannot safely disappear merely because its replica currently displays the item as absent. The design must establish that information predating the removal cannot later be accepted as an unremoved addition.

One approach tracks **causal stability**: confirmation that a removal has reached every replica still permitted to participate, together with sufficient tracking of message history to prevent older states from undoing that knowledge. Acknowledgements can establish receipt, but “every online replica acknowledged” is insufficient when R3 remains an authorized offline replica. Even acknowledgements from all replicas need a rule for stale messages still in transit. A more advanced design can compact per-tag markers into shared causal summaries, but those summaries and their merge rules must still recognize old, removed additions.

A concrete alternative is an **epoch checkpoint protocol**, where an epoch is a version of the accepted replica membership and state history:

1. Establish the participating replica set and reconcile removals into a common checkpoint, coordinating concurrent writes or briefly pausing them.
2. Require every continuing replica to acknowledge the checkpoint. An unreachable replica must either delay cleanup or be formally retired from participation.
3. Install the cleaned checkpoint in a new epoch and reject old-epoch state and operation messages. This prevents queued old messages from restoring discarded additions.
4. Require a returning retired replica, such as R3, to replace its stale state with an authorized current snapshot before rejoining. It cannot directly merge its old state into the new epoch.

This adds coordination and admission rules beyond the supplied union merge. Simply waiting for an arbitrary duration, deleting matched pairs locally, or assuming an offline replica will never return does not provide those guarantees. The cleanup experiment explicitly lacks the required acknowledgement, retirement, and stale-message protections. [A28-CLEANUP]

The implemented contract is eventual convergence of observed-remove **membership**, assuming replicas exchange their accumulated states and preserve the required evidence. It does not provide a globally latest wall-clock remove, numeric quantity, stock reservation, prevention of overselling, or immediate agreement while disconnected. Those require additional semantics or coordination; none follows from union alone. [A28-STATE; A28-PARTITION]
