The current implementation finishes with **value 7**. Its token check prevents an older leader from overwriting a generation the storage server has already seen, but it ignores ordering between commands from the same generation. The repair is to compare the pair **`(token, sequence)`** atomically with the write.

## What happens to each arrival

The server starts at `max_token=40, value=0`. It accepts tokens greater than or equal to its remembered token and ignores sequence numbers. [A07-STORAGE]

| Arrival | Command `(token, sequence, value)` | Current implementation | State afterward |
| --- | --- | --- | --- |
| 1 | A: `(41, 1, 6)` | Accept: `41 > 40` | `max_token=41, value=6` |
| 2 | B: `(42, 2, 8)` | Accept: `42 > 41` | `max_token=42, value=8` |
| 3 | A: `(41, 2, 9)` | Reject: `41 < 42` | `max_token=42, value=8` |
| 4 | B: `(42, 1, 7)` | Accept: `42 = 42` | `max_token=42, value=7` |

Arrival 3 is an **old-leader write**. Arrival 4 is an **earlier command from the current generation**. The existing check handles the former, but not the latter.

A lease expiring changes who is entitled to act; it does not cancel requests already sent or remove them from the network. Thus, nonoverlapping leases do not make arrival 3 impossible. Even checking a lease immediately before sending would leave time for a pause, expiration, a new leader, and delayed delivery. [A07-LEASE]

There is also a limit to the existing token protection: storage rejects token 41 only after it has remembered a higher token. Merely granting token 42 at the lock service does not instantly update storage. Arrival 1 can therefore be accepted even if A's lease has already expired.

## An atomic rule that enforces both kinds of ordering

For each resource, store its latest accepted **revision**, meaning the pair `(token, sequence)`, together with the current value and the accepted command's payload. Compare revisions by token first; compare sequence numbers only when the tokens match. Thus, every `(42, …)` is newer than every `(41, …)`, while `(42, 2)` is newer than `(42, 1)`.

Perform this decision and any state change as one indivisible storage operation:

| Incoming revision compared with stored revision | Decision |
| --- | --- |
| Greater | Replace the value and stored revision; report one newly applied change |
| Smaller | Reject as superseded; make no change |
| Equal, identical payload | Return an explicit duplicate/already-applied result; make no change |
| Equal, different payload | Return a conflict; make no change |

Equality must cover the command's relevant contents, not just its identifier. Reusing one revision for different values is an invalid command identity, not a legitimate update. A legitimate next update needs a higher sequence number. Retries keep the original revision and payload, as stipulated in [A07-ARRIVALS].

With this rule, arrivals 1 and 2 produce `(41, 1), value=6` and then `(42, 2), value=8`. Arrival 3 has an older token, and arrival 4 has a smaller sequence within token 42. Both are rejected, leaving **value 8**.

Rejecting every equal *token* would be too restrictive: after accepting `(42, 1)`, the server must allow `(42, 2)`. The duplicate test belongs to the complete revision, not the token alone.

The minimal rule also handles an identical retry of a much older applied command: its revision is smaller, so it is rejected as superseded without changing the value or claiming a new change. If clients must receive the original successful result for **every** previously applied command, keep a durable command record keyed by `(resource, token, sequence)`, including its payload and result. An identical retry can then return that recorded result marked as a duplicate, even after later revisions have applied; a different payload under that identity is a conflict. This history is needed to distinguish an old applied command from an old command that never applied, not merely to prevent old writes from changing the value.

## Where enforcement belongs

The remembered revision must live with the authoritative resource state, survive restarts and failover, and govern every write path. Comparing the revision, updating the value, remembering the revision, and recording any newly applied result must be atomic. Otherwise, two requests could both pass a separate check and then update in the wrong order. Multiple storage replicas must enforce the same shared ordering rather than maintain unrelated local maxima.

Client clocks do not enforce this rule. They may disagree, and a timestamp comparison at a client cannot stop a request from arriving after a newer write. Likewise, a lease check before sending does not validate the request at the moment storage changes. The increasing token establishes generation order; the storage check enforces that order at the point where the effect occurs.

## What the correction guarantees

The stored revision never decreases. Once a command is accepted, no lower revision can overwrite it, and an identical retry cannot create a new business change. Because these commands are complete replacements, accepting sequence 2 before sequence 1 is consistent with the stated rule: the later command supersedes the earlier one.

This does **not** guarantee that every command is delivered or applied, that a response reaches its caller, or that work progresses during an indefinitely long network partition. Superseded commands may never apply at all. Eventual progress requires a writer with an acceptable revision to communicate with available storage and complete its retries. Ordering protection remains useful during failures, but it does not repair the communication failure itself.
