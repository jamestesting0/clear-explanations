**The deployed SDK 2.3.1 implementation and server 2.4 protocol govern these requests.** With `legacyMode=false`, `timeout` is ignored. Resolution uses the first non-nullish `timeoutMs` from call options, then constructor configuration; only if neither supplies a value does it convert the environment value with `Number`, using `1500` when the variable is absent. | Request | Client wait timer | Transmitted `x-deadline-ms` | Server computation budget |
|---|---:|---:|---:|
| R1 | 6000 ms | `6000` | 5000 ms |
| R2 | 2500 ms | `2500` | 2500 ms |
| R3 | No timer started | No request sent | None |

**R1:** Per-call `timeoutMs:6000` overrides constructor `2500` and environment `4000`. The server caps the transmitted 6000 ms budget at 5000 ms. [A15-REQUESTS] [A15-IMPLEMENTATION] [A15-SERVER]

**R2:** Per-call `timeout:1` is ignored, so constructor `timeoutMs:2500` wins. Neither legacy `timeout` value changes the units or budget. [A15-MIGRATION] [A15-REQUESTS]

**R3:** Constructor `timeout:30` is ignored. With no `timeoutMs`, the client evaluates `Number("2s")`, which is `NaN`, and rejects it before networking. An invalid environment value does not trigger the default. There is no duration-string parser in this build. [A15-IMPLEMENTATION] [A15-REQUESTS]

**The R1 trace is consistent:** 5030 ms is below the 6000 ms client timer. The server's 5000 ms limit covers computation starting on the server, while transit and response delivery add wall time. It is not a 5000 ms end-to-end limit. The trace alone does not locate that additional time precisely. [A15-SERVER] [A15-REQUESTS]
