The current windows advance by timestamp peer groups, so both events at `ts=20` see the balance after both events. `LAST_VALUE` returns the last status in that current frame, not the final status of the reporting population. The intended report needs its population filtered first, a deterministic `(ts,id)` window order, and different frames for the running balance and final status.

## What the current query computes

The supplied default frame is `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`. With `ORDER BY ts`, “current row” includes every row tied at the current timestamp. Those tied rows are peers.

| Returned id | Rows in the frame | `running_total` | `LAST_VALUE(status)` |
| --- | --- | --- | --- |
| 1 | id 1 | `5` | `open` |
| 2 | ids 1, 2, 3 | `5 + 7 - 2 = 10` | Last status among the timestamp-20 peers |
| 3 | ids 1, 2, 3 | `10` | Same peer-group endpoint |
| 4 | ids 1, 2, 3, 4 | `5 + 7 - 2 - 1 = 9` | `closed` |

The two timestamp-20 deltas are both included for either peer, so their summed result of 10 is invariant to the order between those two events. In contrast, choosing the last status depends on that order: the supplied run ended the peer group with id 3's `paid`, but `ORDER BY ts` alone does not specify that id 3 comes after id 2. The query does not guarantee `paid` rather than `review` for that endpoint.

The outer `ORDER BY ts,id` arranges the displayed results; it does not supply the missing tie-breaker inside either window. It is already present in the current query, so adding it again would not repair anything.

Three different values must remain distinct:

- `status` is the status stored on the current event.
- The current `LAST_VALUE` is the status at the end of the current timestamp peer group, with the order inside that group unspecified.
- The required `final_status` is the status on the final event of the selected reporting population, using the business rule `(ts,id)`.

## Corrected report

This query selects the reporting population before calculating either window:

```sql
WITH reporting_population AS (
    SELECT id, account, ts, status, delta
    FROM event
    WHERE ts <= 20
)
SELECT id, ts, status,
       SUM(delta) OVER (
           PARTITION BY account
           ORDER BY ts, id
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_total,
       LAST_VALUE(status) OVER (
           PARTITION BY account
           ORDER BY ts, id
           ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
       ) AS final_status
FROM reporting_population
ORDER BY ts, id;
```

Running this corrected query on the supplied data gives:

| id | ts | status | running_total | final_status |
| --- | --- | --- | --- | --- |
| 1 | 10 | open | 5 | paid |
| 2 | 20 | review | 12 | paid |
| 3 | 20 | paid | 10 | paid |

Each part has a separate job:

- **Population:** `WHERE ts <= 20` excludes id 4 before the windows see any events.
- **Account grouping:** `PARTITION BY account` calculates each account independently.
- **Logical ordering:** the window's `ORDER BY ts,id` applies the business tie-breaker. It puts id 2 before id 3.
- **Running-balance frame:** `ROWS ... CURRENT ROW` includes events from the beginning through the particular current event, yielding 5, then 12, then 10.
- **Final-status frame:** `... UNBOUNDED FOLLOWING` includes the end of the entire selected account partition on every row. Its last event is id 3, so every row displays `paid`.
- **Presentation:** the outer `ORDER BY ts,id` displays the computed rows in the desired order.

Changing to `ROWS` without adding the window tie-breaker would still leave the order of the two timestamp-20 events unspecified. Conversely, adding `id` inside the windows makes each ordering key unique here, but a frame ending at the current row would still make `LAST_VALUE` return the current event's status rather than the final report status.

## Filtering before and after windows

An outer filter around a subquery containing windows removes rows from the displayed result after those window values have been computed. It does not redefine the population used by the inner windows.

If the corrected full-partition `LAST_VALUE` were computed over all four events and only then filtered to `ts<=20`, the displayed rows would still be ids 1–3, but all would show **`closed`**, taken from the excluded id 4. Filtering first makes the final status **`paid`**, as required.

There is a useful qualification for this exact example: applying an outer upper-time cutoff to the **current, incorrect query** does not change its surviving window values. Its frames already end at the current timestamp, so the later `ts=30` event was never included in the frames for ids 1–3. Filtering before or after that query therefore leaves the same incorrect running balances `5,10,10` and the same current-frame statuses. The outer filter fixes neither its peer-group balance behavior nor its interpretation of “final.”

Likewise, a correctly ordered running balance alone would still give `5,12,10` for these three rows after an outer cutoff, because the removed event occurs later. That coincidence does not establish that filter placement is generally interchangeable: a whole-population final status changes here, and removing earlier contributing events can change running balances too.

## Removing window ordering

Removing the ordering from `SUM(delta)` gives a whole-account total on every row: 9 for the unfiltered four-event population, or 10 if `ts<=20` is selected first. Neither is the required sequence `5,12,10`.

A whole-population total and a running balance answer different questions. Similarly, removing ordering from `LAST_VALUE` would not define which event is last according to `(ts,id)`. The report needs an explicit population and logical order, with each frame chosen for the particular column's meaning.
