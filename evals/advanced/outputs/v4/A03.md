`copied` freezes which element references the list contains, but those references still point to mutable `StringBuilder` objects. `wrapped` additionally remains connected to the original list structure through `window`, so it does not even freeze which elements occupy those positions.

## What each object represents

| Variable | List structure | Element objects |
| --- | --- | --- |
| `base` | The mutable `ArrayList` | The original builders, subject to replacement |
| `window` | A view of `base` positions 1 and 2 | Whatever builders occupy those positions |
| `copied` | An unmodifiable snapshot of the view's element references | The original B and C builders |
| `wrapped` | An unmodifiable wrapper around the live `window` view | The builders currently exposed by that view |

`subList(1, 3)` includes index 1 and excludes index 3, so the initial window is `[B, C]`. A view uses the backing list's storage instead of taking a separate snapshot of its contents. The wrapper blocks changes through the wrapper but continues reading from that view.

`List.copyOf(window)` captures the references currently in the window. Subsequent replacements in the source do not replace references in `copied`. It does not copy the internal character data of each builder or make those builders immutable. This matches the supplied [Java 21 `List` API summary](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/List.html).

## Why the two mutations have different effects

`window.set(0, new StringBuilder("B2"))` replaces a reference. The view's position 0 corresponds to `base` position 1, so both now refer to the new B2 builder. `wrapped` delegates to that view and therefore also shows B2.

`copied` retains the old reference to the original B builder. That builder was not modified; it was merely removed from that position in `base`. Consequently, `copied` still shows B. For this `ArrayList`, replacement with `set` is not a structural modification that changes the list's size, so this operation does not invalidate the view.

`base.get(2).append("!")` instead changes an existing object. All four lists still refer to the same C builder. Appending to that builder changes what each list displays at its C position, including `copied`.

The first three lines of the supplied OpenJDK 21 observation are therefore:

```text
base=[A, B2, C!, D]
copied=[B, C!]
wrapped=[B2, C!]
```

The successful `append` and the failed `copied.add(...)` act on different things. `add` would modify the returned list itself, which is prohibited. `append` modifies a referenced builder, which the list does not control. The next output is:

```text
copied-add=blocked
```

Calling this result simply “immutable” would obscure the distinction. Its membership and element references cannot be changed through the result, including by `set`, but the state of its mutable elements can still change.

## What the later structural change establishes

`base.add(new StringBuilder("E"))` changes the backing list's structure outside the `window` view. Under the documented `subList` contract, the view's semantics are then undefined. OpenJDK 21 detects that modification when the supplied code calls `window.size()` and throws `ConcurrentModificationException`:

```text
window-size=invalidated
copied-after=[B, C!]
```

The exception does not establish that another thread exists. This one thread made an outside structural modification and then used the affected view. The name describes a category of conflicting modifications; it is not a thread detector.

The portable conclusion is that the old view must no longer be relied on after that outside structural change. The API boundary does not promise that every implementation, every operation, or every later access will throw that exact exception. The supplied trace is evidence of this OpenJDK behavior, not a universal guarantee of fail-fast detection.

`wrapped` still delegates to the same affected view, so wrapping it does not restore defined view behavior. In contrast, `copied` has independent membership and remains usable. It still shares its original B and C builders, so future changes to those particular builders could still change its displayed text.

## Construction that meets the report contract

Export `List<String>` and convert each builder into a string while constructing the report:

```java
static List<String> snapshotLabels(List<StringBuilder> labels) {
    var text = new ArrayList<String>(labels.size());
    for (StringBuilder label : labels) {
        text.add(label.toString());
    }
    return List.copyOf(text);
}

// Called at request time, while window is still a valid view:
List<String> report = snapshotLabels(window);
```

`toString()` captures each builder's current character content as an immutable `String`. Later builder edits cannot change that string. `List.copyOf` then prevents modification of the resulting list's membership and references.

In the stated one-thread example, calling this before either mutation produces a report permanently containing `[B, C]`. Calling it after the two element mutations, while the view is still valid, produces a report permanently containing `[B2, C!]`. Construct the report from a valid source at request time; copying an already invalidated view is not a repair strategy.

Calling `List.copyOf` twice would not achieve this. A second call still copies or reuses the same element references; it does not recursively copy the builders. It may even reuse a suitable unmodifiable list rather than allocate another list.

A safe public contract for the proposed result is: **“The report is an unmodifiable list of immutable label strings captured when the report is requested. Later changes to the source list or its builders do not change the report.”** Under your one-thread setup, construction reads a stable source during that request. A future multithreaded implementation would additionally need a way to obtain a consistent source snapshot during construction; that is separate from the displayed bug.

For more complex exported elements, an unmodifiable outer list alone remains insufficient. The contract would need a copying or immutable-conversion policy covering every mutable part reachable through those elements, including nested collections. Otherwise callers could retain a structurally fixed report whose contents still change before next week's comparison.
