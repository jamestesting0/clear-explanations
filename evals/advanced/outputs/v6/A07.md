**The current implementation finishes with value `7`.** Its token check prevents worker A from overwriting B after token 42 has reached storage, but it does not order B's own commands. The repair is to compare the pair **`(token, sequence)` atomically at storage**, with explicit handling for retries. [A07-STORAGE; A07-ARRIVALS]

## What each arrival does now

Storage begins at `max_token=40`, `value=0` and ignores sequence numbers.

| Arrival | Incoming command | Decision | State afterward |
| --- | --- | --- | --- |
| 1 | A: token 41, sequence 1, value 6 | Accept: `41 >= 40` | Token 41, value 6 |
| 2 | B: token 42, sequence 2, value 8 | Accept: `42 >= 41` | Token 42, value 8 |
| 3 | A: token 41, sequence 2, value 9 | Reject: `41 < 42` | Token 42, value 8 |
| 4 | B: token 42, sequence 1, value 7 | Accept: `42 == 42` | Token 42, value 7 |

These outcomes follow from the specified comparison, regardless of the order in which commands were sent. [A07-STORAGE; A07-ARRIVALS]

There are two different stale-write problems:

- **An obsolete leader:** arrival 3 belongs to generation 41 after storage has accepted generation 42. The existing token check rejects it.
- **An obsolete command within the current generation:** arrival 4 belongs to generation 42, but sequence 1 is older than the already applied sequence 2. The existing check accepts it because it ignores sequence.

Lease expiration does not retract an already sent message. A write issued under a valid lease can arrive after expiration; a paused client can also retain an outdated belief about its lease. Thus, leases alone do not make arrival 3 impossible. They govern grants at the lock service, while the delayed write is decided at storage. [A07-LEASE]

Rejecting every token equal to `max_token` would prevent arrival 4, but would also reject legitimate later commands from B. The distinction needed is between newer and older commands **within** token 42. [A07-REVIEW]

## An atomic rule that implements the business ordering

Call `(token, sequence)` a **revision**: it identifies a command's position in the required order. Compare tokens first; compare sequences only when tokens match. Formally, incoming `(t, s)` is newer than stored `(T, S)` when:

\[
t>T \quad\text{or}\quad (t=T\ \text{and}\ s>S).
\]

Consequently, any command from token 42 outranks every command from token 41, regardless of their sequence numbers. This matches the supplied business rule. [A07-ARRIVALS]

For each resource, store the latest accepted revision, its complete command payload, and the resulting value. Perform the following decision and any update as **one indivisible storage operation**:

| Incoming revision and payload | Storage action | Response meaning |
| --- | --- | --- |
| Revision is newer | Replace value and remembered revision/payload together | Newly applied command |
| Revision is equal; payload is identical | Leave everything unchanged | Already applied; duplicate retry |
| Revision is equal; payload differs | Leave everything unchanged | Conflict: one command identity has two payloads |
| Revision is older | Leave everything unchanged | Stale command; no new change |

“Payload” must cover the command's relevant contents, not merely the revision. Sequence numbers must remain attached to the same command on retry, as specified; assigning a fresh sequence to a retry would make it look like a new command. [A07-ARRIVALS]

Under this rule, arrival 2 stores `(42, 2)` and value `8`. Arrival 3 loses on token; arrival 4 loses on sequence. The corrected final value is therefore **`8`**. If B then sends `(42, 3)`, it can legitimately update the resource again.

An identical retry of the current revision receives an “already applied” receipt rather than another new-change indication. A retry of a command superseded by a later revision is rejected as stale, also without a new change. If the API additionally promises to reproduce the original success result for every historical retry, storage needs durable command receipts indexed by `(resource, token, sequence)`; retaining only the latest revision cannot establish whether an older command previously succeeded or was never applied.

## Where the ordering must be enforced

The remembered revision must live with the authoritative storage state that decides whether the write takes effect. Its comparison and update must be atomic with the value update, persist across restarts, and be respected by every server that can accept writes for the resource. Otherwise, separate servers or a restarted server could accept an older command using an outdated remembered revision.

A client-side check cannot enforce this: a pause or network delay can occur after the check but before arrival. Client clock comparisons likewise do not provide the specified generation-and-sequence order; clocks can disagree, and a timestamp check outside the actual storage update does not prevent another write from intervening. The increasing tokens and fixed sequences provide the ordering identifiers, while storage provides the enforcement point. [A07-LEASE; A07-ARRIVALS]

This rule also does **not** mean storage rejects an old token at the instant its lease expires. Until storage observes a newer revision, it may accept a still-delayed command with a revision higher than its remembered one. Enforcing lease validity at the instant of writing would require an additional mechanism beyond this revision comparison.

## What the correction guarantees

Accepted revisions move forward: an older generation or an older sequence cannot overwrite a newer revision already accepted by storage, and an identical retry cannot cause another business change. Because these commands replace the entire value, skipping sequence 1 when sequence 2 arrives first implements the requested “newer supersedes older” behavior. It does not promise to execute every command in send order. [A07-ARRIVALS]

The correction does not guarantee message delivery, delivery of responses, or eventual progress through a permanent network partition. A lost response can still leave the caller uncertain and require a retry. Progress requires communication and usable storage to become available again; the ordering rule preserves correctness while that progress is unavailable.
