The query has two independent defects: the `WHERE` clause removes customers without paid orders, and joining two separate sets of child records multiplies the amounts before aggregation. Repairing the customer population or the order count does not repair that multiplication. [A04-QUERY]

## What the current query returns

All monetary values below are integer cents.

| name | paid_orders | gross | refunds | net |
| --- | ---: | ---: | ---: | ---: |
| Ada | 4 | 320 | 40 | 280 |
| Ben | 1 | 40 | `NULL` | 40 |

Cy is absent. These results follow from [A04-DATA] and [A04-QUERY].

The **grain** of a relation means what one row represents. Before refunds are joined, Ada's paid order has two rows, one per line. Joining refunds on `order_id` then matches each of those lines to both refund records. The resulting grain is one line/refund combination within an order:

| Customer | Order | Line amount | Refund amount |
| --- | ---: | ---: | ---: |
| Ada | 10 | `2 × 50 = 100` | 15 |
| Ada | 10 | `2 × 50 = 100` | 5 |
| Ada | 10 | `1 × 60 = 60` | 15 |
| Ada | 10 | `1 × 60 = 60` | 5 |
| Ben | 20 | `1 × 40 = 40` | `NULL` |

Ada's four rows produce:

- `COUNT(o.id) = 4`, because order ID 10 appears four times.
- `gross = 100 + 100 + 60 + 60 = 320`.
- `refunds = 15 + 5 + 15 + 5 = 40`.
- `net = 320 − 40 = 280`.

Ben has one line and no refund. The refund `LEFT JOIN` preserves his line using a row whose refund fields are `NULL`. `SUM(r.amount)` therefore returns `NULL`, while the `COALESCE` inside the net expression converts that missing refund total to zero, giving `40 − 0 = 40`.

Ada's cancelled order 11 is removed by the paid-status condition. Cy initially receives an unmatched row from the `LEFT JOIN`, but its `o.status` is `NULL`. `WHERE o.status = 'paid'` retains only rows where that comparison is true, so it removes Cy's row too. [A04-QUERY]

## The required result

Ada has one paid order with gross `2 × 50 + 1 × 60 = 160`, refunds `15 + 5 = 20`, and net `140`. The cancelled order contributes nothing. The full business result is:

| name | paid_orders | gross | refunds | net |
| --- | ---: | ---: | ---: | ---: |
| Ada | 1 | 160 | 20 | 140 |
| Ben | 1 | 40 | 0 | 40 |
| Cy | 0 | 0 | 0 | 0 |

These are derived from the supplied records under [A04-CONTRACT].

## Aggregate each child set before joining

First reduce lines and refunds separately to at most one row per `order_id`. Then join those totals to paid orders, preserving all customers:

```sql
WITH line_totals AS (
    SELECT order_id,
           SUM(quantity * unit_price) AS gross
    FROM line
    GROUP BY order_id
),
refund_totals AS (
    SELECT order_id,
           SUM(amount) AS refunds
    FROM refund
    GROUP BY order_id
)
SELECT c.name,
       COUNT(o.id) AS paid_orders,
       COALESCE(SUM(lt.gross), 0) AS gross,
       COALESCE(SUM(rt.refunds), 0) AS refunds,
       COALESCE(SUM(lt.gross), 0)
         - COALESCE(SUM(rt.refunds), 0) AS net
FROM customer AS c
LEFT JOIN orders AS o
       ON o.customer_id = c.id
      AND o.status = 'paid'
LEFT JOIN line_totals AS lt
       ON lt.order_id = o.id
LEFT JOIN refund_totals AS rt
       ON rt.order_id = o.id
GROUP BY c.id, c.name
ORDER BY c.id;
```

The relevant grains are now:

| Relation or stage | What one row represents |
| --- | --- |
| `customer` | One customer, identified by `id` |
| `orders` | One order, identified by `id` |
| `line` | One line record |
| `refund` | One refund record |
| `line_totals` | One order with at least one line |
| `refund_totals` | One order with at least one refund |
| Joined rows before the final `GROUP BY` | One paid order, or one unmatched placeholder for a customer with none |
| Final result | One customer |

Grouping each child table by `order_id` makes that key unique in its totals relation. Each paid order can therefore match at most one line total and at most one refund total. Neither join multiplies an order row. `COUNT(o.id)` now counts orders correctly without `DISTINCT`; the unmatched customer row has a null order ID and contributes zero to that count.

The paid condition belongs in the orders join: it controls which orders match while leaving every customer eligible for output. Grouping by customer ID also keeps different customers separate even if they have identical names.

## Why the review proposals are incomplete

**Moving the predicate into `ON` and using `COUNT(DISTINCT o.id)` fixes population and count, but leaves the monetary inputs duplicated.** Ada would have a correct count of one alongside the same incorrect gross of 320 and refunds of 40. Cy would survive, but the proposed edits alone would still leave empty gross and refund totals as `NULL`, and `NULL − 0` is still `NULL`.

**`SUM(DISTINCT ...)` removes duplicate numeric values, not duplicate contributions from the same business record.** It happens to recover Ada's totals in this dataset because her two line amounts differ and her two refund amounts differ. But two legitimate lines each worth 40 cents must contribute 80 cents; `SUM(DISTINCT line_amount)` would contribute only 40. Two separate 15-cent refunds must similarly contribute 30, not 15. Equal amounts are not evidence that records are interchangeable. [A04-DATA, A04-REVIEW]

Pre-aggregation sums every legitimate child record exactly once before the independent child sets can multiply each other.

## Missing rows, zero amounts, and `COALESCE`

These situations have different record-level meanings:

| Situation | Before zero handling | Required monetary interpretation |
| --- | --- | --- |
| Order has no refund records | No refund-total row; the join supplies `NULL` | Refund total 0 |
| Order has a real refund record of amount 0 | A refund-total row with numeric 0 | Refund total 0 |
| Customer has no paid orders | One unmatched joined row; all monetary inputs are `NULL` | All totals 0; paid-order count 0 |

The contract deliberately displays the same refund amount for the first two cases, but they differ if you later need a count of refund records. Such a count should be calculated inside `refund_totals`, alongside its sum.

`SUM` ignores null inputs and returns `NULL` when it has no non-null amount to sum. `COALESCE(total, 0)` implements the contract's zero display rule. It cannot restore customers filtered out earlier, remove duplicated contributions, or correct the grain of a join.

A paid order with no lines still has a non-null `o.id`, so this rewrite counts it. Its gross contribution is zero. If it has refunds, those still contribute, and its net can be negative; if it also has no refunds, both totals are zero. No display-layer repair is required.

Finally, this safety depends on the uniqueness of the joined keys. Adding a raw one-to-many table, such as multiple shipment rows per order, before the final sums could repeat each order's totals again. Aggregate that new child relation to one row per order before joining it, or calculate the revenue totals before introducing that additional row expansion.
