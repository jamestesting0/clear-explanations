**The incident is consistent with the outbox design: one durable local event can cause multiple remote reservations.** The order and outbox event commit together, but the remote reservation and the later local “sent” update do not. A missing acknowledgment leaves the sender unable to tell whether the remote operation happened. [B29-S1]

## The transaction boundaries and the incident

There are three separate changes to state:

1. The order database commits O8 and E8 together. This prevents that committed order from lacking its corresponding committed outbox event.
2. The receiver creates a reservation in its own system.
3. After receiving success, the sender commits E8's sent flag in a second local transaction. [B29-S1, B29-S3]

The observed sequence crosses the gap between steps 2 and 3:

| Time / step | Remote result | Sender's durable status |
| --- | --- | --- |
| 09:00: commit O8 and E8 | No reservation established by this local commit | E8 unsent |
| Send E8 with key A1 | R101 created; response lost | E8 remains unsent |
| 09:01: retry E8 with key A2 | R102 created; success received | E8 still unsent until the update commits |
| Commit the sent update | Both reservations already exist | E8 sent |

This sequence is reported in the incident record. It requires neither two orders nor two outbox rows: the same row was delivered twice. [B29-S3]

## Why acknowledgment and crash windows matter

A request might fail before the receiver performs it, or the receiver might perform it and lose the response. A sender waiting without a response cannot distinguish those outcomes from the local sent flag alone. The incident demonstrates the latter case. [B29-S1, B29-S3]

A crash creates a similar window: even after receiving success, the dispatcher could crash before committing the sent update. On restart, E8 would still look unsent and be retried. This retry is useful when an earlier request failed to execute, but can repeat an already completed remote effect unless the receiver recognizes the retry. [B29-S1]

The receiver offers precisely that recognition through the **Idempotency-Key**: within its retention window, the same key and payload identify a repeat of the original operation. But A1 and A2 are different keys. Keeping E8 in the request body does not help because the receiver does not independently deduplicate that field. The current attempt-based keys therefore present each attempt as a new operation under the receiver's contract. [B29-S2, B29-S3]

## Comparing the proposed changes

**Marking sent before the request creates a loss window.** If the process commits that flag and crashes before sending, the event appears completed locally even though that attempt never reached the receiver. Normal processing of unsent rows will skip it. Moving the flag changes which failure is possible; it does not make the remote effect atomic with the local update. [B29-S1, B29-S4]

**A stable key derived from event_id addresses the demonstrated duplicate.** For E8, every retry must use the same key in the same account and route, with the same payload. In the observed one-minute retry, the receiver would then return R101's original result instead of creating R102. A different payload under that retained key would produce 409, not permission to reinterpret the same operation. [B29-S2–B29-S4]

The resulting guarantee is bounded: **within 24 hours after first use, retries covered by the same account, route, key, and payload reuse the original reservation result without creating another reservation.** Delivery attempts can still occur more than once, and successful completion still depends on communication and recovery. This is not an unconditional promise of exactly-once delivery or permanent uniqueness. [B29-S1, B29-S2]

## Old manual replays need additional protection

At 36 hours, the receiver may have forgotten the key. Reusing a stable key then may create a new reservation, so the permitted manual replay exceeds the protection currently supplied. [B29-S2, B29-S4]

A durable solution needs receiver-side protection covering the full replay horizon: for example, an atomically enforced uniqueness rule for the logical event or reservation, or deduplication retention at least as long as every permitted retry and replay. Indefinitely permitted replays require correspondingly durable protection. The identity check and reservation creation must be enforced together so concurrent attempts cannot both create reservations.

Until such protection exists, old ambiguous events need an authoritative reconciliation path before resubmission, with unresolved cases held for investigation. Merely checking for a reservation and then issuing an unprotected create can still race with another request. The packet supplies no completed reconciliation mechanism that resolves all such cases. A local flag change alone cannot fill that missing remote guarantee. [B29-S1, B29-S4; design implications]
