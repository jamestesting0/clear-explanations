In the shown program, none of the three modes raises an exception to the loop's `except` block. `clean` returns `ok`, `parse` returns `recovered`, and `lookup` returns `forced`. The two failures are suppressed at different layers. [A05-CODE]

## Exact output and control flow

```text
clean ok open,body,commit,close,outer-finally
parse recovered open,body,rollback-value,close,after-with,outer-finally
lookup forced open,body,close,outer-finally
```

### `clean`: the return waits for normal context-manager exit

Entering `transaction()` runs the generator through `open` to `yield`. The function then records `body` and reaches `return "ok"`.

That return is pending while Python exits the `with` statement. A return is not an exception, so the context manager resumes the generator normally after `yield`. The generator's `else` records `commit`, and its `finally` records `close`. The function's outer `finally` then records `outer-finally` without changing the pending return. The caller receives `ok`.

`after-with` is skipped because the pending return continues after cleanup; execution does not resume at the next ordinary statement in the function. [A05-CODE]

### `parse`: the context manager suppresses `ValueError`

The body raises `ValueError("bad input")`. The `contextmanager` machinery throws that exception into the suspended generator at its `yield`. The generator catches it, records `rollback-value`, runs its `finally` to record `close`, and finishes normally.

**The missing re-raise in the generator's `except ValueError` is the suppression point.** Normal completion after handling the thrown exception tells `contextmanager` that the exception was handled; its exit method consequently suppresses the body exception. It does not automatically raise it again.

The `with` statement therefore finishes normally, and execution reaches `after-with`, followed by `return "recovered"`. The outer `finally` records its event and permits that return. No `commit` event occurs because the generator took its exception handler rather than its `else`. [A05-CODE]

### `lookup`: the outer `finally` suppresses `KeyError`

The body raises `KeyError("missing")`, which is likewise thrown into the generator at `yield`. Its `except ValueError` does not match. The generator skips `else`, runs `finally` to record `close`, and lets the `KeyError` escape.

At this point the context manager has preserved the exception. The function is unwinding toward its caller, so it runs the outer `finally`. That block records `outer-finally` and executes `return "forced"`.

**That return replaces the pending `KeyError`.** An exception selected for propagation is still subject to control flow in a finalizer. Consequently the caller receives `forced`, and `after-with` is never reached. [A05-CODE]

Removing only the outer final return would produce `ok`, `recovered`, and a propagated `KeyError`, respectively. It would not make all three modes raise. The reviewer's claim overlooks normal context-manager exit on return and the separate suppression of `ValueError`. [A05-CLAIMS]

## What `close` proves

Here, `close` proves that the generator's finalizer appended that event. It does not prove that an exception reached the caller: one exception is handled inside the generator, and the other is discarded later by the function's finalizer. It also does not establish rollback, since the lookup path records no rollback event.

These are event labels, so none establishes actual persistence or resource recovery. In a real implementation, a log that cleanup started would additionally need to be distinguished from evidence that cleanup completed successfully.

## A small refactor for the shown operations

Catch the ordinary operation exceptions that require rollback, re-raise them, and remove returns from the outer finalizer:

```python
@contextmanager
def transaction():
    events.append("open")
    try:
        yield
    except Exception:
        events.append("rollback")
        raise
    else:
        events.append("commit")
    finally:
        events.append("close")

def work(mode):
    try:
        with transaction():
            events.append("body")
            if mode == "parse":
                raise ValueError("bad input")
            if mode == "lookup":
                raise KeyError("missing")
            return "ok"
    finally:
        events.append("outer-finally")
```

For the shown event-only operations, this gives:

| Mode | Caller observes | Event sequence |
| --- | --- | --- |
| `clean` | `"ok"` | `open,body,commit,close,outer-finally` |
| `parse` | Original `ValueError` | `open,body,rollback,close,outer-finally` |
| `lookup` | Original `KeyError` | `open,body,rollback,close,outer-finally` |

The bare `raise` re-raises the active exception with its existing traceback. It does not construct a replacement exception or turn the failure into a return value. Both ordinary failure types are now covered, and neither reaches an `after-with` recovery path.

The finalizer itself is useful: it ensures cleanup occurs during normal returns and exceptional exits. Its former `return` was dangerous because it replaced the pending outcome. It could also hide an exception raised by the context manager's cleanup on the lookup path.

## When cleanup can fail too

The simple refactor assumes the event appends succeed. Replacing them with fallible rollback and close operations requires an explicit policy for multiple failures. A plain cleanup exception can become the exception seen by the caller, with the original retained only in Python's exception context. That changes the top-level type and can break the stated retry policy.

To preserve the original `ValueError` or `KeyError` as the exception the caller catches, use this behavior:

1. Keep the original operation exception active as the primary failure.
2. Attempt rollback and close independently, so a rollback failure does not prevent an attempt to close. Catch ordinary exceptions from each cleanup operation and record their stage and original exception object.
3. Attach those cleanup failures to the primary exception in a structured field, such as `cleanup_failures`, and ensure the error-reporting boundary renders or records them. Then use bare `raise` while still handling the primary exception. Keeping only a note saying “cleanup failed” would lose useful failure details.
4. If there is no primary operation failure, propagate any cleanup failure. If several cleanup operations fail, represent all of them, for example with an `ExceptionGroup` on Python 3.11 or later.

Any fallible outer-function cleanup must participate in the same policy; otherwise it can still replace the primary exception after the context manager has preserved it. A failure in the successful completion action is also a failure to report, followed by an attempt to close. Whether rollback is appropriate after a failed real commit depends on that persistence system's semantics, which these event labels do not specify.

An alternative is to raise an `ExceptionGroup` containing both the operation and cleanup failures. That makes both failures explicit, but its top-level type is the group, not `ValueError` or `KeyError`. The caller's exception handling and retry classification must be updated if that representation is chosen. For the requirement to preserve the existing top-level operation type, attaching and reporting secondary cleanup failures is the compatible approach.

This is targeted handling of cleanup failures, with both failures retained; it is not broad suppression. The scope here is ordinary exceptions derived from `Exception`. It does not establish correct cancellation, interpreter-shutdown behavior, or real transaction recovery; those need their own lifecycle and persistence rules. [A05-REQUIREMENT]
