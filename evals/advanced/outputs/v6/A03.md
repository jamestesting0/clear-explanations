`copied` preserves which element objects were selected, but it still shares those mutable objects. `wrapped` preserves neither their text nor the selected references against changes through the backing list. Neither meets the full snapshot contract. [A03-CODE, A03-API]

## The four lists hold different kinds of references

Initially, the relationships are:

| Variable | List structure | Element objects it exposes |
| --- | --- | --- |
| `base` | The mutable `ArrayList` | Builders for A, B, C, D |
| `window` | A view of `base` at indexes 1 and 2 | The same B and C builders |
| `copied` | An unmodifiable snapshot of the selected element references | The original B and C builders |
| `wrapped` | An unmodifiable wrapper around `window` | Whatever builders that valid view exposes |

A **view** refers back to another list's storage. A snapshot of **references** retains its selected objects, but does not copy or freeze those objects' contents.

### Replacing B changes a list slot

`window.set(0, new StringBuilder("B2"))` replaces the reference at the first position of the view, which is index 1 in `base`. It does not edit the original B builder. Consequently:

- `base`, `window`, and `wrapped` now expose the new B2 builder at that position.
- `copied` still holds the original B builder, whose contents remain `B`.

`set` does not change the list's length, so this operation does not invalidate the view. The wrapper prevents changes *through the wrapper*, but does not prevent this permitted change through `window`. [A03-CODE]

### Appending to C changes a shared object

`base.get(2).append("!")` leaves the reference in the list unchanged. It mutates the C builder itself. All four lists still refer to that same builder, so all display `C!`.

This produces the first three observed lines:

```text
base=[A, B2, C!, D]
copied=[B, C!]
wrapped=[B2, C!]
```

The distinction is between replacing a reference in one list structure and changing the object that several structures refer to. [A03-CODE, A03-OBSERVATION]

## What the exceptions establish

`copied.add(...)` throws `UnsupportedOperationException`, producing:

```text
copied-add=blocked
```

That demonstrates that the list rejects the attempted modification. `List.copyOf` provides an unmodifiable list, including protection against replacing elements through `set`; it does not make the builders immutable. A caller could still invoke `copied.get(1).append("?")`, changing the shared C builder. Blocking list edits is therefore insufficient for the promised stable report. [A03-API]

Next, `base.add(new StringBuilder("E"))` changes the size of the backing list outside `window`. The resulting states must be described carefully:

| Variable | After `base.add(...)` |
| --- | --- |
| `base` | `[A, B2, C!, D, E]` |
| `window` | Its subsequent semantics are undefined by the supplied `subList` contract |
| `wrapped` | Still delegates to that affected view; it provides no independent snapshot |
| `copied` | Still contains the original B builder and the shared C builder |

OpenJDK 21 detected the invalidated view when the program called `window.size()`, yielding the observed final lines:

```text
window-size=invalidated
copied-after=[B, C!]
```

That `ConcurrentModificationException` does not establish that another thread exists. This program changes `base` and subsequently accesses an affected view in one thread. The name describes a class of modification problems; the actual cause here is the backing list's structural change. [A03-CODE, A03-OBSERVATION]

The portable boundary is the one in [A03-API]: after a structural backing-list change outside the view, its semantics are undefined. The observed exception is useful implementation evidence, but a maintainer must not rely on every later view access, or every implementation, throwing that exact exception. `copied` is independent of the view's list structure, so that invalidation does not invalidate its own membership.

## Return immutable text values

For this contract, return `List<String>` and capture each builder's text while constructing the report:

```java
static List<String> snapshotLabels(List<StringBuilder> labels) {
    var values = new ArrayList<String>(labels.size());
    for (StringBuilder label : labels) {
        values.add(label.toString());
    }
    return List.copyOf(values);
}

// At the request point, while this view is valid:
List<String> report = snapshotLabels(base.subList(1, 3));
```

`StringBuilder.toString()` captures the builder's current text in an immutable `String`. `List.copyOf(values)` then prevents changes to the returned list. The library can continue replacing its internal list elements and appending to its builders; neither action changes these strings. If constructed before the shown mutations, the report remains `[B, C]`.

In the stipulated single-threaded setting, the construction runs without another operation interleaving source edits. A future concurrent implementation would separately need to ensure that the capture represents one consistent point in time; neither list copying nor string conversion alone provides that coordination.

Calling `List.copyOf` twice does not help with mutable elements. Both calls concern list contents as references, not copying each builder. A second call may even reuse an already suitable unmodifiable list; allocation identity is not the snapshot guarantee. [A03-API]

A safe contract for this implementation is: **“The returned list and its string values are immutable. They preserve the labels' text captured for the request, and later edits to the source list or its builders cannot change the report.”** For more complex element types, that same promise requires an explicit policy for copying or freezing every mutable part visible through the report. Copying an outer object while retaining mutable nested objects would recreate the same defect at another level.
