Both `after-gather` checkpoints show `available=70` and `committed=0`, with A still pending and uncancelled. B has released its own reservation, but `gather` has propagated B's exception without cancelling A. [A01-CODE]

## Output and event order

The supplied program produces these six lines, first for `scenario(False)`, then for `scenario(True)`:

```text
after-gather {'available': 70, 'committed': 0} False False
final {'available': 70, 'committed': 30}
trace A:reserved,B:reserved,B:released,B:cleanup,caller:caught,A:committed,A:cleanup
after-gather {'available': 70, 'committed': 0} False False
final {'available': 100, 'committed': 0}
trace A:reserved,B:reserved,B:released,B:cleanup,caller:caught,A:released,A:cleanup,caller:cancel-observed
```

The common beginning is:

| Event | Available | Committed | Reservation still outstanding |
| --- | ---: | ---: | ---: |
| Initial state | 100 | 0 | 0 |
| A reserves 30, then waits at the closed gate | 70 | 0 | 30 |
| B reserves 20, then yields at `sleep(0)` | 50 | 0 | 50 |
| B raises `ValueError`; its handler releases 20 | 70 | 0 | 30 |
| B runs its `finally`; the caller catches B's error | 70 | 0 | 30 |

This gives the first checkpoint in each run. A cannot commit yet because the gate is still closed. It also has not been cancelled, so both `a.done()` and `a.cancelled()` are `False`. The caller's exception handler only appends an event; it does not release anything. [A01-CODE]

In the **non-cancelling run**, `gate.set()` lets A resume. A adds 30 to `committed`, records `A:committed`, and runs its `finally` before its result becomes available to `await a`. Its reservation becomes committed rather than available again, producing `{available: 70, committed: 30}`.

In the **cancelling run**, `a.cancel()` requests cancellation. When A resumes from `await gate.wait()`, `CancelledError` enters its coroutine. Its `except BaseException` releases 30 and re-raises; its `finally` then records cleanup. Only afterward does `await a` raise `CancelledError` to the caller, which records `caller:cancel-observed`. The final state is `{available: 100, committed: 0}`. [A01-CODE]

The accounting relationship throughout is:

```text
available + committed + outstanding uncommitted reservations = 100
```

At either first checkpoint, the missing 30 is A's outstanding reservation. Both final checkpoints have no outstanding reservation, so `available + committed` is again 100.

## Which mechanism does what?

**`gather` propagates the failure.** With the default `return_exceptions=False`, B's failure reaches the awaiting caller while A remains active. That propagation does not establish that every sibling finished or released its resources. The first reviewer's proposed rollback boundary is therefore incorrect.

**Cancellation enters the coroutine as an exception; it does not skip its handlers.** Here, A's handler catches cancellation, releases the reservation, and re-raises. Its `finally` runs during that exit. The second reviewer's explanation is also incorrect.

**Awaiting A establishes when A has finished.** Calling `cancel()` alone does not synchronously perform A's release. In this program, awaiting A waits through the release and finalizer and then reports the cancellation. The caller's `except asyncio.CancelledError` observes that result; it does not perform the release. [A01-CODE]

In Python 3.12, `asyncio.CancelledError` derives from `BaseException`, not `Exception`. Replacing the worker's `except BaseException` with `except Exception` would still catch B's `ValueError`, but would miss A's cancellation. A's `finally` would still append `A:cleanup`, while its reservation would remain outstanding: the cancelling run would finish with `{available: 70, committed: 0}`. This particular strategy therefore depends on catching cancellation for rollback and then re-raising it. A cleanup log entry alone does not establish that rollback happened.

Short examples that end immediately can obscure this distinction: shutting down `asyncio.run` cancels remaining tasks. If that happens after a caught `gather` failure, the shutdown cancellation is a separate cause of cleanup. In the supplied program, the request coroutine stays alive and explicitly decides what happens to A.

## A structure that enforces the group boundary

Give one coordinator ownership of the group response and of a ledger recording each reservation as `held`, `committed`, or `released`. Workers may prepare reservations, but do not publish participant success or perform an irreversible commit during preparation.

For the in-memory example, a concrete structure is:

```python
# Pseudocode: acquisition and ledger registration are one synchronous step.
holds = []
try:
    async with asyncio.TaskGroup() as group:
        for request in requests:
            group.create_task(prepare_and_register(request, holds))

    # Reached only if all preparations succeeded.
    # In this toy model, this is synchronous and cannot fail midway.
    commit_prepared_holds(holds)  # marks each hold committed
finally:
    # The task group has finished before this cleanup starts.
    for hold in holds:
        if hold.status == "held":
            release_and_mark_released(hold)

# Publish group success here. An outer handler publishes failure only
# after this entire scope has exited and releases have completed.
```

On an ordinary child failure, `TaskGroup` cancels unfinished siblings, waits for them, and raises its collected failure information. The outer cleanup also releases reservations belonging to workers that had already finished preparing; cancelling unfinished tasks alone would miss those holds. Recording ownership before the next `await` and assigning release to one owner prevent an acquired hold from disappearing from the ledger or being released twice.

This structure depends on preparation never committing and on the stated toy cleanup operations succeeding. If release becomes asynchronous, the coordinator must await it before responding. If release fails or its completion is uncertain, merely ending the tasks cannot prove that every hold was released; the operation needs a recovery state and a policy for completing that recovery.

## Where external transfers change the problem

Neither `gather` nor `TaskGroup` makes an external transfer transactional. A sibling can already have committed before cancellation arrives, and a timeout or cancellation can leave the coordinator unsure whether a remote commit succeeded.

The external design therefore needs durable reservation and transfer states, a way to reconcile uncertain outcomes with the provider, and stable operation identifiers so retries cannot duplicate a transfer. Release only reservations confirmed to be uncommitted. Preserve any committed transfer even when the group response is a failure, as the requirement specifies. [A01-NOTES]

If the business additionally requires every transfer to commit together or none to commit, that needs an external protocol capable of providing that guarantee. A local preparation barrier reduces premature commits but cannot prevent partial success among independent remote commits. The in-memory counter example proves the shown task ordering and accounting; it does not establish those external guarantees.
